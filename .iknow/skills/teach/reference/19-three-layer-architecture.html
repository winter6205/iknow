核心定义

Harness（运行时壳） 有状态的编排层。负责：拼上下文窗口、执行工具、权限检查、Hook 触发、会话持久化、子代理调度。
关键属性：每次 LLM 调用前由 Harness 重组上下文；Harness 拥有控制权，LLM 没有。
Agent Memory（会话记忆） 单次会话内的上下文管理。包括：对话历史 transcript、当前状态、跨轮先验（prior chunks）。
关键属性：会话结束消失；自动注入上下文窗口；不需要工具调用就能被 LLM 看到。
External Knowledge Base（外置知识库） 跨会话持久化的结构化知识。通过工具接口（MCP / 函数调用）按需检索，不自动出现在上下文中。
关键属性：LLM 必须主动调用工具才能"换页"进来；是 LLM 上下文与持久化世界的硬边界。

关键边界

🔴 工具面（Tool Surface） External KB 与 LLM 之间的硬边界。LLM 只能通过工具调用（kb_retrieve / kb_compile / MCP 等）访问 KB，不能直接读取。即使 KB 有 10 万条事实，LLM 也"看不到"，除非主动检索。
🔴 上下文窗口（Context Window） LLM 每次调用能看到的全部内容。由 Harness 拼装：system prompt + CLAUDE.md + conversation transcript + tool schemas + 最新 tool_result。窗口外的知识对 LLM 等于不存在。
🔴 会话边界（Session Boundary） Agent Memory 与 External KB 的分水岭。会话结束 = Agent Memory 消失；KB 持久化就保留，不持久化就消失（iknow 就是不持久化，重启全清空）。

iknow 的具体缺陷

  • 无持久化：InMemoryKnowledgeStore 是纯内存对象，进程重启全部丢失（docs/architecture.md:65 明确列为 non-goal）
  • 无跨会话记忆：每次启动 CLI 都是空白状态，需要重新 seed
  • 无外部 LLM 知识：只有 seed-kb.ts 硬编码的 HR/IT/财务文档

你接下来想做的：把 iknow 升级到 gbrain 级别

这意味着给 iknow 加一个持久化的 External KB。最低成本的路径：

  1. 把 InMemoryKnowledgeStore 替换成 SQLite + sqlite-vec（轻量、单文件）
  2. 或者把 gbrain 作为 MCP server 接进来（gbrain serve --http + MCP client）
  3. 保留 iknow 的 4 个 kb_* 工具作为"统一接口"——内部实现换成 gbrain 的 hybridSearch

无论选哪条路，三层架构不变：iknow 的 Harness 继续拼上下文；Agent Memory 继续管会话；External KB 变成持久的。
