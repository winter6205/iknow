09 · 工程化实践

AI Agent 从「能跑」做成「可观测、可容错、可计费、可审计、可上线」

来源：PDF 第 178–203 页《08 工程化实践（面试八股文）》。卡片为压缩提炼，[原文 Pxxx] 标注出处页码，供教学引用。

1. 模型路由与容错

模型路由 Model Routing 像快递分拣中心——按「任务类型、成本预算、延迟要求、合规区域」决定请求走哪家模型，而不是所有流量打同一端点。 [P178]
容错 Fault Tolerance 某家模型超时/限流/报错/质量异常时，系统自动切换、重试或降级，对用户表现为「慢一点」或「差一点但可用」，而非整站不可用。 [P178]

多模型管理（统一抽象）[P179]

  • Provider Adapter：每厂商一个适配器，统一接口 chat(messages, tools, model_id) -> Completion。
  • 配置中心：维护 model_id → endpoint / 密钥 / RPM-TPM 限额 / 区域 / 价格表。
  • 能力矩阵：标注是否支持 JSON Mode / 函数调用 / 视觉 / 长上下文，路由时做能力匹配。
  • 密钥与合规：国产与海外模型涉及数据出境与行业合规，路由也是合规路由。

优先级调度策略[P179]

策略 含义 适用
固定优先级 列表顺序尝试 简单可靠
成本优先 满足质量阈值下选最便宜 批处理、非实时
延迟优先 SLA 内选最快 交互式产品
负载感知 结合队列深度、429 率动态调整 大规模生产
任务分类路由 代码类→A，摘要类→B 提高性价比

优先级不是「永远用大模型」，而是在约束下最优化（成本/延迟/质量/可用性）。[P179]

三态熔断器 Circuit Breaker[P180]

  • Closed：正常转发；统计失败率/连续失败次数。
  • Open：失败超阈值，快速失败（不再调下游），进入冷却。
  • Half-Open：冷却结束，放行少量探测请求；成功回 Closed，失败回 Open。

与重试的关系：熔断解决「系统性故障时的雪崩」；重试解决「偶发网络抖动」。二者常一起用：熔断打开时不再重试下游，改为降级。[P180]

自动降级[P180]

  • 模型降级：强模型→弱模型。
  • 功能降级：关多步 Agent 改单轮问答；减少工具数量。
  • 输出降级：长文→要点列表。

关键：降级要可观测（degraded=true），最好对用户透明提示。[P180]

重试与指数退避[P180]

公式：wait = min(cap, base * 2^attempt + jitter)，jitter 避免惊群效应。可重试：超时/连接错误/429/部分 5xx；不可重试：401·403·400·内容政策拒绝。[P180]

Q1 为什么做模型路由而非全量用最强模型？
A 最强模型更贵更慢，且并非所有子任务都需要；路由在质量/成本/延迟/可用性/合规间权衡，多供应商提高容灾。[P181]
Q2 熔断器和重试分别解决什么？一起用注意什么？
A 熔断防故障扩散和雪崩；重试提高偶发成功率。熔断 Open 阶段停止盲目重试同一下游，改降级/切供应商；对 429 用限流+退避避免放大拥堵。[P181] 
@dataclass
class CircuitBreaker:
    failure_threshold: int = 5
    success_threshold: int = 2   # 半开阶段连续成功次数
    open_seconds: float = 30.0
    half_open_max_calls: int = 3
    # 状态机: CLOSED -> (失败超阈值)-> OPEN
    #        OPEN -(冷却结束)-> HALF_OPEN
    #        HALF_OPEN -(连续成功)-> CLOSED
    # 退避: wait=min(cap, base*2**attempt + jitter)   [P181-183]

2. Token 成本控制

Agent 多轮多工具，上下文膨胀极快；目标是让每次会话/任务/租户支出可预测、可优化、可告警。[P184]

  • 计数：tiktoken 按 encoding_for_model 选编码；本地计数只是估算，应与 API 返回的 usage 对账。[P184]
  • 精简 Prompt：删冗余/合并系统提示；结构化输出减少澄清；长文档先摘要或 RAG 取 Top-K；消息裁剪保留 system+最近 N 轮+关键摘要。[P184]
  • 缓存策略：精确缓存（哈希完全一致命中，实现简单命中率低）；语义缓存（embedding 相似度复用，命中率高但需防「相似但意图不同」）；结果分层（热问题走缓存冷问题走模型）。[P184]
  • 模型选择/批量：小模型做分类/路由/摘要，大模型做生成；Batch API 非实时更便宜；合并短任务。[P185]
  • 监控告警：维度=租户/功能/模型/Agent 步骤；指标=日均 Token、单次 P95 成本、异常飙升；预算封顶硬限制。[P185]
Q3 为什么 tiktoken 计数只能「估算」？
A 实际计费依赖服务商分词器版本、特殊 token、多模态输入；本地计数用于预算控制与截断，应以 API usage 与账单对账。[P185]
Q4 语义缓存和精确缓存怎么选？
A 低成本高 QPS 重复咨询适合语义缓存；强合规强正确性场景需提高阈值、加业务校验或禁用；精确缓存适合幂等调用。[P185]

3. 全链路可观测性

Agent 路径依赖模型决策，分支多、偶现问题多，没有 Trace 很难排障。[P187]

  • 结构化日志：JSON 一行一条（ELK/Loki/ClickHouse）；字段含 timestamp/level/trace_id/span_id/tenant_id/agent_name/step/model/latency_ms/token_usage/error_code。切忌只打一大段自然语言。[P187]
  • 链路追踪：Trace=一次请求从头到尾；Span=一个单元（一次 LLM 调用/工具执行/检索）；span_id/parent_span_id 构成树。[P187]
  • 每步记录：step_index、thought 摘要、tool_name、tool_args（脱敏）、observation 摘要、耗时、重试次数、是否降级。[P187]
  • 工具：LangSmith（与 LangChain 结合紧）；LangFuse（开源可自托管，偏产品分析+成本+质量）。[P187]
Q5 Agent 为什么比传统服务更需要 Trace？
A 传统调用链相对固定；Agent 路径依赖模型决策，分支多。Trace 能把「哪一步选了哪个工具、参数是什么、返回多长」串起来。[P188]
Q6 结构化日志和 Trace 区别？
A 日志是事件流，适合检索告警；Trace 是因果树，适合分析延迟与依赖。二者通过 trace_id 关联，互补而非二选一。[P188]

4. 安全与权限

默认假设「模型不可信」：输入可能恶意、输出可能有害、工具调用必须经权限与校验。[P189]

  • Prompt 注入：用户自然语言覆盖系统指令；缓解=分层指令、特权数据与用户原文不同上下文、输出结构化由代码校验、最小权限工具。[P190]
  • 越狱 Jailbreak：绕过安全对齐；缓解=安全分类器、输入输出策略、关键操作 HITL、审计。[P190]
  • 输出过滤：PII/身份证/信用卡正则；二次分类；敏感词与行业合规列表。[P190]
  • 工具调用权限：白名单（每租户/角色可用工具）；参数校验（JSON Schema、范围、SQL 参数化）；两步授权（模型提议→策略引擎批准→执行）。[P190]
  • 数据脱敏：日志/Trace 中手机号邮箱地址打码；RAG 结果按权限过滤。[P190]
  • 审计日志：谁在何时、对什么资源、通过哪个 Agent、执行什么工具，不可被普通用户删除。[P190]
Q7 为什么「永远不信任模型输出的工具调用」？
A 模型可能被诱导产生危险参数；应对工具调用做 schema 校验、权限检查、速率限制，必要时人工确认，不能把模型当安全边界。[P190]
Q8 Prompt 注入和越狱区别？
A 注入侧重篡改指令/上下文改变行为；越狱侧重绕过安全对齐输出违规内容；防护需多层（输入/模型/工具/输出/审计）。[P191]

5. 部署与运维

容器化+K8s 为主；自托管需 GPU 与专用推理栈。[P192]

  • Docker：镜像环境一致；env 放密钥/路由/开关；/health 探活。[P192]
  • K8s：Deployment 副本滚动更新；HPA 按 CPU/QPS 扩容；Service/Ingress 暴露+TLS；ConfigMap/Secret 配置密钥分离。[P192]
  • CI/CD：CI=lint/单测/镜像构建/漏洞扫描；CD=灰度发布/自动回滚。[P192]
  • 蓝绿 vs 金丝雀：蓝绿两套环境切换、回滚快、资源占用高；金丝雀小流量新版本，指标异常即回滚，风险更可控。[P192-193]
  • 模型版本管理：Prompt/模型名/工具清单版本一并记录到 Trace 与配置；不可变发布标签（如 v20260401）。[P193]
  • A/B 测试：对 Prompt/模型/工具策略分流，比较任务成功率/成本/延迟/满意度，需统计显著性。[P193]
Q9 金丝雀发布关注哪些指标？
A 错误率、P95 延迟、Token 成本、业务指标（任务完成率、投诉）；Agent 还看工具失败率/重试率/熔断率。[P193]

6. 性能优化

瓶颈常在串行 LLM 调用、工具 RTT、过大上下文；方向：并行、流式、限流、缓存、连接复用。[P195]

  • 异步：asyncio/消息队列，I/O 等待不阻塞线程；无依赖工具并行。[P195]
  • 流式：边生成边 SSE，TTFB 下降；注意中间状态与最终答案一致性。[P195]
  • 并发控制：Semaphore 限制同时 LLM 调用数，防 429。[P195]
  • 连接池：HTTP keep-alive；DB 连接池。[P195]
  • 缓存分层：L1 进程内 LRU（极低延迟）；L2 Redis（多实例共享，需 TTL 序列化）；读路径 L1→L2→回源模型。[P195]
Q10 Streaming 影响计费或日志吗？
A 计费仍以 Token 为准；日志需聚合完整响应再记一条，或记增量 chunk 并关联 trace_id；注意流式中途断开的部分结果处理。[P195-196]

7. 评估与测试

没有度量就没有优化。覆盖：对不对（准确性）、稳不稳（鲁棒性）、快不快与贵不贵（效率）。[P197]

维度 含义 示例指标
准确性 任务完成、答案正确 人工标注、LLM-as-judge（谨慎）
鲁棒性 噪声/对抗/边界 成功率方差、最坏 case
效率 步数/延迟/费用 平均工具调用次数、Token
  • 测试框架：单测（工具解析/路由/熔断状态机）；集成（Mock LLM 固定输出）；端到端（沙箱+小型真实调用）。[P197]
  • Benchmark：固定数据集+评分器，注意数据泄漏与评分器偏差。[P197]
  • 人工 vs 自动：自动跑大规模筛选，人工抽审争议样本。[P197]
Q11 用 LLM 给 LLM 打分有啥坑？
A 可能偏好冗长、格式讨好，与裁判模型强相关；应对=人机混合、多裁判投票、规则评分结合、对抗样本集。[P198]
Q12 如何设计 Agent 回归测试集？
A 覆盖主路径、典型失败、工具错误、长上下文、多语言；每条含输入、期望工具或答案要点、不可出现项；版本化并与 CI 集成。[P198]

8. 幻觉问题的工程解决方案

事前—事中—事后三层治理。[P200]

  • 事前：RAG 用可靠片段 grounding；结构化 Prompt「仅依据引用回答」；限定领域与数据源。[P200]
  • 事中：置信度过滤；工具验证（计算/查询/代码执行以外部为准）。[P200]
  • 事后：事实核查（检索交叉验证/数据库比对）；引用标注（逐句带来源编号）。[P200]
Q14 RAG 一定能降幻觉吗？
A 不一定。若检索质量差、重排失败、模型忽略上下文仍可能错答；需检索评估、重排序、引用约束、拒答策略。[P200]
追问：工具结果与检索矛盾听谁的？ → 定义优先级（权威数据库 > 实时工具 > 检索片段）；矛盾时输出不确定并建议人工。[P200]

9. 综合面试题库（节选 15+）

Q15 多模型网关架构？ → 统一 Adapter；配置中心维护能力与配额；入口鉴权+租户路由；优先级调度+熔断+重试退避+降级链；全链路 Trace+usage 计费；密钥按租户环境隔离。[P201]
Q16 指数退避为何加 jitter？ → 避免大量客户端同一时刻齐刷刷重试造成重试风暴。[P201]
Q17 语义缓存如何保证安全？ → 分租户隔离、键含模型与 Prompt 版本、相似度阈值保守、敏感任务禁用或二次确认、TTL 与主动失效。[P201]
Q18 OTel 在 Agent 里打哪些 Span？ → 顶层请求 Span；子 Span 含每次 LLM/检索/工具/重试/降级；属性 model/token/tool.name/error.type。[P201]
Q19 工具「两步授权」？ → 模型仅生成意图与参数 → 策略服务校验角色/资源 ID/速率 → 执行器真正调用。[P201]
Q20 蓝绿 vs 金丝雀？ → 蓝绿适合二进制切换、快速回滚、可接受双倍资源；金丝雀适合渐进验证、对错误更敏感的生产流量。[P201]
Q21–Q29 含 HPA 指标、异步吞吐、真实成本监控、评估集泄露、幻觉排查、最小可观测方案、关键/非关键路径分级、Semaphore 设多大、为何 Prompt 需版本化。[P201-203]
