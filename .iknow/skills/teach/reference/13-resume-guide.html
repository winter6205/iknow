小白向 · 详细版：可直接复制的模板、句式与模块描述

来源：PDF 第 263–279 页《AI Agent 项目简历撰写指南》。卡片为压缩提炼，[原文 Pxxx] 标注出处页码，供教学引用。

0. 使用方式建议

  1. 先通读「总原则」与「常见简历问题诊断」，建立标准。
  2. 按主语言（Python / Java / Go）复制「项目经历模板」，填数字与职责。 [P263]
  3. 从「各模块描述示例」里挑与项目相符的句子，拼进「核心职责 / 技术亮点」。
  4. 对照「技能清单写法」整理一页纸技能区，最后做一遍文末「三问自检」。

1. 简历撰写总原则

1.1 STAR 法则在简历中的应用

字母 英文 含义
S Situation 情境：业务背景、用户是谁、数据/流量规模
T Task 任务：要达成的目标、要解决的矛盾（延迟、成本、准确率等）
A Action 行动：你具体做了什么技术决策与实现
R Result 结果：可验证的指标、上线效果、复盘结论

简历与面试的区别：面试可按 STAR 慢慢讲；简历篇幅极短，通常把 STAR 压缩成 1～3 句话，不出现「STAR」字样，也不写小说式前因后果。 [P263]

简历里的推荐压缩方式
STAR 要素 简历里怎么写 劣质写法
S 半句到一句：场景 + 规模（用户/请求量/文档量） 「做了一个系统」
T 嵌入动词：为降低/为提升/为满足 SLA 「负责开发」
A 关键技术名 + 你的动作（设计/实现/推动/排障） 「使用各种技术」
R 数字或前后对比 「效果很好」「显著提升」
[P264]
万能句式（可直接套用）：
在 [场景与规模] 下，为 [目标指标]，采用 [方案 A + 关键技术名]，[你本人主导的动作]，最终实现 [量化结果 / 明确对比]。 [P264]
「一条 bullet 里塞满 STAR」范例 差：负责 RAG 模块，使用了向量数据库。
好：在日均 1 万+ 问答请求的内部知识库场景下，为降低幻觉与尾延迟，采用 混合检索（向量+BM25）+ Cross-Encoder 重排，并落地 Redis 热点缓存 与 批量向量化配置，将 P95 端到端延迟从 800ms 降至 320ms，人工抽检回答准确率从 72% 提升至 86%。 [P264]

多写几条时的节奏：第一条偏「整体职责与结果」，后面几条分别写「编排 / RAG / 记忆 / 工具 / 观测」中的深度点，避免每条同一句式开头。 [P264]

1.2 数字量化的重要性

面试官默认：没有数字 ≈ 没做过、或记不清、或不敢验证。 [P264]

类别 可写内容
性能 QPS、RPS、P95/P99 延迟、首字延迟（TTFT）、单次请求成本
质量 准确率、召回率、F1、MRR、nDCG、用户评分、bad case 占比
规模 文档条数、向量维度、索引分片、日活、会话轮次、工具调用次数
效率与成本 Token 消耗下降%、GPU 占用、人力节省、迭代周期缩短（Agent 岗很吃香）
稳定性 可用性 99.X%、错误率、熔断次数、事故复盘后的改进（偏工程岗必写）

若暂时没有线上指标，可诚实写：「在自建 200 条问答集上，F1 从 0.61 → 0.79」；「压测单机 X req/s 时 P95 Y ms」。避免虚构业务数据。 [P265]

1.3 技术深度 > 广度

广度：一行写「会 Python、会 LangChain、会 Milvus、会 K8s」——读者无法区分你和「看过教程的人」。

对比范例 浅：熟悉 RAG 与 Agent 开发。
深：针对多跳问答中「检索漂移」问题，对比 仅向量检索 与 HyDE + 混合检索，在业务测试集上选择后者，Recall@5 从 0.58 提升至 0.81，并记录失败样本用于周度迭代。 [P265]

简历结构建议：技能清单/技术栈一行体现广度（与 JD 关键词对齐）；项目经历 bullet 体现深度（每个点尽量有「方案 + 结果」）。 [P266]

1.4 避免的常见错误

错误类型 说明 改进方向
泛泛动词 「参与」「协助」「熟悉」无下文 改为「设计并实现」「将 X 从 A 优化到 B」「推动上线」
只堆名词 只写技术栈，不写动作 每个技术栈词后跟「用来解决了什么问题」
抢功 把团队成果全写成「我」 写清「在 X 人团队中负责 Y 子系统」，面试可自洽
无关堆砌 大段传统 CRUD，与 Agent 无关 Agent 岗优先：编排、工具、RAG、评测、成本、延迟、可观测
泄密 写真实客户名、未公开数据 用「某金融客户」「Top3 互联网」；数字用区间或同比
口语与 emoji 「很厉害」「🔥」 全文书面语，专业、克制
过长段落 HR 10 秒扫一份简历 多用短句、分号列表；核心数字加粗（若投递系统支持）
[P266]

2. 技术栈展示

原则：按 「语言/运行时 → Web 框架 → Agent/模型 → 检索与数据 → 消息与任务 → 可观测与部署」 分组，每组一行或一行半；不要把 30 个词无结构地堆成一行。 [P266]

三个「不要」：① 不要写「精通」除非真能经得住深挖；② 不要写已废弃或只复制过 Demo 的版本号；③ JD 里强调的词往前放、写全拼（如对方写 LangGraph，别只写 LC）。 [P267]

2.1 Python 版一句话技术栈

Python · FastAPI · LangGraph · RAG（Milvus + ES 混合检索）· Redis · PostgreSQL · Docker · OTel

分组：语言 Python 3.11+（类型注解/asyncio）｜Web FastAPI、Uvicorn、Pydantic v2｜Agent LangChain、LangGraph（或 AutoGen、自研状态机）｜模型 OpenAI 兼容 API、vLLM/Ollama、提示词与工具 Schema 治理｜检索 Milvus/Qdrant/Weaviate、ES（BM25）、混合检索、bge-reranker｜数据 Redis、PostgreSQL｜消息 Celery、Kafka、RabbitMQ｜可观测 OTel、LangSmith/Langfuse、结构化日志｜部署 Docker、K8s、CI。 [P267]

2.2 Java 版一句话技术栈

Java 17 · Spring Boot 3 · WebFlux/SSE · OpenFeign · Resilience4j · Elasticsearch · Redis · PostgreSQL · K8s

与 Python Agent 服务协作时务必写清边界（避免面试穿帮）：「Java 侧负责会话、鉴权、网关、B 端编排与检索结果合并；Python 侧负责 LangGraph 与重模型推理（如实调整）。」 [P268]

2.3 Go 版一句话技术栈

Go · Gin · gRPC · LLM 网关与流式代理 · Redis · PostgreSQL · OTel · Prometheus · K8s

分组：语言 Go 1.22+｜Web/RPC Gin/Fiber/Echo、gRPC、protobuf｜Agent 相关 高性能 LLM 代理、流式 chunk 转发、工具执行器、连接池与背压｜检索 Redis、PostgreSQL(pgx)、ES 客户端｜可观测 OTel Go、Prometheus、Grafana、zap/slog｜部署 Docker、K8s、健康检查与优雅退出。 [P268]

3. 项目经历模板（三个版本）

每个版本都建议包含：项目名称、项目描述、技术栈、核心职责、技术亮点、项目成果。按需补充：起止时间、你的角色（独立/核心开发/成员）、团队规模、是否已上线。 [P269]

3.1 Python 版（完整可复制模板）

项目定位 项目名称：企业级 AI Agent 智能助手平台
项目描述：基于大模型的企业级智能客服与知识助手系统，支持多轮对话、知识库检索、工具调用与人工兜底；面向内部员工或外部客户，对接企业文档与工单系统，满足合规与审计要求。
技术栈：Python, FastAPI, LangChain, LangGraph, Milvus, Redis, PostgreSQL

核心职责（填你的数字）：

  1. 设计并实现 Agent 多步编排与状态持久化，支持工具失败重试与人工介入节点，日均稳定处理 X 万轮对话。
  2. 搭建 RAG 流水线：文档解析、分块、向量化与增量更新，并实现混合检索 + 重排序，将 Top-5 命中率从 X% 提升至 Y%。
  3. 落地会话级记忆与业务记忆分层策略，结合 Redis TTL 与 PostgreSQL 归档，将长会话上下文成本降低约 Z%。
  4. 与模型网关联调流式输出与限流熔断，将端到端 P95 延迟控制在 X ms 内。

技术亮点：① 用 LangGraph（或自研状态机）显式建模「规划→工具→反思→输出」，配置循环与步数上限避免无限 ReAct；② RAG 侧「向量+关键词」混合检索 + Cross-Encoder 重排，对 PDF 表格与 FAQ 做结构化解析与路由。 [P269]

3.2 Java 版（完整可复制模板）

项目定位 项目名称：企业级智能问答与 Agent 编排服务平台
技术栈：Java 17, Spring Boot 3, Spring WebFlux, OpenFeign, Resilience4j, Elasticsearch, Redis, PostgreSQL, Kafka（可选）

核心职责：

  1. 设计并实现模型网关调用层：流式 SSE、超时重试、熔断与配额，保障大促期间核心链路可用性达 X%。
  2. 封装工具执行与权限校验（角色、数据域），与内部 CRM/工单 API 集成；工具失败时降级为纯 RAG 回答。
  3. 主导检索策略在 Java 侧的编排：查询改写请求发送、结果合并与重排结果融合，将业务相关问题的 Top-3 命中率提升 X%。
  4. 使用 Micrometer + Prometheus 搭建核心指标大盘，缩短平均故障定位时间。

技术亮点：WebFlux + SSE 低延迟流式体验，线程池隔离与背压避免阻塞扩大；Resilience4j 按租户限流与多模型供应商切换，单点故障自动降级备用模型；与向量/Agent 服务通过 gRPC/HTTP 明确契约与 SLA，前后端 Trace ID 贯通。 [P270]

3.3 Go 版（完整可复制模板）

项目定位 项目名称：高并发 LLM 网关与 Agent 执行引擎
技术栈：Go, Gin（或 Fiber）, gRPC, Redis, PostgreSQL, OpenTelemetry, Prometheus, Kubernetes

核心职责：

  1. 实现高性能流式代理：chunk 转发、连接复用、优雅关闭，单机压测支撑 X k QPS（写明环境）。
  2. 设计工具执行沙箱与超时控制，隔离用户输入与下游 HTTP 调用，降低 SSRF 与资源耗尽风险。
  3. 基于 Redis 的令牌桶与滑动窗口限流，按租户与模型维度配额，保障核心客户 SLA。
  4. 全链路 Trace ID 贯通网关、工具与向量检索，可观测数据在 P95 X ms 内完成上报。

技术亮点：连接池与内存分配优化降低 GC 压力与尾延迟；多模型路由策略（成本/延迟/质量优先可配置，失败自动切换）；与 Python Agent 编排服务职责分离（Go 负责 IO 密集与网关）。 [P271]

5. 技能清单写法

目标：让 HR 与面试官在 10 秒内判断「是否匹配 JD」，并给你面试追问入口。 [P275]

  • JD 出现的关键词往前放（岗位写「LangGraph」就显眼写 LangGraph）。
  • 每一行 2～5 个具体词，不要一行 20 个。
  • 少用「熟悉/了解」；若用，必须跟具体事实：「了解 LoRA，曾用 X 数据集跑通过一次微调实验」。
  • 不要单列「ChatGPT」；可写「大模型 API 集成与流式对话」。
  • 证书与语言：外企或海外团队可写 CET/雅思/托福；与岗无关可省略。

7. 针对不同背景的简历建议

7.1 应届生 / 小白

  • 侧重点：学习能力、完整闭环、诚实、可验证（代码/数据集/实验记录）。
  • 项目数量：1～2 个深挖远好于 5 个浅尝；每个项目能讲清「数据从哪来、指标怎么算、失败怎么改」。
  • 深度来源：课设、毕设、开源贡献、天池/Kaggle、个人 GitHub；写明复现了哪篇/哪个仓库，你的增量是什么。
  • 没有线上数据：明确写「自建 N 条评测集」「离线 F1 / Recall@k」「本地/云主机压测」，不要装成大规模生产。
[P278]

7.2 1～3 年经验

  • 侧重点：ownership、线上结果、协作边界、技术权衡。
  • 每条经历写清：你负责的模块、与谁协作（前端/算法/运维）、上线后的指标。
  • 主动写 1 条与事故、评测、成本、延迟相关的内容，区分度明显。
  • 权衡示例：「在延迟敏感场景放弃重型重排模型，改用轻量双塔+规则后处理，P95 达标且 Recall@5 仅降 2 个点，业务接受。」
[P278]

7.3 转行人员

  • 侧重点：可迁移能力、学习路径、项目与目标岗的重叠度。
  • 过去工作翻译：后端 → 稳定性/性能/接口契约；数据 → ETL/质量/评测集；产品运营 → 需求拆解/指标体系。
  • 简历上写清投入：例如「6 个月系统学习 + 2 个完整项目」，减少「只培训过」印象。
[P279]

结语 · 投递前三问自检

  1. 这条经历能否在面试里展开讲满 8～10 分钟？（背景、方案、取舍、数据、复盘）
  2. 简历上的数字是否经得起追问？（口径、采样时间、环境）
  3. 关键词是否与目标 JD 对齐？（可适当同义替换，但不要造假经历）

好简历 = 真实经历 + 清晰结构 + 可验证结果。 [P279]
