Chunking 切分——为什么它最影响召回质量

第三课 · RAG 基础原理系列 | 参考：RAG 技术卡 | 上一课：Embedding

先回答一个直觉问题

上节课你知道了"把文本切成 K 段 → 每段变成一个向量 → 查询时找最像的那段"。那"每段切多大"就变成了一个尖锐的问题：

  • 切太大了（比如一整个章节作为一个 chunk）：向量包含太多信息，语义被稀释——就像一张照片里既有猫又有狗还有车，embedding 找不到"重点在猫"的精确方向。
  • 切太小了（一个句子一个 chunk）：向量方向很明确，但丢失了上下文——"退款将在 3 个工作日内原路返回"这句话如果没有前面的"退货条件"，回答可能不完整。

这就是 chunking 的本质困境：语义精度 vs 上下文完整，不可兼得，只能找平衡点。

  1. 设 chunk=1、overlap=0 → 只召回命中句本身，零噪声零上下文——如果你的问题恰好是"退款几天到"，那回答正确；如果问的是"退货的退款时间"，LLM 没看到前面的"退货条件"。
  2. 设 chunk=4、overlap=0 → 召回了命中句+额外 3 句上下文，但可能带上无关主题句。
  3. 设 chunk=3、overlap=1 → 每次滑动窗口重叠 1 句。同一个句子在多份 chunk 中出现，召回概率增加，但存储量也增加（约 overlap/size × 100%）。

三种主流切分策略

策略 怎么做 适用场景 代价
固定长度（最常用） 每 N 个 token/字符一刀切 通用，作为 baseline 可能切断语义完整的段落
语义切割 按段落/句子边界停，或 NLP 判定"这一段意思说完"再切 文章结构清晰的文档（带标题/分段） 实现更复杂，依赖分句/分割模型
递归切分 先按大块段落切 → 大块超过上限再递归往下切到句子级 多种长度文档混合的场景 速度稍慢（需多粒度切分）

Overlap 重叠：为什么需要？

如果你把一个句子的"前半段"落在 chunk A 末尾、"后半段"落在 chunk B 开头——这两段各自向量化后，谁都不包含完整的含义。查询时可能哪个都召不回。

Overlap 解决这个问题：相邻 chunk 共享一些文本，即使边界切得不巧，至少有一份 chunk 保留了完整语义。

✅ 好处

边界附近的语义不丢失；召回率显著上升（尤其对于问句和关键词跨 chunk 的情况）。

⚠️ 代价

同样的文档存储更多的向量（chunk 数膨胀约 10-20%）；检索稍慢、存储增加。

社区共识：overlap 设为 chunk 长度的 10-20% 是推荐起点 [LlamaIndex docs / Reddit r/LocalLLaMA]。

Chunk 大小不够选、"不测不知道"

这是 RAG 里最反直觉的一点：没有绝对的"最佳 chunk 大小"，它取决于：

  • 你的文档风格：小说（长段上下文依赖）→ 大 chunk；知识库 FAQ（一问一答）→ 小 chunk。
  • 你的常见查询：问"具体数值"→ 小 chunk（精确命中）；问"整体策略"→ 大 chunk（需要综合上下文）。
  • 你的 embedding 模型：模型的最大上下文长度（比如 512 tokens vs 8192 tokens）直接影响 chunk 上限。

实操唯一正确方法：

建 200 条评测集 → 试 chunk_size=256/512/1024 → 跑 Recall@k → 看曲线选最优。RAG 是一个工程实验过程，不是一劳永逸的配置项。下一课的手搭 RAG CLI 里你会亲手验证这一点。
