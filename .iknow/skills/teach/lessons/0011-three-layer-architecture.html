先做一个诊断

在开始之前，请判断下面三个说法对不对：

说法 1：「Agent 的记忆能力来自 LLM 本身——模型越强，记忆越好。」

说法 2：「gbrain 没有接入 LLM，所以它只是一个数据库。」

说法 3：「Harness 和 Agent Loop 是同一个东西。」

核心模型：Agent = Model + Harness

这是整套课程最重要的一个等式。来自 Claude Code 官方文档：

Claude Code is the agentic harness around Claude.
The model reasons; the harness supplies tools, context management, and execution environment.

翻译：Claude Code 是 Claude 模型的智能体外壳（harness）。模型负责推理；harness 提供工具、上下文管理和执行环境。

🍳 厨房类比
把 Agent 想象成一家餐厅：

LLM = 厨师——能读菜谱、能做决策、能判断味道，但自己不能出门买菜、不能记住昨天的客人点了什么。
Harness = 厨房——有灶台（工具执行）、有冰箱（上下文管理）、有服务员（权限和 Hook）、有记事板（会话记录）。
Agent Memory = 今天的订单记录——写在厨房的白板上，下班就擦掉。
External Knowledge Base = 菜谱档案馆——在另一个房间，通过传菜窗口（MCP / Tool 接口）递进来。

三层各自的职责

🔧 Layer 1 · Harness（运行时壳）
有状态的编排层。控制工具执行、权限、上下文注入、会话持久化、子代理。每次 LLM 调用前，Harness 负责把"所有需要的信息"拼成上下文窗口。
iknow 的 Harness：agent-loop/（循环调度）+ tools/registry.ts（工具注册）+ cli/（TTY REPL）+ session-api/hub.ts（HTTP 多会话）
Claude Code 的 Harness：内置 Bash/Read/Write/Edit 工具 + PreToolUse Hook + CLAUDE.md 注入 + JSONL 会话持久化 + MCP server 管理
🧠 Layer 2 · Agent Memory（会话记忆）
单次会话内的上下文管理。包括对话历史、当前轮次状态、跨轮先验（prior chunks）。不持久化——会话结束就消失。
iknow 的 Agent Memory：ConversationState（interaction/conversation.ts）= turns[] + last_priors[] + history_finals[]
Claude Code 的 Agent Memory：对话 transcript（JSONL）+ CLAUDE.md 每次会话重新加载 + auto memory（MEMORY.md 前 200 行）
📚 Layer 3 · External Knowledge Base（外置知识库）
跨会话持久化的结构化知识。通过 Tool 接口（MCP 或函数调用）按需检索，不自动出现在上下文中。
iknow 的 KB：InMemoryKnowledgeStore（纯内存，进程重启消失）+ 4 个 kb_* 工具
gbrain：Postgres + pgvector + TSVECTOR + Anthropic Claude 合成（gateway.ts）+ 17+ embedding provider
你的目标：把 iknow 的 InMemoryKnowledgeStore 升级为 gbrain 级别的持久化

一条完整请求的数据流

当用户问「公司年假制度是什么？」，三层如何协作？

// Step 1: Harness 组装上下文 context = systemPrompt // 系统指令（不变的） + claudeMd // 项目记忆（每次会话加载） + transcript // 对话历史（Agent Memory） + toolSchemas // kb_retrieve 等工具的 JSON Schema + latestUserMessage // "公司年假制度是什么？" → LLM(context) // Step 2: LLM 决定调用工具 LLM → tool_call: kb_retrieve({ query: "年假制度", doc_type: "hr_policy" }) // Step 3: Harness 执行工具（访问 External KB） results = kb_retrieve.execute(...) // 关键词臂 + 向量臂 + RRF 融合 → 5 个 chunks，带 citation 元数据 // Step 4: Harness 把结果注入上下文 context += tool_result(results) → LLM(context) // 第二次调用——这次 LLM "看到"了检索结果 // Step 5: LLM 生成有引用的答案 LLM → "根据公司 HR 政策 [来源:doc-hr-001]，年假为 15 天..." // Step 6: Harness 更新 Agent Memory transcript += [user_msg, tool_call, tool_result, assistant_msg] last_priors = derivePriorsFromAnswer(answer, store) // 提取 5 个 source_spans 供下轮用

来源：iknow 源码 src/agent-loop/llm-agent.ts:152-247（LLM 循环）+ src/interaction/conversation.ts:49-82（先验推导）

关键洞察：外置知识库不在上下文中

Step 2-4 是整个架构的核心。gbrain 的几十万条知识、iknow 的几百个 chunks——它们永远不自动出现在 LLM 的上下文窗口里。只有当 LLM 决定调用 kb_retrieve 工具时，Harness 才执行检索，把结果注入下一轮上下文。

这就是你的调研材料里说的那句话（gbrain-world-memory.html 第 177 行）：

gbrain 里的几十万条事实，永远不在模型的上下文里。
gbrain 与模型之间隔着一条硬边界：MCP 工具面。

这个边界叫工具面（tool surface）。iknow 用的是函数调用（kb_retrieve 等 4 个工具），gbrain 用的是 MCP 协议——但本质一样：外置知识库通过工具接口按需"换页"（page-in）到上下文。

回答你的四个核心问题

Q1：gbrain 的 company brain 是什么？

它不是一个代码模式，是一个部署拓扑。代码里没有任何 isCompanyBrain 开关。

gbrain 本身是个人知识库工具。把它变成"公司脑"需要三步部署：

  1. 换存储：从 PGLite（单机 WASM Postgres）迁移到 Supabase Postgres
  2. 分 source：把数据库分成多个 source（shared / customers / internal），每个 source 用 OAuth 控制谁能读/写
  3. 开 HTTP MCP：暴露 HTTP 端点 + OAuth 2.1，每个同事注册一个 OAuth client

运行时代码完全不变——同一个 gbrain serve --http 二进制。这就是为什么代码里找不到"company brain mode"。

来源：_upstream_gbrain/docs/tutorials/company-brain.md（558 行，完整的部署教程）

Q2：gbrain 没有接入 LLM 吗？

接入了，而且接得很深。gbrain 有一个统一的 AI Gateway（src/core/ai/gateway.ts），支持：

  • Embedding：17+ 个 provider（OpenAI / ZeroEntropy / Voyage / Anthropic / Cohere / DashScope / Zhipu / Groq / DeepSeek / OpenRouter / Together / Ollama / llama.cpp / LiteLLM / MiniMax / Azure / Google）
  • 知识合成：用 Anthropic Claude（默认 Opus 4.7，'deep' 层级）做 gbrain think——从检索结果生成带引用的综合答案
  • Query 扩展：用 OpenAI 做 LLM multi-query（search.mode=tokenmax 时）

所以 gbrain 不只是数据库。它是：Postgres 存储 + 向量检索 + 关键词检索 + 图谱检索 + LLM 合成引擎。

Q3：我是不是需要自己做一个 LLM？

不需要。iknow 已经有 LLM 客户端了：

文件：src/agent-loop/llm-client.ts，类 OpenAiCompatibleLlmClient。它通过 OpenAI 兼容协议调用 LLM（默认连接 http://localhost:20128/v1，模型 deepseek-flash-combo）。

iknow 的 LLM agent loop 在 src/agent-loop/llm-agent.ts 里完整实现了：

  • 构建 system prompt + tool schemas
  • 调用 LLM → 解析 tool_calls
  • 执行工具 → 注入 tool_result
  • 循环直到 LLM 输出最终文本（或达到 max_hops + 8 extra rounds）

来源：src/agent-loop/llm-agent.ts:152-247（循环主体）

你现有调研的评价

你收集的 agent-memory-harness-guide 两份材料质量不错，但存在明显的深度错位：

Agent 记忆分层架构 ⭐⭐⭐⭐ 最强项——四层模型、读写路径、compaction、多代理隔离讲得系统
gbrain 架构级分析 ⭐⭐⭐ 文档级覆盖好，但缺少源码路径、schema、事务和实际工具协议

你的直觉是对的——概念层够用，实现层不够深。特别是标题写着"Harness 底层原理"，实际深度是架构抽象，不是产品内部机制。本节课补的就是这个缺口。

本课的核心收获

三句话记住三层

1. Harness 是有状态的编排层——它拼上下文、执行工具、管权限、持久化会话。LLM 是被它调用的无状态预测器。

2. Agent Memory 是会话内的上下文管理——对话历史、当前状态、跨轮先验。会话结束就消失。

3. External KB 是跨会话的持久化知识库——通过工具接口按需检索，不自动出现在 LLM 上下文里。

面试问答示范

面试官：你的 iknow 项目里，Agent 的记忆是怎么工作的？

你的回答：iknow 的记忆分三层。第一层是 Harness，也就是 agent-loop，负责编排整个执行流程——组装上下文、执行 kb_* 工具、控制 max_hops 预算。第二层是会话记忆，存在 ConversationState 里，包含 turns（对话轮次）、last_priors（上一轮检索命中的 chunks，供下轮 boost）、history_finals（最近 6 条最终消息，给 LLM 看）。第三层是外置知识库 InMemoryKnowledgeStore，通过 kb_retrieve 工具按需检索——关键词臂用 CJK n-gram + IDF，向量臂用 cosine，RRF 融合取 top-5。关键设计是外置知识库不自动出现在 LLM 上下文里，只有 LLM 主动调用 kb_retrieve 时才检索，这避免了上下文污染。
