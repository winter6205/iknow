正常路径全景（happy path）

假设用户问「公司的退款政策是什么？」，没有触发任何边界情况（不是竞对、不是敏感、不需要 compile）。代码走的路径是：

answer(query)→ answerInner()→ ① kb_retrieve→ ② kb_verify_citation→ ③ kb_governance→ ④ envelope() → G2

就这四步。下面逐步看代码。

入口：answer() 方法

answer(query, opts?) — 公开入口

src/agent-loop/loop.ts:60-92
async answer(query: string, opts?: AgentAnswerOpts): Promise<IknowAnswer> {
  const trace = new ToolTrace();       // 记录本次调了哪些 tool
  const notes: string[] = [];          // 收集备注（降级/超时/权限等）
  const hopState = { n: 0 };           // hop 计数器（可变对象）

  try {
    return await this.answerInner(query, trace, notes, hopState, ...);
  } catch (err) {
    // G2 铁律：即使崩了也必须返回带 snapshot_id 的信封
    notes.push(`unexpected_error: ${msg}`);
    return this.finalize({ text: "处理请求时发生意外错误...", ... });
  }
}
TS 注解：
• async answer(...): Promise<IknowAnswer> — 这是一个异步方法，返回一个"未来会拿到 IknowAnswer 的承诺"。调用方用 await agent.answer(q) 等结果。
• opts?: AgentAnswerOpts — ? 表示这个参数可选（可以不传）。
• const hopState = { n: 0 } — 用一个对象包一个数字，是因为 JS 里数字是值传递，对象是引用传递。这样内部函数改 hopState.n 外面能看到。

面试要点：注意 try/catch 里的 finalize()——即使整个 loop 崩了，也必须返回一个带 snapshot_id 的 G2 信封。这是"G2 铁律：never return without snapshot_id"（loop.ts:80 注释）。

Step ①：kb_retrieve（第 1 跳）

第一次检索

src/agent-loop/loop.ts:170-184
// 1) retrieve (hop) — first retrieve merges turn prior_chunks when provided
if (hopState.n >= this.maxHops) {
  return this.hopLimit(trace, hopState.n, notes);  // 预算用完，强制退出
}
hopState.n += 1;                                    // 消耗 1 hop
const firstInput = buildFirstRetrieveInput(q, turnPriors);
trace.record("kb_retrieve", { ...firstInput });     // 记录到 tool_calls 日志
let retrieved = await kbRetrieve(
  this.store, firstInput, this.session, retrieveOpts
);
TS 注解：
• await kbRetrieve(...) — await 意思是"等这个异步操作完成再往下走"。因为 kb_retrieve 可能要调 embedding API（网络请求），所以是 async 的。
• let retrieved — 用 let 不用 const，因为后面可能重新赋值（比如 verify 失败后 re-retrieve）。
• { ...firstInput } — 展开运算符，把 firstInput 对象的字段复制一份传给 trace.record（避免 trace 持有引用后被后续修改污染）。

面试要点：hopState.n >= this.maxHops 是预算检查——如果 5 跳用完了，直接返回"探索步数已达上限"的 G2，不再继续。这防止 agent 无限循环。

Step ②：kb_verify_citation（第 2 跳）

引用校验

src/agent-loop/loop.ts:232-273
let top = retrieved.chunks[0]!;              // 取排名第一的 chunk
const claim = this.deriveClaim(q, top.summary);  // 构造待校验的"声明"

if (hopState.n < this.maxHops) {
  hopState.n += 1;                           // 消耗 1 hop
  const full = this.store.getChunk(top.chunk_id).text;  // 拿原文
  const v = kbVerifyCitation(this.store, {
    claim,
    source_span: { chunk_id: top.chunk_id, quote: full.slice(0, 120) },
  });
  verifyNote = `verify=${v.verdict}`;        // "verify=supported" 之类

  if (v.verdict === "unsupported" && hopState.n < this.maxHops) {
    // 校验不通过 → 用当前 chunk 作 prior 再检索一次（第 3 跳）
    hopState.n += 1;
    retrieved = await kbRetrieve(this.store,
      { query: q, prior_chunks: [{ chunk_id: top.chunk_id, summary: top.summary }] },
      this.session, retrieveOpts
    );
    top = retrieved.chunks[0]!;              // 更新 top
  }
}
TS 注解：
• retrieved.chunks[0]! — 末尾的 ! 是"非空断言"，告诉 TypeScript"我确定这里不是 undefined"。如果真的是 undefined 运行时会崩。
• full.slice(0, 120) — 只取原文前 120 字符作为引用片段（verify 只需要看一小段就够判断覆盖率）。
• v.verdict === "unsupported" — 三态之一。如果是 unsupported，说明 top chunk 的原文撑不起这个声明，需要换一块。

面试要点：verify 失败后不是直接说"不知道"，而是用当前 chunk 作 prior 再检索一次——这就是 prior_chunks 的轮内用途（不是轮间，是同一轮里的"换一块试试"）。

Step ③：kb_governance（不计 hop）

治理快照

src/agent-loop/loop.ts:288-304
const govAction = needsGovernance ? "detect_conflict" : "snapshot_status";
trace.record("kb_governance", { action: govAction, doc_id: primaryDoc });
let g = this.safeGovernance(primaryDoc, govAction);

// 如果 detect_conflict 返回 ok，再补一次 snapshot_status 拿正式水印
if (needsGovernance && g.status === "ok") {
  trace.record("kb_governance", { action: "snapshot_status", doc_id: primaryDoc });
  g = this.safeGovernance(primaryDoc, "snapshot_status");
}
TS 注解：
• needsGovernance ? "detect_conflict" : "snapshot_status" — 三元表达式：如果问题涉及"冲突/对比/最新吗"就用 detect_conflict，否则直接 snapshot_status。
• this.safeGovernance(...) — 包了一层 try/catch 的 governance 调用（loop.ts:494-535），超时/权限拒绝都不会崩，而是降级返回本地 snapshot。

面试要点：governance 不消耗 hop（loop.ts:23 注释："Only kb_retrieve + kb_verify_citation count as hops"）。为什么？因为 governance 是"盖章"动作，不是"探索"动作——它不产生新信息，只是给已有信息打治理标签。

Step ④：envelope() → G2 信封

组装最终答案

src/agent-loop/loop.ts:331-367 + 369-388
// 取前 3 个 chunk 的原文片段作为引用
const spans = retrieved.chunks.slice(0, 3).map((c) => ({
  chunk_id: c.chunk_id,
  quote: this.store.getChunk(c.chunk_id).text.slice(0, 160),
}));

// 拼装人读文本
let text = `根据企业知识库：\n${body}`;
if (g.status === "conflict") text += "\n\n【治理】检测到冲突状态...";
if (g.status === "stale")    text += "\n\n【治理】相关文档可能已过期...";

// 组装 G2 信封
return this.envelope({
  text,
  source_spans: spans,
  snapshot_id: g.snapshot_id,
  governance_status: g.status,
  trace,
  hops: hopState.n,
  notes: notes.length ? notes : undefined,
});
TS 注解：
• .map((c) => ({...})) — 箭头函数返回对象时必须加括号 ({...})，否则 JS 会把 {} 当成代码块。
• notes.length ? notes : undefined — 如果没有备注就不传这个字段（JSON 序列化时 undefined 会被忽略，保持输出干净）。

面试要点：G2 信封的 6 个字段（text / source_spans / snapshot_id / governance_status / tool_calls / hops_used）每个都有存在理由——text 给用户看、source_spans 给审计追问、snapshot_id 给合规追溯、governance_status 告诉用户"这条答案现在还可不可信"、tool_calls 给评测脚本、hops_used 说明探索深度。

面试 Q&A（本课素材）

Q：你的 agent loop 是怎么工作的？
正常路径四步：先 kb_retrieve 双臂检索拿候选 chunk，然后 kb_verify_citation 校验 top chunk 的原文能不能撑起回答（三态），接着 kb_governance 打治理快照（freshness + conflict + snapshot_id），最后组装 G2 信封返回。整个过程有 max_hops=5 的硬预算，只有 retrieve 和 verify 消耗 hop，compile 和 governance 不计。如果 verify 不通过，会用当前 chunk 作 prior 再检索一次——这是轮内的"换一块试试"机制。
Q：为什么 governance 不计 hop？
因为 governance 是"盖章"动作，不是"探索"动作。它不产生新信息（不检索新 chunk、不校验新声明），只是给已有信息打治理标签（freshness / conflict / snapshot_id）。如果把它也算 hop，那每次回答都要额外消耗 1-2 跳预算在"盖章"上，真正的探索空间就被压缩了。
Q：如果整个 loop 崩了怎么办？
answer() 方法有 try/catch 兜底（loop.ts:79-91）。即使 answerInner 里任何一步抛异常，catch 里也会调 finalize() 返回一个带 snapshot_id 的 G2 信封，text 是"处理请求时发生意外错误"。这是 G2 铁律：never return without snapshot_id——企业场景下，即使失败也要有审计水印。
