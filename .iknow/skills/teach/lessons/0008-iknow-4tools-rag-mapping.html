第一步：一句话理解 kb_retrieve

kb_retrieve 做什么：拿用户的查询字符串，去知识库里找最相关的 5 个 chunk（一小段原文片段），按相关度排序返回。

就这一句话。下面我们看代码是怎么实现这句话的。

术语先对齐（这些词你可能听过但不一定真懂，下面遇到会反复出现）：
• chunk = 一小段原文（比如"公司退款政策：3 个工作日内原路退回"就是 1 个 chunk）。
• embedding = 把一段文字变成一串数字（向量），这样计算机能算"两段文字像不像"。
• BM25 = 一种"关键词匹配打分"算法——查询里的词在 chunk 里出现越多、越少见，分越高。
• RRF (Reciprocal Rank Fusion) = 把多路召回（关键词、向量、事实）的排名融合成一个统一排名的公式。
• 向量化召回 / 向量臂 = 用 embedding 算"语义相似度"找 chunk。
• 关键词召回 / 关键词臂 = 用 BM25 算"词重合度"找 chunk。

  • export async function kbRetrieve — export 意思是"这个函数可以被其他文件 import"。async 意思是"异步函数"——可能需要等网络（embedding API）才能返回。
  • (store, input, session, options?) — 4 个参数。逗号分隔。options? 的 ? 表示可选，可以不传。
  • Promise<KbRetrieveOutput> — 返回类型。意思是"返回一个未来会拿到 KbRetrieveOutput 的承诺"。调用方用 await kbRetrieve(...) 等结果。
  • if (!input.query || input.query.trim().length === 0) — ! 是逻辑非（不是），|| 是"或者"。所以这是"如果 query 不存在 或者 query 是空白字符串"。.trim() 去掉首尾空格。
  • throw new ValidationError(...) — 抛异常，函数立即停止。调用方需要 try/catch 接住。
TS 语法小结：
• async / await / Promise<X> = 异步三件套。第一次见没关系——记住"async 函数返回 Promise，await 等 Promise 完事"。
• ? 在参数后面 = 可选。
• <X> = 泛型。这里 Promise<KbRetrieveOutput> 表示"这个 Promise 最终会给出 KbRetrieveOutput 类型的东西"。
• throw new XxxError(...) = 抛异常。

一句话总结：kb_retrieve 接收一个查询，先检查查询非空，然后去知识库找相关 chunk，最后返回排序好的 chunk 列表。

逐行讲：

  • new Map<string, number>() — 创建一个 Map（键值对集合）。键是字符串（chunk_id），值是数字（boost 权重）。
  • for (const p of input.prior_chunks ?? []) — 遍历 prior_chunks 数组。?? 是"空值合并运算符"——如果左边是 null 或 undefined，就用右边（空数组 []）。
  • priorBoost.set(p.chunk_id, 0.15) — 把每个 prior chunk 设为 0.15 的 boost（"加分"）。
  • ?: 是三元运算符。"如果 prior_chunks 存在且非空，就把 query 和所有 prior summary 拼起来；否则就用原 query"。
  • input.prior_chunks.map((p) => p.summary).join(" ") — 把 prior 数组里每个元素的 summary 字段拿出来，用空格连成一个字符串。
什么是 prior_chunks？假设用户先问"退款政策"，然后接着问"那运费险呢"——第二条查询如果只用"运费险"，可能搜不到。prior_chunks 就是把上一轮找到的相关 chunk 的摘要带过来，让第二条查询能"参考"上一轮的结果。expandedQuery 就是"拼上 prior 后的扩展查询"。

一句话总结：把上一轮的相关 chunk 摘要拼到当前查询里，让多轮对话能"记住"上下文。

逐行讲：

  • 144 行：body = chunk.summary + chunk.text——把 chunk 的摘要和正文拼起来，等会用来打分。
  • 145 行：kw = scoreKeyword(expandedQuery, body, idf)——用 BM25 算法算"关键词臂"的分数。idf 是"逆文档频率"，意思是一个词越少见，权重越高（"退款"比"公司"更稀有，所以"退款"命中得分更高）。
  • 146 行：ov = scoreOverlap(expandedQuery, body, idf)——算"重叠臂"的分数（词重合度）。这是 当没有真 embedding API 时的 fallback——所以 retrieve.ts 在没有 vector index 时也能跑。
  • 155-168 行：如果 index 是 "fact" 或 "both"，再算一个 factBoost（用 fact 文本和 fact_keywords 来打分）。但 factBoost 只用于排序分数，164 行注释明确说"never expose fact text in output"——事实文本永远不进 G2 信封，避免 LLM 直接抄 fact 文本产生幻觉。
  • 170 行：prior = priorBoost.get(chunk.chunk_id) ?? 0——查这个 chunk 是不是上一轮相关，是的话加 0.15 的 boost。?? 0 是"如果没有就当作 0"。
  • 172-174 行：过滤门槛。如果这个 chunk 在所有臂上的分数都低于最低线（关键词 2.5 + fact boost、或者 prior boost、或者 overlap 0.12），就 continue 跳过它——不进入候选名单。这步防止低质量 chunk 污染最终排名。
  • 176-181 行：把通过门槛的 chunk 放进 candidates 数组，存三个分数：keyword（关键词臂分数 + prior 加成）、overlap（重叠臂分数 + prior 加成）、factBoost（事实臂分数）。
关键设计点（面试常问）：
1. 为什么用 BM25 + overlap 两条臂？——关键词臂抓"精确词"（订单号、产品名），重叠臂是 embedding 的简化版（没有 embedding API 时也能跑）。
2. 为什么 fact 文本不进 G2？——LLM 直接抄 fact 文本会"看上去对"但实际是 hallucination。只让 fact 影响排序、不让 fact 文本进最终答案，强制 LLM 必须引用 chunk 原文。
3. 为什么有 MIN_KEYWORD 门槛？——防止所有 chunk 都返回（噪声召回），保证返回的 chunk 至少有一个臂有信号。

一句话总结：遍历每个 chunk，算三路分数（关键词/重叠/事实），过门槛后存进 candidates 数组。

第六步：RRF 融合（真正的魔法在这）

src/kb-retrieve/rrf.ts（整个文件 37 行，能全贴）

真实源码（完整）
1/** Standalone Reciprocal Rank Fusion (k=60). No external package imports. */
2export const RRF_K = 60;
3
4export interface RankedHit {
5  id: string;
6  score: number;
7}
8
9/**
10 * Reciprocal Rank Fusion: score += 1 / (k + rank), ranks are 0-based.
11 * Then normalize to max=1 and sort descending.
12 */
13export function rrfFusion(
14  lists: RankedHit[][],
15  k: number = RRF_K,
16): RankedHit[] {
17  const scores = new Map<string, number>();
18
19  for (const list of lists) {
20    for (let rank = 0; rank < list.length; rank++) {
21      const hit = list[rank];
22      if (!hit) continue;
23      const add = 1 / (k + rank);
24      scores.set(hit.id, (scores.get(hit.id) ?? 0) + add);
25    }
26  }
27
28  if (scores.size === 0) return [];
29
30  const max = Math.max(...scores.values());
31  const fused: RankedHit[] = [];
32  for (const [id, raw] of scores) {
33    fused.push({ id, score: max > 0 ? raw / max : 0 });
34  }
35 fused.sort((a, b) => b.score - a.score);
36  return fused;
37}

逐行讲：

  • 17 行：scores 是 Map，键是 chunk_id，值是累积的 RRF 分数。
  • 19-26 行：核心循环——遍历每一路列表，对每个候选加 1 / (60 + rank)。
    rank=0（第一名）得 1/60 ≈ 0.0167
    rank=1（第二名）得 1/61 ≈ 0.0164
    rank=49（第五十名）得 1/109 ≈ 0.0092
    越靠前加分越多，所以"在多路都靠前"的候选自然胜出。
  • 23 行：scores.set(hit.id, (scores.get(hit.id) ?? 0) + add)——如果这个 id 之前出现过，就累加；否则从 0 开始。?? 0 是"如果没找到就用 0"。
  • 30 行：找出最大分数（用于归一化）。
  • 33 行：所有分数除以 max，归一化到 [0, 1]。这样返回的 score 是个百分比，不会太大。
  • 35 行：按融合后的分数降序排。
RRF 为什么这样设计？
简单。不用学、不用调参（k=60 是论文默认值）。核心思想：一个候选在多路都靠前 = 真的好。如果你只在关键词臂第一但在向量臂第 50 名，RRF 分数是 0.0167 + 0.0092 = 0.0259；如果你在两路都第一，RRF 分数是 0.0167 + 0.0167 = 0.0334——后者胜出。

一句话总结：RRF 把多路排名融成一个分数，公式就一行：score += 1 / (60 + rank)。

面试 Q&A（用这节课的素材）

Q：你的 RAG 检索怎么实现的？
我的 kb_retrieve 走三路召回 + RRF 融合：关键词臂（BM25 打分）、向量臂（有真 embedding API 时用余弦相似度，否则 fallback 到 overlap）、事实臂（只用于排序，事实文本不进 G2）。三路各取前 50 候选，RRF 公式融合（1 / (60 + rank)），最终返回 top 5。如果 embedding API 网络挂了，只接 NetworkError，降级到 overlap 臂继续跑；其他错误继续抛不让 bug 静默。
Q：为什么 fact 文本不进 G2 信封？
因为 LLM 直接抄 fact 文本会"看上去对"但其实是 hallucination。我让 fact 只影响排序分数（用 scoreKeyword/scoreOverlap 算），但不让 fact 文本出现在最终答案里。这样强制 LLM 必须引用 chunk 原文，引用溯源才是真实的。
Q：BM25 和 embedding 召回的区别是什么？
BM25 是关键词打分——"查询里的词在 chunk 里出现越多、越少见，分越高"。embedding 是语义相似度——把文字变向量算余弦相似度，能抓到"语义近但词不同"（如"退款"和"退货"）。我两条都跑是因为任何一条单独召回都不够：BM25 抓不到同义词，embedding 抓不到精确生僻词（订单号）。三路融合补齐。
