你的目标反解

你说的"企业知识库 + 向量检索增强 + LLM 对话辅助"，在业内叫 RAG 系统（Retrieval-Augmented Generation）。它不是一个大块，而是五个管线阶段串成一条链：

① 文档处理 & 切分→ 原始文档 → 清理 → 切 chunk（固定窗口 / 语义边界 / 层级）
② Embedding & 索引→ 每段 chunk 向量化 → 写入向量库（Milvus / Qdrant / pgvector）+ 元数据索引
③ 检索 & 重排→ Query 向量化 → 向量 + BM25 多路召回 → RRF 融合 → Cross-Encoder 重排
④ 生成 & 引用→ 拼 prompt + 检索结果 → LLM 生成答案 → 附来源引用
⑤ 评测 & 迭代→ 建离线评测集 → 量化 Recall@k / 准确率 → 切分 / 模型 / 策略调优

来源：参考卡片 05-RAG 技术 [原文 P54-85]

你要学的 = 五个阶段 × 两个深度

每个阶段都有两层知识：概念层（说得清是什么、为什么）和 工程层（能动手搭、能调优）。你当前在 Dify/Coze 中的经验是"概念层通、工程层缺"。

文档处理
chunk 长度怎么定？语义切分 vs 固定窗口？重叠窗口要不要？
Embedding
选哪个模型？bge-m3 / text-embedding-3 / m3e？维度对性能影响？
检索
纯向量够不够？BM25 补什么？RRF 怎么融合分数？
重排
Cross-Encoder 比双塔好多少？放哪一步？延迟/成本权衡？
生成
prompt 模板怎么防幻觉？上下文窗口不够？引用如何溯源到原文？
评测
Recall@k / MRR / Faithfulness 怎么算？200 条评测集足以发现 regression？

先学什么？四步路线

  1. 手搭一个最简 RAG CLI（~100 行）—— 跳过框架，直接体验 ⑤ 步管线，理解每个环节存在的原因。
  2. 加上混合检索 + 重排 —— 对比纯向量 vs 多路召回，观察指标变化。
  3. 建评测集 + 量化循环 —— 没有评测的 RAG 是盲人摸象。写一个 recall@k 脚本，调 chunk 长度看看曲线。
  4. 选一个向量库上 Docker —— Milvus（推荐）或 Qdrant，把本地脚本包装成可部署服务。
重要提醒：Dify/Coze 替你封装了上面每一步。你要做的是"揭开封装"——手写一遍 ⑤ 步管线，不是为了造轮子，而是为了在面试中被问到"为什么选这个 chunk 长度""重排放在哪""召回率多少"时，能讲出你的实验数据和取舍理由。

学完后你该能回答这三个问题

1. 拆成 ⑤ 个阶段后，你认为哪一步最难？（没有标准答案，重要的是你能说出"为什么"）
2. 为什么纯向量检索不够，需要 BM25 混合？
3. 如果用户说"答案不对"，你怎么定位是检索问题还是生成问题？
