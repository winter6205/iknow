第一招：找「枢纽节点」，别从第一个文件开始读

方法 1

陌生代码库第一步：找那个「把所有东西收集到一起」的文件

一个成熟项目里，几乎总有一个文件扮演着「总目录」的角色——它把散落各处的功能收集成一个列表。找到它，你就拿到了整个系统的骨架。读 100 个散文件，不如先读这 1 个总目录。

怎么找？问自己一个问题：「如果这个程序要把所有工具打印出来给 LLM 看，它会遍历哪个数组？」 然后去找那个「打印」命令。

我就是这么找到 gbrain 的枢纽的。gbrain 有个命令叫 gbrain --tools-json（把所有工具打印成 JSON）。它的实现在这里：

_upstream_gbrain/src/commands/tools-json.ts:3-16

真实源码（完整，就 14 行）
3export function printToolsJson() {
4  const tools = operations.map(op => ({
5    name: op.name,
6    description: op.description,
7    parameters: Object.fromEntries(
8      Object.entries(op.params).map(([k, v]) => [
9        k,
10        `${v.type}${v.required ? '' : '?'}`,
11      ]),
12    ),
13  }));
14
15  console.log(JSON.stringify(tools, null, 2));
16}

逐行讲：

  • 3 行：export function printToolsJson() — export 表示这个函数能被别的文件 import。() 里没有参数，说明它不需要任何输入。
  • 4 行：operations.map(op => ({...})) — 这一行就是线索。operations 是一个数组，.map() 把数组里每个元素（这里叫 op，是 operation 的缩写）变成一个新对象。所以「所有工具」就存在 operations 这个数组里。
  • 5-6 行：每个工具取它的 name（名字）和 description（描述）。
  • 7-12 行：把工具的参数（op.params）整理成「参数名 → 类型」的形式。v.required ? '' : '?' 是三元表达式：如果参数是必填的就什么都不加，否则加个 ? 表示可选。
  • 15 行：console.log(JSON.stringify(...)) — 把结果打印成格式化的 JSON。
TS 语法：箭头函数返回对象要加括号
op => ({...}) 里那个 ({...}) 外面的括号不能省。因为箭头函数里 {} 会被当成「函数体」，要返回一个对象字面量必须用 () 包起来，写成 => ({...})。这是新手最容易踩的坑。

顺藤摸瓜：这个文件顶部一定有一句 import { operations } from ...。跟着这个 import 跳过去，就到了真正的枢纽——

_upstream_gbrain/src/core/operations.ts:5316（枢纽本体）

真实源码（节选开头 + 结尾，中间省略）
5316export const operations: Operation[] = [
5317  // Page CRUD
5318  get_page, put_page, delete_page, list_pages,
5319  // ... (中间还有约 90 个工具，按功能分组，每组有注释) ...
5395  run_onboard,
5400  run_skillopt,

逐行讲：

  • 5316 行：export const operations: Operation[] = [ — 定义一个常量数组。Operation[] 是 TS 类型标注，意思是「一个由 Operation 类型组成的数组」。整个 gbrain 的全部工具，就是这个数组里的每一项。
  • 5317-5318 行：注释 // Page CRUD 说明这一组是「页面的增删改查」，后面跟着 4 个工具的名字。CRUD = Create（创建）/ Read（读）/ Update（更新）/ Delete（删除），是后端最常用的缩写。
  • 5395、5400 行：数组的最后几个工具。

一句话总结：gbrain 的全部 102 个工具，都登记在 operations.ts:5316 这一个数组里。这就是你要找的「gbrain 本来有哪些工具」的权威答案。

第二招：搞清「一个工具长什么样」

方法 2

找到枢纽后，挑一个最简单的工具，搞清它的「形状」

知道了工具都存在哪，下一步是弄懂一个工具由什么构成。挑数组里最简单的那个，读懂它的结构，其余 101 个都是同一个模子。

gbrain 里一个工具，就是一个符合 Operation 接口的对象。接口定义在这里：

_upstream_gbrain/src/core/operations.ts:589-619

真实源码（工具的形状定义）
589export interface Operation {
590  name: string;
591  description: string;
592  params: Record<string, ParamDef>;
593  handler: (ctx: OperationContext, params: Record<string, unknown>) => Promise<unknown>;
594  mutating?: boolean;
605  scope?: 'read' | 'write' | 'admin' | 'sources_admin' | 'users_admin';
606  localOnly?: boolean;
607  cliHints?: { ... };
619}

逐行讲（只看前 4 个核心字段）：

  • 590 行 name：工具的名字（LLM 调用时用的那个字符串）。
  • 591 行 description：工具的描述——这是给 LLM 看的，LLM 靠它决定什么时候调这个工具。
  • 592 行 params：这个工具接受哪些参数。Record<string, ParamDef> 是 TS 类型，意思是「一个键是字符串、值是 ParamDef 的字典」。
  • 593 行 handler：真正干活的函数。(ctx, params) => Promise<unknown> 表示它接收上下文和参数，返回一个异步结果。
TS 语法：interface 和 ?
• interface Operation { ... } = 定义一种「对象的形状规范」。任何对象只要符合这些字段，就是一个 Operation。
• 字段名后面的 ?（如 mutating?、scope?）= 可选字段，可以不写。name / description / params / handler 没有 ?，所以是必填的。
一个工具 = 「菜单」+「厨房」（这个比喻记住，下面反复用）：
• 菜单（给 LLM 看）：name + description + params —— 告诉 LLM「你能点什么菜、要告诉厨房什么口味」。
• 厨房（真正做菜）：handler —— 收到点单后真正执行的代码。
LLM 只看菜单，不看厨房。它照着菜单点单，厨房（handler）负责把菜做出来。

看一个真实工具长什么样（gbrain 最简单的工具之一 get_page，读取一个页面）：

真实源码（节选，handler 部分省略）
623const get_page: Operation = {
624  name: 'get_page',
625  description: 'Read a page by slug (supports optional fuzzy matching)...',
626  params: {
627    slug: { type: 'string', required: true, description: 'Page slug' },
628    fuzzy: { type: 'boolean', description: 'Enable fuzzy slug resolution...' },

逐行讲：

  • 623 行：const get_page: Operation = { — 定义一个常量，类型是 Operation。注意：菜单（name/description/params）和厨房（handler）写在同一个对象里。
  • 627 行：slug: { type: 'string', required: true } — 这个工具必填一个参数 slug（页面的地址），类型是字符串。required: true 表示必填。
  • 628 行：fuzzy 没有 required，所以是可选参数。

一句话总结：gbrain 的一个工具 = 一个对象，里面同时装着「菜单」（name/description/params）和「厨房」（handler）。

第三招：顺藤摸瓜——「LLM 真的能看到全部 102 个吗？」

方法 3

别停在枢纽，继续追问：这个列表「最终被谁消费」

找到总目录还不够。要追问：这个列表最终喂给了谁？喂的过程中有没有被筛选？ 顺着调用链往下走一层，常常会发现「定义了 100 个，但真正暴露给 LLM 的只有一部分」。

gbrain 的 102 个工具，并不是全部都给 LLM 看。gbrain 的 LLM 子代理（subagent）只能看到其中白名单里的 14 个。这个白名单在这里：

为什么这招重要：如果只停在第一招，你会以为「gbrain 给 LLM 102 个工具」。但顺藤摸瓜到第三招才发现：定义 102 个 ≠ 暴露 102 个。gbrain 用白名单把 LLM 能用的收窄到 14 个——这恰恰和你 iknow 的做法是同一个思想（下一节讲）。

一句话总结：gbrain 定义了 102 个工具，但 LLM 子代理实际只能调用白名单里的 14 个。「定义」和「暴露」是两回事。

  • 1 个是原创（kb_verify_citation）：上游根本没有，是你新造的。

还有一个思想是共通的（面试加分点）：gbrain 用 brain-allowlist 把 102 个工具收窄到 14 个给 LLM；你 iknow 干脆只造 4 个。两者背后是同一个工程原则：不要给 LLM 太多工具——工具越多，LLM 越容易选错、越难推理。gbrain 的 OperationContext.remote（区分可信本地调用 vs 不可信 agent 调用）和你 iknow 的 caller_role 注入（鉴权进 host、不进 tool 入参）也是同一个「信任边界」思想。

面试 Q&A（用这节课的素材）

Q：你的项目和上游 gbrain 是什么关系？
iknow fork 自 gbrain，但不是照搬——是一次有意识的收窄。gbrain 是通用知识大脑，有 102 个工具（页面、图谱、任务队列、代码智能都做）。我只取「可溯源的企业知识库问答」这一条窄缝，重写成 4 个高度特化的工具：kb_retrieve（检索，收窄自上游 query）、kb_compile（编译事实，收窄自 extract_facts）、kb_governance（治理，收敛上游散落能力）、kb_verify_citation（引用核验，上游完全没有，是我原创的）。
Q：为什么只给 LLM 4 个工具，而不是像上游那样多？
工具越多，LLM 越容易选错、推理负担越重。上游 gbrain 其实也懂这个道理——它定义了 102 个工具，但用白名单（brain-allowlist）把 LLM 子代理能用的收窄到 14 个。我走得更彻底：这个场景只需要「检索→核验→编译→治理」四个动作，所以只造 4 个，每个职责单一。这也让 max_hops=5 的预算控制更干净——只有检索和核验消耗 hop。
Q：你怎么快速读懂一个陌生的大型代码库？
三步。第一，找「枢纽节点」——那个把所有功能收集成列表的文件，比如 gbrain 的 operations.ts 一个数组登记了全部 102 个工具；读它比读 100 个散文件高效。第二，挑最小的单元搞清「形状」——读懂一个工具由 name/description/params/handler 构成，其余都是同模子。第三，顺藤摸瓜追问「这个列表最终被谁消费、有没有被筛选」——这样才发现 gbrain 定义 102 个但只暴露 14 个给 LLM。另外我坚持代码是 ground truth：gbrain 文档说 ~90 个工具，实际数出来是 102，文档会滞后。

2. gbrain 定义了多少工具，LLM 子代理实际能用多少？

3. 你的 4 个工具里，哪个是上游完全没有、纯原创的？

1. 对任何陌生代码库说出三步读法（找枢纽 / 搞清形状 / 顺藤摸瓜），并知道 gbrain 的枢纽是 operations.ts:5316。
2. 说出 gbrain 有 102 个工具、LLM 实际见 14 个，以及「定义 ≠ 暴露」。
3. 讲清你的 4 个工具对应上游哪几个（2 收窄 / 1 收敛 / 1 原创），并纠正「重启工具」的误解——你做的是有意识的收窄+补强。
