# Spec: Canonical host-read policy for read-capable ACI tools

**Status:** draft
**Basis:** ADR-0128 (`docs/adr/0128-host-read-capability-across-tools.md`) + wayfinder ticket `docs/wayfinder/tickets/hsr-1-fs-read-capability.md` (closed, operator-confirmed) + ADR-0092 (`docs/adr/0092-fs-isolation-modes.md`). Planning artifact; no code lands from this file alone.

## Approach

**One cohesive capability, one PR, a coordinated commit series.** This spec touches several files, but it is a single logical change: _one_ read policy applied consistently across every read-capable tool. Splitting it would ship a widened read surface on some tools while another tool still enforces the old, narrower (and differently-denying) rule — the exact inconsistency the spec exists to remove, and the same class of intermediate state SC5 forbids. The multi-file shape is therefore answered by **commit ordering inside a single PR**, not by splitting the spec: the policy module plus its enforcement across _all_ read-capable tools lands in the earliest commit(s), and no commit widens any tool's host reach until the protection is already live and green (SC5). Review of the series, not the branch count, is what verifies this.

## Objective

Make ordinary host-path reads behave the same through `read_file`, `grep`, and `glob` in **both** filesystem modes (`global` / `workspace`), behind **one** canonical read policy, without weakening the credential / sensitive-path protection shell reads already have.

Today the three tools carry three separate task-root allowlists — `read-file.ts` resolves through `resolveWithinRoot` with `extraReadRoots` (`src/harness/aci/tools/read-file.ts:140-153`, `:320-353`), while `grep.ts` (`src/harness/aci/tools/grep.ts:111-113` `readRoot` → `:355` `resolveSearchRoot`) and `glob.ts` (`src/harness/aci/tools/glob.ts:88-90` `readRoot` → `:213` `resolveSearchRoot`) each re-derive a smaller reach. ADR-0092 already declares both modes to be **broadly readable host views** — workspace mode "primarily tightens writes" (`docs/adr/0092-fs-isolation-modes.md:11`, `:24`) — so the tools' narrower read surface is an inconsistency, not a designed boundary. ADR-0128 confirms the operator picked the broad-read reading and explicitly rejected implementing it by granting `/` as an unguarded read root.

Who benefits: the model (one reachability rule to learn, identical answers in both modes) and the operator (one protected-path roster to audit in the read policy, held to at least the strength of the shell wall's roster by a test, so file reads can never end up more permissive than shell reads).

Success looks like: a file at any ordinary host path is reachable through all three tools in both modes; a protected credential path is **refused** through all three tools (typed tool error) and through the symbol tools' direct file opening (readable sentinel string, same family as `renderNoServer`), with **no** symlink alias able to reach what its target could not, and no undecidable path able to slip through as an allow; and the protected-path policy is in place and enforced **before** any tool's host reach is widened, so no intermediate state exists where reach grew and protection had not.

## Boundaries

- **Does:**
  - **One shared read-policy module and contract.** A single module owns (a) _which_ paths a read-capable tool may reach, given the mode and the identity roots, and (b) _which_ reached paths are protected. It is a value/pure-function surface (no tool-local state), so `read_file` / `grep` / `glob` / symbol tools all call the same code and cannot drift. The three per-tool `readRoot` + `resolveSearchRoot` allowlists and `read-file.ts`'s `computeExtraReadRoots` become **one** derivation the tools consume — not three parallel implementations of a widened rule.
  - **The protected-path inventory, enumerated and owned here.** One frozen list — credentials / key material / sensitive dotfiles / system-account files — matching or exceeding what shell reads are protected by today (`SENSITIVE_PATH_FRAGMENTS`, `src/harness/permission/hard-walls.ts:135-158`, read by both `commandContainsSensitivePath` at `:3047` and the `hard-wall:sensitive-path` spec at `:3336-3343`). The inventory names its **match shape** per entry: path-glob (`.ssh/`, `.aws/`, `.gnupg/`, `.config/gh/`, `.kube/`, `.docker/config.json`), extension-glob (`*.pem`, `*.key`, `*.p12`), exact-basename (`id_rsa`, `id_ed25519`, `.netrc`), dotfile-glob (`.env`, `.env.*`), and absolute-prefix (`/etc/passwd`, `/etc/shadow`, `/proc/self/environ`).
    - **Ownership is this spec's, exclusively.** The roster is a **new constant declared by the shared read-policy module itself**. It is _not_ a byte-for-byte reuse of `SENSITIVE_PATH_FRAGMENTS`, _not_ an edit to `src/harness/permission/hard-walls.ts`, and _not_ a change that requires coordination with, review by, or sequencing against `specs/hard-wall-ast-migration.md` — that spec's Out-of-this-spec bullet states `SENSITIVE_PATH_FRAGMENTS` "is not edited (no fragment added, removed, or re-anchored)", so it neither needs nor accepts a roster change from here. Landing this roster is a plain, self-contained addition in this spec's own module.
    - **Two separate frozen lists, with a no-weaker pin.** The shell command wall's `SENSITIVE_PATH_FRAGMENTS` and the read policy's roster are **two distinct frozen lists with two distinct edit authorities**; this spec touches only the second, and the shell wall keeps consuming its own text roster byte-unchanged. They are coupled by exactly one test-level invariant (SC9): for every path both lists cover, the read policy's roster denies **at least everything** `SENSITIVE_PATH_FRAGMENTS` denies, so widening host reach through the read tools can never produce a path that is denied to shell reads but allowed to file reads. Convergence of the two lists into one is a later, separate concern and is not this spec's deliverable.
  - **Route the three read tools' host reads through the policy.** `read_file` (direct file open), `grep` (its `path` search root, on **both** engines — the pinned ripgrep spawn and the Node degrade walk, `grep.ts:268-284`), and `glob` (its `path` search root, on both the rg path and the Node walker). Reach widens to ordinary host paths in **both** modes; the policy — not a mode flag — is what still refuses protected paths.
  - **Route the symbol tools' direct file opening through the policy.** Symbol search stays project-indexed; the **file opening** the language server performs (`symbol.ts:170-193` `withResolvedSymbol` → `client.withDocumentOpen`, `src/harness/lsp/client.ts:97`, which reads on-disk text for `didOpen` / `didChange`) is a real read of file contents and must consult the same policy. The `didOpen` path is where the bytes enter the server; a later query result is downstream of it.
  - **Apply the policy before content enters a tool result.** Every deny decision is made on the **canonicalized** path before the file is read, before any bytes are buffered, and before grep/glob emit any line or path. Tool-local output masking is explicitly **not** a read-authorization boundary (ADR-0128 consequence 1) — masking may additionally reduce what a partially-permitted read exposes, but it never substitutes for the decision.
  - **Symlink handling.** The policy judges the **realpath** of the target, and the pre-resolution path where the link itself is what a tool would open. A symlink whose target is protected is denied even when the link's own name is ordinary, and vice versa: an ordinary file reached through an ordinary symlink chain is allowed. A symlink pointing **into** a protected directory is denied by the same inventory entry that protects the directory.
  - **Mode-specific user-visible errors** that describe the actual rule (ticket acceptance point): a refusal says which rule fired (protected path vs outside the reachable host view) and does not claim a filesystem-mode restriction that is not the one in force.
  - **One explicit error direction, on two typed channels.** The policy answers a protected path with **refusal**, never with masking, and the refusal is delivered on whichever channel the tool already owns (see "Error surface" below): `read_file` / `grep` / `glob` raise a **typed tool error** naming the protected-path rule; the symbol family, whose signature is `T | string` and which has no error channel, returns a **readable sentinel string** in the same family as `renderNoServer` (`src/harness/aci/tools/lsp.ts:196`). Both are refusals; only the carrier differs. No third direction (silent pass, partial content, mask-instead-of-refuse) is available to an implementer.
  - **Error surface (the two channels, reconciled).**

    | Tool family                                                           | Return/throw contract                     | Protected-path answer                                                                                                                                                                                                                                                                  |
    | --------------------------------------------------------------------- | ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | `read_file`, `grep`, `glob`                                           | throw `ToolExecutionError`                | typed tool error whose message names the **protected-path** rule (not a mode restriction, not a path-absence error)                                                                                                                                                                    |
    | `find_symbol`, `get_symbols_overview`, call-hierarchy, `lsp_*` family | `Promise<T \| string>` — no error channel | readable sentinel string, same family and rendering path as `renderNoServer`, naming the **protected-path** rule; **not** a thrown error, and **not** a reuse of the existing `no-server` / no-project-anchor meanings (a protected-path denial is a distinct, distinguishable string) |

    The symbol sentinel is produced **before** `client.withDocumentOpen` is called, so no `didOpen` ever carries protected bytes. SC2 and SC4 name the same decision on these two carriers; they do not contradict.

  - **EXIT / failure direction: fail-closed.** Every path that cannot be _decided_ is a **deny**, never an allow and never a silent pass. Concretely:
    - **Canonicalization failure is deny.** If `realpath` on a candidate throws — `ENOENT` / `ELOOP` from a dangling symlink, `EACCES` / `EPERM` on a path component, `ENAMETOOLONG` / overflow on an over-long path — the read policy **denies** with a message that names the _resolution_ failure (distinguishable from a protected-path denial and from "outside the reachable host view"), because a path whose canonical form is unknown cannot be shown to be safe. This includes empty-string and whitespace-only input: they canonicalize to nothing and are denied, not passed through to a tool that would then throw an untyped error.
    - **No permissive default on error.** A thrown error anywhere in decision-making is caught at the policy boundary and converted to the typed deny (or sentinel string, per channel); an exception can never propagate as an _allow_ or as an untyped crash out of a tool handler.
    - This is the security boundary's open-vs-closed answer: **closed**. The only outcomes are `allow` (a canonicalized, non-protected, in-reach path) and `deny` (protected, out-of-reach, undecidable, or failed-to-resolve).
  - **Tests**, per read-capable tool, for: ordinary external file; protected path; symlink alias of a protected path; and both `global` and `workspace` modes.
- **Confirms with human:** none remaining. The roster shape is an operator decision ((b), a path-shaped roster owned by this spec's own shared read-policy module) recorded in Open Questions; the inventory contents and per-entry match shapes are enumerated in the boundary list above and land as a new constant in the shared module. Everything else is settled by ADR-0128 / the closed ticket and is **not** re-opened here.
- **Out of this spec:**
  - **Write roots.** `write_file` / `edit_file` keep their current containment (live `taskRoot` ∪ session tmp, ADR-0092 Round-2). This spec adds no writable path and removes none.
  - **A project-only read mode.** A third fs mode restricting reads to the project is a separate decision (ADR-0128; ticket), not a variant of this one.
  - **The unified shell parser / the ADR-0123-0125-0127 migration series, and the shell wall's roster.** `specs/hard-wall-ast-migration.md` owns `commandContainsSensitivePath`'s parse-based rewrite; it explicitly disclaims editing the sensitive-path roster (`SENSITIVE_PATH_FRAGMENTS` "is not edited"). This spec **consumes** the shell wall as the protection floor and does not re-specify the parser or the parse verdicts — and it does **not** route its roster anywhere: the read policy's protected-path roster is a **new constant owned by this spec's shared read-policy module** (see "Ownership is this spec's, exclusively" above). This spec neither edits nor claims edit authority over `SENSITIVE_PATH_FRAGMENTS`, and requires no coordination, sequencing, or PR-level coupling with `hard-wall-ast-migration.md`; the only coupling is the no-weaker test pin (SC9), which reads the shell roster and asserts on it without changing it.
  - Bash's own read posture, the bwrap mount stack, `--ro-bind` shapes, and ADR-0129 effect boundaries beyond shell intent.
  - The last-read ledger, the grep scope gate, glob's `limit` / `pattern` semantics, read_file's paging / size / binary-reject contract — all unchanged.
  - Egress, network tools, MCP resource reads, `read_image`.

## Success Criteria

Every criterion is binary and maps to a named test surface. The product path is `npm test` (vitest: unit + harness + integration). Read-tool coverage lands in `tests/harness/aci/tools/` (a new `host-read-policy.test.ts` for the shared module, plus additions to `read-file.test.ts`, `grep.test.ts`, `glob.test.ts` and the existing `tests/harness/aci/read-path-live-task-root.test.ts` vintage pins); the permission-side denial anchors live in `tests/harness/permission/`. Protected-path fixtures are created inside per-test temp directories — never the repository's `data/`, never a real `~/.ssh` / `~/.aws` path, never real credential content.

- **SC1 — ordinary host file, all three tools, both modes.** A file at an ordinary host path **outside** the live `taskRoot` (a temp dir unrelated to the task root) is readable via `read_file`, discoverable by content via `grep`, and discoverable by name via `glob` — under `fsMode: "global"` **and** `fsMode: "workspace"`. Binary: six assertions pass (3 tools × 2 modes), and each succeeds through the real tool handler against real temp files, not a mock. Test surface: `tests/harness/aci/tools/host-read-policy.test.ts` (mode-parameterized) + `read-file.test.ts` / `grep.test.ts` / `glob.test.ts`.
- **SC2 — protected path, all three tools, both modes — refused.** A read of a protected credential / sensitive path (`~/.ssh/id_rsa`, `~/.aws/credentials`, a `.env` file, a `*.pem`) is **refused** via `read_file`, `grep`, and `glob`, under both modes. The direction is **pinned here, not deferred to the implementer**: the read policy answers a protected path with a **refusal**, and masking is _not_ an available answer on these three tools. (Masking may still exist downstream as a separate, additive concern over _already-permitted_ content — it never substitutes for this decision, per the Boundaries bullet "Apply the policy before content enters a tool result".) No protected file's bytes appear in any tool result. Binary: the refusal is a **typed tool error** whose message names the **protected-path** rule (not a nonexistent mode restriction, not "file not found"), and the same fixture **is** still refused through the shell channel's unchanged `SENSITIVE_PATH_FRAGMENTS` protection. Test surface: `tests/harness/aci/tools/host-read-policy.test.ts`, cross-checked against the existing anchors `tests/harness/permission/sensitive-path-command.test.ts` and `tests/harness/aci/permission.test.ts`'s `commandContainsSensitivePath` cases, which stay green.
- **SC3 — symlink alias denied, no bypass.** A symlink at an ordinary path pointing **at** a protected path is denied by the same rule as a direct read of the target — for all three tools, both modes. The reverse direction is also pinned: an ordinary file reached through an ordinary symlink chain is **allowed** (so the fix is not "refuse every symlink"). Binary: for each of the 3 tools × 2 modes, the alias read fails and the benign alias read succeeds. Test surface: `tests/harness/aci/tools/host-read-policy.test.ts` (symlink section; `mkdtemp` + `symlink` on the host tmp).
- **SC4 — symbol-tool direct file open uses the same policy, on the symbol family's own channel.** A `find_symbol` / `get_symbols_overview` / call-hierarchy call naming a protected path is denied by the canonical read policy, at the point the language server would open the document — i.e. the refusal happens **before** `didOpen` puts the bytes into the server, not by post-filtering the query result. Carrier: these tools return `T | string` and have **no error channel**, so the denial is returned as a **readable sentinel string in the same family as `renderNoServer`** (`lsp.ts:196`) — **not** a thrown `ToolExecutionError` (which the signature cannot produce) and **not** a reuse of the existing `no-server` / no-project-anchor sentinels, whose meanings stay distinct and separately asserted. The sentinel is produced before `client.withDocumentOpen` is entered, so no `didOpen` ever carries protected bytes. This is the same _decision_ SC2 pins on `read_file` / `grep` / `glob`, carried on the channel those tools actually own — the two criteria are consistent by construction, not by later reconciliation. Binary: a symbol call on a protected file returns the protected-path sentinel and the server is never opened on that file; a symbol call on an ordinary file is unchanged from today. Test surface: `tests/harness/aci/lsp.test.ts` (the existing symbol/LSP suite; a stub client may stand in for the language server at that boundary — the policy call itself is real, and the test asserts `withDocumentOpen` / `didOpen` is **not** reached for the protected path).
- **SC5 — ordering: policy enforced before any reach broadening.** The protected-path policy is live and enforced on every read-capable tool **before** the host-reach widening in SC1 merges. No commit in the series broadens one tool's reach while another tool is still unguarded. **This criterion is also the answer to "does this span too many files to be one task":** the response is a single PR whose commit series is ordered protection-first, never a split into separately-merged protection and reach changes. Binary: the commit series shows the policy module + its enforcement across **all** read-capable tools in the same PR (or an earlier one) as the first reach widening; `git log` over the branch shows no commit that widens `read_file` / `grep` / `glob` reach ahead of the policy landing. This is a series-order check, reviewed at merge, not a runtime assertion.
- **SC6 — the shared policy is the single answer.** The three tools do not each carry their own reach derivation. The per-tool `readRoot` allowlists (`grep.ts:111`, `glob.ts:88`) and `read-file.ts`'s `computeExtraReadRoots` (`:140-153`) either delegate to the shared module or are deleted in favor of it. Binary: `rg -n "extraReadRoots|resolveSearchRoot" src/harness/aci/tools/` shows one owner, not three; and `npm test` is green, including `tests/harness/aci/read-path-live-task-root.test.ts` (the per-call `LiveTaskRoot` vintage invariant — root and extras on the same snapshot — must survive the refactor, since it is an existing regression guard, not an incidental detail).
- **SC7 — no write-root drift.** `write_file` / `edit_file` behavior and containment are byte-identical before and after. Binary: `npm test` green with no assertion relaxed; `git diff` over `write-file.ts` / `edit-file.ts` shows no reach change; `tests/harness/aci/tools/write-file*.test.ts` and `edit-file*.test.ts` unchanged.
- **SC8 — no unguarded `/`.** The implementation does not achieve host reach by adding `/` (or an equivalent) as an unguarded read root. The reachable set is "ordinary host paths minus the protected-path inventory", and the refusal is issued by the policy. Binary: code review of the shared module shows a positive protected-path check on every arm; a test asserts that a protected path **under a directory that is otherwise fully reachable** is still refused (so the rule cannot be satisfied by scoping the reachable set).
- **SC9 — the read-policy roster is no weaker than the shell roster (the two-roster pin).** The read policy's roster and `SENSITIVE_PATH_FRAGMENTS` are two separate frozen lists (see Boundaries), and the read policy's is **never weaker** on the paths both cover: every path the shell wall denies via `matchSensitivePath` (`hard-walls.ts:3315`) is also denied by the read policy. Binary: a test iterates the shell roster's fragments through the read-policy matcher and asserts deny for each, so no future edit can narrow the read policy below the shell floor without going red; `git diff` over `hard-walls.ts` and `SENSITIVE_PATH_FRAGMENTS` in this series is empty. Test surface: `tests/harness/aci/tools/host-read-policy.test.ts` (roster-parity section, importing the shell roster read-only).
- **SC10 — empty and whitespace input denied, no crash.** The empty string, whitespace-only strings, and a path reduced to separators are passed straight at the policy matcher. They are **denied** (fail-closed per the EXIT contract), never allowed, never forwarded to a tool that would throw an untyped error, and the matcher itself does not throw. Binary: each input returns the typed deny (file tools) / the named resolution-failure sentinel (symbol family) with a message that identifies the unusable input; no uncaught exception, no `TypeError`, no `ENOENT` leaking out of the matcher. Test surface: `tests/harness/aci/tools/host-read-policy.test.ts` (empty-input section; one direct matcher call plus one end-to-end `read_file` call).
- **SC11 — overflow / over-long input has a defined typed outcome, never a crash and never an allow.** A path at or above the platform path-length limit (`PATH_MAX`; `ENAMETOOLONG` on realpath) and a path with an extreme segment count (deep nesting, and a very long single segment) are passed at the matcher. Each has a **defined, typed** result: a deny whose message names the resolution failure (the "too long" refusal of the EXIT contract), or a named `"too long"` refusal variant — the implementation picks one, names it, and the test pins that choice. Binary: neither input produces an uncaught throw, an untyped crash, a truncated-path allow, nor a silently-truncated match against the roster. Test surface: `tests/harness/aci/tools/host-read-policy.test.ts` (overflow section; synthetic long strings, no filesystem access needed for the matcher-level cases).
- **SC12 — concurrency: the policy is pure, the decision precedes the open.** The policy is a pure, stateless function of (path, mode, identity roots) with **no cross-call mutable state** (no memo cache keyed on client or session, no counters, no lazy initialization of protected state). Concurrent calls therefore cannot race the decision: N simultaneous `find_symbol` calls against one shared, refcounted `withDocumentOpen` client produce N independent verdicts computed **before** any open, and a protected path's verdict does not depend on whether another call for the same file is in flight. Binary: a test fires concurrent symbol calls (mixed protected and ordinary paths, and repeated calls on the same path) against a single shared stub/refcounted client and asserts each result matches its single-threaded verdict; the protected ones never reach `withDocumentOpen` / `didOpen`. The shared policy module is additionally importable and callable with no client, no `ctx`, and no session handle — asserted by calling it directly in the SC9/SC10/SC11 sections with no fixtures. Test surface: `tests/harness/aci/tools/host-read-policy.test.ts` (concurrency section, `Promise.all` over the real tool handlers) + `tests/harness/aci/lsp.test.ts` for the shared-client refcount case.
- **SC13 — exception input denied (fail-closed canonicalization).** A symlink whose target does not exist (dangling), so `realpath` throws `ENOENT`; a symlink loop (`ELOOP`); and a path whose traversal hits a non-readable component (`EACCES`, e.g. a `chmod 000` directory, skipped when running as a user for whom mode bits do not restrict — the case is then registered as not-run, per the test policy, not silently passed). All are **denied** per the EXIT contract, with a message naming the **resolution failure** — distinct from a protected-path denial and from an out-of-reach denial — and never an allow. Binary: each case returns the typed deny / resolution-failure sentinel; no raw `ENOENT` / `ELOOP` / `EACCES` escapes from the matcher or from a tool handler, and no exception escapes the policy as an allow. Test surface: `tests/harness/aci/tools/host-read-policy.test.ts` (exception section; `mkdtemp` + `symlink` on the host tmp, targets created and then removed to make the link dangle, plus a self-referential link for the loop).

## Inherits / Changes

### Quoted from ADR-0128 (accepted, 2026-09-28)

> "ADR-0092 defines global and workspace filesystem modes as broadly readable host views; workspace mode primarily tightens writes under home. Read-capable ACI tools currently impose separate task-root allowlists, producing inconsistent behavior for ordinary host files. The `read_file`, `grep`, and `glob` tools should support ordinary host-path reads in both modes under one canonical read policy; symbol tools remain project-indexed, but any direct file opening must use that policy. Protected credentials and other sensitive paths must retain at least the protections applied to shell reads before any tool's host reach is broadened; granting `/` as an unguarded read root is not an acceptable implementation. This decision does not expand the `write_file` or `edit_file` write roots, and a future project-only read mode would require a separate decision."

and its consequence:

> "The shared policy must be applied before file contents enter a tool result, including through symlinks and language-server file opening. Tool-local output masking alone is not a read authorization boundary. The downstream specification must define the protected-path inventory and tests for ordinary external files, protected files, symlink aliases, and both filesystem modes across each read-capable tool."

### Quoted from ADR-0092 (the fs-mode contract this spec does not re-decide)

> "The optional **workspace mode**: home is visible, writes = live `taskRoot` + **session tmp**; the rest of home is not writable by default."

and, on the fence shape:

> "**Write tools**: the containment root of `write_file` / `edit_file` is **the same** under both modes (live `taskRoot` ∪ session tmp) — the workspace mode adds no new rejection surface on the write-tool side; its tightening lands only in the bash fence's mount layer."

This spec reads the corollary ADR-0128 draws: the modes differ on the **write** axis, so the **read** axis must not differ on them either — hence one answer in both modes (SC1).

### Existing seams the contract depends on

- `resolveWithinRoot` (`src/harness/aci/tools/helpers.ts:246-269`) — today's containment primitive: realpath-based, symlink-escape rejecting, with `extraReadRoots` / `extraWriteRoots` / `sessionTmpRoot`. The shared policy composes with it; it does not replace the realpath discipline.
- The per-tool read roots being unified: `read-file.ts:140-153` (`computeExtraReadRoots`) + `:320-353` (`resolveReadTarget`); `grep.ts:111-113` (`readRoot`) + `:288-296` (`resolveSearchRoot`); `glob.ts:88-90` (`readRoot`) + `:222-247` (`resolveSearchRoot`). Assembly wiring for all three: `src/harness/aci/tools/registry.ts:788-819`.
- The shell's protected-path protection, which is the floor: `SENSITIVE_PATH_FRAGMENTS` (`hard-walls.ts:135-158`), the command-text reader `commandContainsSensitivePath` (`:3047`, exported and re-exported through `src/harness/aci/permission.ts:109`, applied pre-spawn at `src/harness/aci/tools/bash.ts:855-858`), and the path-tool hard wall `hard-wall:sensitive-path` (`hard-walls.ts:3336-3343`, matched via `matchSensitivePath` at `:3315` over the `path` / `file` / `filepath` / `target` input keys). The reason string at `:3340-3341` names the inventory categories and stays accurate.
- The LSP direct-file-open surface: `src/harness/aci/tools/symbol.ts:170-193` (`withResolvedSymbol` → `client.withDocumentOpen`) over `src/harness/lsp/client.ts:97` (`withDocumentOpen`, which reads on-disk text for `didOpen` / `didChange`); the coordinate-addressed `lsp_*` family in `src/harness/aci/tools/lsp.ts` is the same pipeline and inherits the same treatment.
- The fence's own read posture: `src/harness/sandbox/fs-policy.ts` (global mode binds the host root; system prefixes re-bound read-only) — the read policy is the **tool-layer** counterpart of that posture and must not contradict it.
- ADR-0019 workspace-root decoupling: `<workspaceRoot>/.iknow` is an existing read root (`read-file.ts:76-81`, `:146-148`); it stays reachable under the new policy (it is not protected — the protected-state write guard it mentions was retired by ADR-0092).

- One shared read-policy module exists; the three per-tool reach derivations and `read-file.ts`'s `extraReadRoots` computation defer to it (SC6).
- `read_file` / `grep` / `glob` reach ordinary host paths in both modes (SC1) — a widening, gated on SC5's ordering and SC2/SC3's protection.
- Protected paths are refused on those three tools by the canonical policy (SC2) — refusal, not masking — with no symlink alias reaching what its target could not (SC3).
- The symbol family refuses a protected path at document-open time, carrying the refusal as a readable sentinel string on its `T | string` channel (SC4).
- The read policy's roster is a new constant in the shared module, no weaker than the shell wall's `SENSITIVE_PATH_FRAGMENTS` (SC9); `hard-walls.ts` is untouched.
- The policy is fail-closed on every undecidable input — empty, over-long, and canonicalization-failure paths all deny (SC10 / SC11 / SC13) — and carries no cross-call state (SC12).
- `write_file` / `edit_file` are untouched (SC7); a project-only read mode does not exist (Out of this spec).

### 待写入 (to-persist)

Genuinely new domain terms, **not** yet in `docs/CONTEXT.md` (checked: `文件系统隔离档`, `工作区档`, `taskRoot`, `projectIdentityRoot` are present; none of the following are):

- **canonical read policy** — the single read-authorization rule shared by every read-capable ACI tool, replacing the per-tool task-root allowlists; it is the read-side counterpart of the bwrap fence's read posture, and it is the thing ADR-0128 forbids implementing as an unguarded `/` read root. _Avoid_: calling it "read permission" (that is the ADR-0004 permission middleware, a different layer) or "read fence" (that is bwrap).
- **protected path** — a path in the frozen protected-path inventory, denied to reads regardless of reachability. Needs an `_Avoid_`: it is a **read** notion and must not be conflated with the retired fs-policy protected-state predicate (retired by ADR-0092 per ADR-0019's amendment) or with the write-side hard-wall.
- **host reach** — the set of paths a read-capable tool may open in a given mode. _Avoid_: "workspace read" as if workspace mode narrowed it (ADR-0092 + ADR-0128: it does not).

No ADR is opened by this spec: ADR-0128 already carries the decision. CONTEXT writes are a `domain-modeling` task in a later phase — this file only lists the terms.
