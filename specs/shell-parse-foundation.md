# Spec: Unified shell-parse foundation (migration Stage 0)

**Status:** draft
**Basis:** ADR-0123 + ADR-0124 (+ ADR-0068 amendment 2026-09-24); grounding research (gitignored, main checkout only — `.gitignore:206`, so unverifiable in any other checkout): wayfinder map `unified-shell-parsing`, tickets usp-1 / usp-2 / usp-3 / usp-5, `docs/wayfinder/research/usp-1-parser-survey.md`. **The gitignored material is provenance only.** Every Success Criterion below is a command that runs in this repo or an assertion over files in this repo; no criterion quotes a ticket, and the two adversarial inputs SC4 names are recorded in ADR-0123's 理由 paragraph (`docs/adr/0123-unified-shell-parse-foundation.md:14`: "80k 语句 / 20k 深嵌套"), which is tracked. **The one place a survey measurement is cited is SC4/N2's choice of the 5 000 µs seam budget, and it is provenance for a constant, not the predicate of an assertion** — what SC4 grades is a returned `kind`, in a test that runs in this repo, so if a future host made 5 000 µs insufficient the criterion would fail here, not on a document another checkout cannot read.
**Surface:** new module `src/harness/permission/shell-parse.ts` + `package.json` dependencies + offline divergence-corpus tooling (`scripts/`, `tests/`, with the report's own test file named — `tests/harness/permission/shadow-divergence.test.ts`, which holds SC10's corpus format test and SC11's class-(e) membership-plus-B1 assertion, so those two pins have a committed home instead of a reading of the report's prose) + one notice arm added at the existing `<PromptInput>` call site in `src/tui/app.tsx` (no new `src/tui/` file — see SC13)
**Downstream dependents (not this spec):** `specs/substitution-hard-walls.md` (Stage 1, the ADR-0125 matrix) and `specs/hard-wall-ast-migration.md` (Stages 2-4: destructive → bare-metachar + root-find → splitter retirement and the remaining consumers). Both exist and consume what this spec builds; neither may invent a second parse input.

## Objective

Build the **解析地基** as a standalone module and freeze the **解析判定** contract, plus the **离线影子对照** tooling that gates Stages 1-4. After this stage lands, the foundation exists, is unit-tested, and is reported on — and **no wall consumes it yet**: every deny / ask / allow outcome in the product is identical to today.

User = the implementers of the two sibling specs (they get one parse input and one gate mechanism instead of re-scanning raw text) and the operator (who reads one divergence report per stage). Success = `parseForSecurity` classifies every input into the closed verdict set with the pinned resource numbers, the `ok` payload carries every syntactic fact Stage 1-4 need (SC16), the degrade seam's outcome type is closed and total (SC15), the dual-run report runs in CI and shows zero UNEXPECTED divergences, and `hard-walls.ts` / `policy.ts` / `bash.ts` / `types.ts` / `declarative.ts` are untouched bytes.

## Assumptions (operator-confirmed — pinned, not re-opened by the implementer)

These are contract parts, not defaults to be rediscovered:

1. Native bindings only: `tree-sitter@0.25.1` + `tree-sitter-bash@0.25.1`, exact pins, N-API vendored prebuilds (`linux-x64`, `linux-arm64`, `darwin-x64`, `darwin-arm64`, `win32-x64`, `win32-arm64`), **not** WASM; `web-tree-sitter` is **not a direct dependency** and **no `.wasm` grammar is installed** — the two checks SC2 states. **Round 7 corrected this clause's wording, because the property was right and the sentence was false as measured:** it previously read "no `web-tree-sitter` anywhere in the tree", and `grep -c web-tree-sitter package-lock.json` prints **3** in this repo today — the package is the peer dependency of the pinned direct dep `@opentui/core@0.5.1` (`package.json:85`, `package-lock.json:1276` → `:1299`, resolved entry `:7954` with `"peer": true` at `:7959`), which no stage of this migration may remove. `engines.node >= 20` already holds; no musl / 32-bit ARM target is required (ADR-0123: "仓库 `engines.node >= 20`、纯 npm 分发、无 musl/32 位 ARM 目标，原生 prebuild 缺口咬不到").
2. Over-cap threshold = **64 KiB per command** (65 536, measured as the UTF-8 byte length of the input string), checked before the parser is touched.
3. Sync timeout budget = **200 ms** (`parser.setTimeoutMicros(200_000)`); budget exceeded → `aborted`. The number is a frozen module constant, `PARSE_BUDGET_MICROS = 200_000`, and **no config, env, or runtime path can change what the public entry passes**: `parseForSecurity(command)` is _defined_ as `parseForSecurityWithBudget(command, PARSE_BUDGET_MICROS)`, and that second entry exists only so the `aborted` arm is provable at a _smaller_ budget (SC4/N2) — Assumption 7's seam-vs-knob rule is what separates it from the forbidden switches, and SC4's companion `rg` pin is what enforces it. ADR-0123:12's 「单一全同步入口 `parseForSecurity(command)`」 still holds verbatim — and round 5's NB5 sweep is what fixed the _attribution_ rather than the wording: that exact phrase is ADR-0123 line 12, not CONTEXT's, whose 解析地基 entry states the same rule with the same content in a different word order (「全同步 `parseForSecurity(command)` 单一入口」), so quoting CONTEXT for the verbatim phrase was a mis-attribution the file then built an argument on. "single entry" is about the entry _consumers_ reach, and the pin proves the second symbol is reachable from nothing else in `src/`.
4. Memo cache = **LRU 64 entries**, keyed by the exact command string (no normalization), module-lifetime, process-local, never persisted. **The per-arm memo policy is pinned here** (SC7 asserts it arm by arm); the one rule is _a verdict is stored only if producing it required a parse — and never a verdict that reports transient or process-level state rather than a property of the string_:

   | verdict arm          | memoized                                          | reason                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
   | -------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | `ok`                 | yes                                               | the payload **is** the expensive value; ADR-0123's premise is that the policy gate and the handler gate share **one** parse over the same string, and that premise is only true if `ok` is stored                                                                                                                                                                                                                                                                                                                                           |
   | `malformed`          | yes                                               | the parse ran, so recomputing means re-running it — the same two-gates premise; and an `ERROR` / `MISSING` tree is a fact of the string under the pinned grammar, so the answer cannot drift between calls                                                                                                                                                                                                                                                                                                                                  |
   | `unknown-syntax`     | yes                                               | same (the parse ran); additionally the modelled roster is a frozen `Set` for the process lifetime, so the out-of-roster test is deterministic per call                                                                                                                                                                                                                                                                                                                                                                                      |
   | `vetoed`             | **no — nothing stored**                           | decided by a character sweep **before** any parser exists; a memo would save one linear scan while pinning a key of arbitrary length and a payload that is a single class name                                                                                                                                                                                                                                                                                                                                                              |
   | `over-cap`           | **no — nothing stored**                           | decided by a length check, and the key is by definition **longer than the 65 536-byte cap** — storing it would make the cache's retained bytes unbounded and would falsify OQ4's arithmetic                                                                                                                                                                                                                                                                                                                                                 |
   | `aborted`            | **no — recomputed on every call, nothing stored** | the timeout measures host pressure at this instant, not the string. A memo would freeze one transient cancellation into a permanent hard deny for that command, and it would contradict Assumption 6, whose fresh-instance-per-command rule exists precisely so no parse inherits the previous parse's state. Note that the _only_ input SC4 can make abort deterministically does so through the budget seam, so SC7's pair for this arm is that seam call — at the frozen 200 000 µs this stage has no satisfiable `aborted` input at all |
   | `parser-unavailable` | **no — nothing stored**                           | this arm reports the _state machine_, which is process-level and terminal, not a property of the string; the seam answers before the cache is consulted, so there is no per-string fact to store                                                                                                                                                                                                                                                                                                                                            |

   Two consequences are pinned with the table, because they are what makes it gradeable: **(i)** an implementation that memoizes `aborted`, or that leaves any non-stored arm in the cache, fails SC7 — and so does one that fails to store `ok` / `malformed` / `unknown-syntax`, since that is the shared-parse premise; **(ii)** because nothing longer than the cap is ever stored, **every key in the cache is ≤ 65 536 bytes by construction**, which is the bound OQ4 reasons about. The policy is a caching detail this spec owns outright — ADR-0123 says only 「按命令字符串的**有界缓存**」 (`docs/adr/0123-unified-shell-parse-foundation.md:12`) and names no size, and ADR-0124 §5 delegates nothing about caching: what §5 delegates is **the over-cap magnitude alone** (「上限取值从宽（64KB 量级，精确值归 spec）」, `docs/adr/0124-parse-verdict-contract.md:18`), which is Assumption 2's business and not this table's — so the memo policy is not a contract part of 解析判定 and grows no ADR and no glossary entry (see 待写入). **[round 7 cite correction: this sentence previously credited ADR-0124 §5 with delegating the memo policy, and the bullet below in 待写入 credited it with all three pinned numbers; §5 is the over-cap clause and speaks about neither the cache nor the budget, so the re-attribution above is what the file's own ADR reads produced.]** Round 2 changed one thing here: pre-revision SC7 said "`over-cap` and `vetoed` are cached", and pinning the _reason_ for each arm exposed that as unbounded key retention for zero saved work, so both arms moved to "not stored" (the row reasons above; OQ4's numbers now hold).

5. Lazy init: the binding is loaded on the first bash permission check that reaches `parseForSecurity` (one-off ≈ 10 ms measured: `require` 4.1 ms + grammar `require` 1.5 ms + first `setLanguage`+parse 4.4 ms). No startup prewarm, no top-level `require`.
6. **Fresh `Parser` instance per command** (never pooled, never reused across a cancelled parse), because "超时取消后复用同一 Parser 实例会对合法输入产出假 `ERROR`（实测，`reset()` 后恢复）——对策即"每命令新建实例"，把状态残留整类排除" (ADR-0123). Measured cost of the per-command construction is ≈ 0 ms.
7. No feature flag, no env-var escape hatch, no runtime shadow mode (usp-5 decision 5: "发布切面：无任何开关（C）"). Rollback of this stage = `git revert`. **The scope of that ban, stated once because two later clauses depend on it:** it covers _process-level input_ — env vars, config files, feature flags, a runtime shadow mode, i.e. any path by which a value can arrive at the module from outside the call — and it does **not** cover a test seam that takes no external input: an exported function whose extra argument is written in the caller's source text (`parseForSecurityWithBudget`, whose only `src/` caller is `parseForSecurity` with the frozen constant), an installer a test uses to substitute a failing dependency, or a getter that only reports (the four seams listed under Changes). The discriminator is not the name but the direction of data flow: a knob lets the _product's_ behavior be changed from outside the module; a seam lets a test see, or supply, something the product supplies itself. SC4's `rg` count is what stops the first seam from silently becoming the second, and no seam here reads `process.env`, a config file, or a flag.
8. Legacy scan (`findDangerousPattern`, `splitShellSegments`, `SENSITIVE_PATH_FRAGMENTS`) is neither deleted nor rewired in this stage; it stays the live decision path and becomes the degrade layer plus the corpus tool's left-hand side. **Its answer is a floor, not a placeholder**: because `findDangerousPattern` is exactly what the `parser-unavailable` arm returns, Stage 0 keeps `hard-walls.ts` byte-intact, **and no stage may weaken what the degrade path answers**. A command the legacy scanner denies today — including the quote-blind substitution branches inside `scanSegment` (`hard-walls.ts:654-665`: `$(`, `${`, backtick, `<(`) — must still be denied under `parser-unavailable` after every stage lands. Relaxations belong to the _parse_ path only; lifting them out of the legacy scanner would turn a hard deny into an allow precisely when the parser is missing, which is the one state where the legacy answer is the only answer. One corollary, because later stages touch this file's fallback: whatever a later stage rewires `findDangerousPattern` to do, the value passed as `legacyScan` must remain a **text-scanning** layer of at least today's strength — it cannot become "the AST path", because by definition the AST path is unavailable in exactly the state that calls for it. If a stage ever needs to split those two roles, it splits them into two functions and passes the text one here; that is a change to the call site, not to this contract. Round 3 closes the ambiguity that last clause leaves open, because Stage 1 asks exactly this question: **the seam's `legacyScan` parameter names a _role_ — "the current text-scanning layer" — not a permanent binding to one exported symbol.** `findDangerousPattern` is the value that fills the role _today_; Stage 1 (`specs/substitution-hard-walls.md`) is the stage that re-homes that symbol, after which it becomes parse-driven, and the legal value from that stage onward is the text scanner Stage 1 extracts out of it, passed at the same call site. Both values are legal in their own stage, both must satisfy the floor above, and neither may be the AST path — so no implementer has to guess whether "exactly one argument is ever legal" freezes the symbol name.

## Boundaries

- **Does:**
  - New module `src/harness/permission/shell-parse.ts` with **two** sync entries and a pure-function contract: `parseForSecurity(command: string): SecurityParseResult` — the entry every consumer reaches, which is what ADR-0123:12 quotes verbatim as 单一全同步入口, and what CONTEXT's 解析地基 entry carries as 全同步 `parseForSecurity(command)` 单一入口 — and `parseForSecurityWithBudget(command: string, budgetMicros: number): SecurityParseResult`, of which the first is _defined_ as the second called with the frozen `PARSE_BUDGET_MICROS = 200_000` (Assumption 3; the seam-vs-knob rule of Assumption 7; SC4's `rg` count, which is what proves the second entry has no `src/` caller but the delegation line). No `async`, no `Promise`, no `await`, no I/O on the parse path; both entries are pure functions of their arguments, which is why a later stage may feed extracted text (a heredoc body — see `heredocs[]`) to `parseForSecurity` recursively without a second export. `HardRuleSpec.match` (comment "Predicate against the raw call input; must be a pure function.", `types.ts:45`; the `match` declaration itself is `types.ts:46`), `checkPermission`, and the bypass consumers (`scripts/sandbox-probe-subagent.ts`) keep their signatures byte-for-byte — "理由：`HardRuleSpec.match` 的同步纯函数契约（`src/harness/permission/types.ts`）零改动" (ADR-0123).

    **Where the `ask` destination is built — and it is not built here.** The permission layer cannot emit an ask at all today: `HardRuleSpec.decision` is the literal `"deny"` (`types.ts:50`) and `checkPermission`'s hard-wall loop returns `deny` and nothing else (`policy.ts:130-141`). The emitting point belongs to Stage 1: one new **mode-aware** step in `checkPermission`, after the layered-rule loop, which carries `unknown-syntax` alongside Stage 1's own ask findings (`specs/substitution-hard-walls.md` Assumption 9 + SC17). Mode-aware means what it says: the step emits its ask only when the resolved mode actually prompts, and stays silent in the mode that does not prompt (`policy.ts:162-170`) and in `plan` (`:171-178`), so ADR-0124 §2's allow-parity holds and `plan`'s deny of non-`read-only` categories is not pre-empted — a step placed _before_ those branches would answer `ask` where today's contract answers allow-or-deny, and neither stage owns that change. Two consequences are pinned here: no implementer should look for an ask seam in this stage's diff, and this stage never touches `policy.ts` (SC13). The same paragraph is why this file names that mode descriptively — "the mode that does not prompt (`full_auto` as named today)", `modes.ts:28` — wherever the _policy_ is described, so the operator's separately filed proposal to rename the value (and possibly merge the yolo axis, which would reverse ADR-0119 §1's "independent boolean state axis, not a fourth `PermissionMode`") cannot silently invalidate this contract. Quoted ADR text keeps the original word.

  - Pre-parse veto (before the parse is trusted, so before `parseForSecurity` would classify): a roster of **解析分歧字符** — control characters except `\t` `\n` `\r`; Unicode whitespace / zero-width (category `Zs`/`Zl`/`Zp` plus `Cf` zero-width and `U+FEFF`); backslash immediately followed by whitespace. The result is a distinct arm of `SecurityParseResult` (`kind: "vetoed"`, carrying the character class), never a seventh verdict, matching "解析判定 … 六态闭集… 加解析前字符级一票否决清单" (CONTEXT). Reason text names the class: "连解析都不做，直接**硬拒**，reason 写明字符类别" and "清单住 `shell-parse.ts`、登记进 spec，每发现一个新分歧登记一条" (ADR-0124). `echo\ test` is vetoed and its reason carries the rewrite hint to the quoted form.
  - `ok` payload (`SecurityParseOk`) — field-level facts, so no consumer re-scans raw text; the per-field coverage rule is **SC16's (α) clause and nothing restates it here** (round 6's MEDIUM 2 rule — one owner per predicate: this line previously printed its own weaker copy of the quantifier, "at least one assertion per field", which after round 6 omits (α)'s population requirement, i.e. would have tolerated a `length === 0` pin for a field the named input cannot fill; round 5's NB2 is the reason the quantifier reads "at least one" inside (α) rather than "exactly one"), and every field below names the consumer that needs it (a fact with no consumer is not added). **Every span in this payload is a JS string index into `text`**, so `text.slice(start, end)` returns exactly the covered substring — a deliberately different unit from Assumption 2's cap, which counts **UTF-8 bytes**; SC16 pins the difference with one non-ASCII command, because a byte-offset implementation passes every ASCII pin and fails that one. **Division of labor, one sentence: the foundation reports "this body is consumed by command word X, whose delimiter word is quoted" as a syntactic fact, and only Stage 1 decides whether that makes the body code or data** — "the parse foundation supplies syntactic facts, deny policy stays with the walls" (ADR-0068 amendment 2026-09-24).
    - `text` — the verbatim input, unnormalized (a consumer that re-reads this string to decide anything is re-scanning, which is what this migration retires).
    - `words[]` (`WordFact`) — `{ text, quoteKind: "none"|"single"|"double"|"ansi-c", value?, span }`, where `value` is the statically-known literal after quote-and-backslash folding (`r\m` → `rm`) and `undefined` when the word contains expansions. Covers Stage 2's backslash-in-word fold (SC-S2-4) and Stage 4's per-word quote state; already in the payload, cited here so nobody re-derives it.
    - `commands[]` (`CommandFact`) — every command node in source order **including** loop bodies, substitution and process substitution: `{ index, argv: WordFact[], span, parentId?, depth }`. `argv[0]` is the command word, operands are `argv.slice(1)`. `depth` is 0 for a top-level command node and +1 per enclosing command-bearing node — the number Stage 1 compares against ADR-0125 §2's cap; the cap itself is Stage 1's, not a fact stored here.
    - `substitutions[]` (`SubstitutionFact`) — one entry per substitution **site**: `{ kind: "dollar-paren" | "backtick" | "procsub-in" | "procsub-out", span, innerCommandIndex, ownerCommandIndex: number | null }`. `kind` is the construct the parse actually saw, so Stage 1 renders `pattern="subst=<node>"` (its SC11) out of this field instead of guessing the glyph from the text; the `-in` / `-out` split is also what makes the combo wall's "`<(...)` only, `>(...)` recurses" rule (Stage 1 Assumption 5) a field lookup rather than a second scan. Collapsing both directions into one `procsub` token is Stage 1's rendering choice; the foundation withholds no direction. **`ownerCommandIndex` is nullable under the same whole-input rule that made `redirects[]` and `expansions[]` nullable (round 5's NB4), and round 6 closes the inconsistency this bullet had left open: the rule reaches a substitution too.** The named case is `$(whoami)` **as the whole input** — a substitution site with no command word to own it, exactly `> /tmp/f`'s shape one construct over — so `null` here means **"this site has no command-word owner"**, and the consequence is the same: `null` routes the site to Stage 1's ask bucket rather than to a code/data claim, and Stage 1 must not resolve an owner it cannot see by scanning text backwards. The rule was not left as an inference from the sibling fields: the alternative the finding offered — _state why a substitution can never be ownerless_ — was checked against this file's own two claims and cannot be held, because `""` is `ok` with an empty `commands[]` (SC15(e)) and a whole input with no command word is therefore an admitted shape, not an error. The shape is declared with the caveat `:63` already carries and for the same reason: whether `tree-sitter-bash` attaches a `command` node to a top-level bare expansion or bare substitution is **not verified in this worktree** (the package is not installed — Basis), so the claim is settled by OQ3's inventory, which now owes a row for both bare shapes, and by SC16's ownerless-arm pin; the falsifier is named there (if the inventory finds the grammar _does_ supply an owner for a bare `$(…)`, it is this null arm and that pin that change, in this stage's PR — not a downstream relabel).
    - `expansions[]` (`ExpansionFact`) — one entry per **`${var}` / `$var` parameter-expansion site**, i.e. the field ADR-0125 §3's three buckets keyed by _name_ needs and nothing else in this payload supplies: `{ name: string | null, span, ownerCommandIndex }`. `name` is the expanded variable's name as the parse saw it (`${API_KEY}` → `"API_KEY"`, `$HOME` → `"HOME"`), so Stage 1 routes secret-name → hard-deny, `BASE_ENV_WHITELIST` → allow, unknown → ask by reading a field — the alternative is slicing `words[].text` or regexing over `text`, which this payload's own `text` bullet forbids ("a consumer that re-reads this string to decide anything is re-scanning, which is what this migration retires") and which SC16's `r\m -rf /tmp/x` pin restates as "not a regex over `text`". **`name` is `null` only where the site has no identifier at all**, and those cases are named so the arm is a declared shape rather than a catch-all: `$((1+2))` (arithmetic over literals — there is nothing to bucket) and `$1` / `$?` (positional and special parameters — not identifiers, so no whitelist lookup is possible and the site goes to Stage 1's ask route, exactly like `heredocs[]`'s `null` receiver). **Where one site contains more than one _name_, it reports one entry per name, each carrying that site's `span`** (spans may therefore repeat), because ADR-0125 §3 sends the _name part_ of every variant family to the three buckets: `${#arr[@]}` → `"arr"`, `${arr[i]}` → `"arr"`, `$((X+1))` → `"X"`, and a genuinely multi-name site such as `$((A+B))` → `"A"` + `"B"`. **Round 6 restricts the rule's domain to names the shell actually expands as names, and drops the array subscript's identifier from it: `${arr[i]}` reports `"arr"` alone, not `"arr"` + `"i"`.** The reason is the citation this bullet itself leans on: `docs/adr/0125-substitution-policy.md:15` does list `${arr[i]}` among the variants whose 名字部分走三桶 — the name part of `${arr[i]}` _is_ `arr` — and the parenthetical the previous version read as authorising `"i"` (「bash 数组下标做算术求值、算术里可藏命令替换」) is that sentence's reason for **recursing into any-position `$(...)`**, i.e. for the subscript being a place a hidden command can live, not for bucketing an identifier that never reaches a whitelist or secret-name lookup as an expanded name. A second entry for `i` would therefore be exactly what this payload's own lead line forbids adding — "every field below names the consumer that needs it (a fact with no consumer is not added)" — and Stage 1's own variant-form pin (its SC7, "three buckets, every variant form") reads `${arr[i]}` → name `arr` and stops there, so nothing downstream loses a read; Stage 1's SC7 restates this file's per-identifier rule in its own words, and it stays true as narrowed, because multi-name arithmetic sites like `$((A+B))` still report one entry per name. **What the narrowing deliberately does not touch is the recursion:** an expansion written in a subscript (`${arr[$(rm -rf /)]}`) is a substitution _site_ and lands in `substitutions[]` like any other nested site, which is the field ADR-0125 §3's 递归检查 sentence feeds — Stage 1's dependence on that case is why the rule was narrowed by _context_ rather than deleted, and `$((X+1))` → `"X"` stays for the same clause-by-clause reason: `$((…))` is itself listed among the bucketed variants, so an arithmetic operand is a name the ADR sends to the buckets. **That is also why this revision declines round 5's NB1 proposal to classify `${#arr[@]}` as a `null` case:** the ADR text the finding cites (`docs/adr/0125-substitution-policy.md:15`) lists `${#var}` among the variants whose name part is bucketed, so answering `null` there would strand the bucket decision and push Stage 1 back to slicing text — the one move this field exists to forbid. `null` is the _no-identifier_ arm, not the _hard-to-parse_ arm. **No `form` discriminator is added**, on the record: ADR-0125 §3 buckets by name only and lists the variant families (`${var:-word}`, `${#var}`, `${var%后缀}`, `${arr[i]}`, `$((...))`) as taking _one_ route — name to the three buckets, any nested `$(...)` to 递归检查 — so a `form` enum would be published surface no consumer reads, and `complexity-anti-drift` is right to flag that. - **OQ4** Cache key width. Assumption 4's memo table already bounds the **keys**, and the arithmetic is now written in the unit each number is actually in: a stored key's _cap-relevant_ length is its UTF-8 byte count, ≤ 65 536 B, so 64 × 65 536 B = 4 194 304 B = exactly **4.0 MiB counted in UTF-8 bytes** (round 3's R13(a) corrects the previous "≈ 4.2 MiB", which mixed decimal MB into a binary-unit figure). Say which unit a future ceiling is stated in, or the two numbers will be argued past each other. What that arithmetic does **not** cover is the `ok` **payload** riding on each key — a 64 KiB command's `words[]` / `commands[]` / `inert[]` / `heredocs[]` arrays are their own allocation with no pinned ceiling. Accept that worst case, or add a byte ceiling that evicts early? Both are compatible with the pinned "LRU 64 entries keyed by command string"; the byte ceiling is a policy preference.
