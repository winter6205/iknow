# Spec: verify-trust-boundary-and-goal-decoupling — declared = implemented: turn-scoped gate, checker precision, envelope fidelity, and a goal feature that is no longer the core loop's switch

> Input = issue #1195 (`verify subsystem: goal-mode coupling, fail-open evidence paths, cross-turn gate scope, and model-facing false claims`). 10 of its 12 sections are confirmed defects, 9 of which land here; §2 (the judge's self-authored `evidence[]` is never cross-checked) is **confirmed as a defect but decided against as a fix** per `#1199` (2026-10-05) — see "Out of this spec" and Success Criterion 11; §7 (narrow-run detection) is **refuted as a misread** and lands only as an opportunistic narrowing. §11 (stale ticket) is a documentation pointer, not code.
> Durable record: the companion plan `plans/verify-trust-boundary-and-goal-decoupling.md` is a local-only working artifact (`plans/` is gitignored, `.gitignore:221`), so it does not travel with the repo; this spec together with issue `#1199` is the durable record of the T9 / Success Criterion 11 decision.
> Basis = ADR-0024 (two judge modules) / ADR-0032 ("auto mode" is the permission axis, "goal feature" is `/goal`) / ADR-0073 (claim window; HITL is not bounced by a CONTRADICTED); `specs/verify-status-contract.md` (inherited, **never modified** by this spec); `docs/CONTEXT.md` entries quoted verbatim in "Inherits / Changes".
> Terminology: throughout this spec, "auto mode" means the **permission axis** (`full_auto`, per ADR-0032); "goal feature" means the `/goal`-pinned continuation module (per ADR-0024 line 6 as amended by ADR-0032). The two are orthogonal (CONTEXT.md:854) yet two distinct modes in the code today share the word `"auto"` — the banner's (a permission fact) and verify-loop's `completionMode` (a goal-feature fact). Step 1 renames each after the axis it reads; neither spelling is prescribed here, only the rule that each names its own axis.

> **Delivery shape — one capability, one PR.** This is a single capability: _the verify subsystem's declared surface matches what it actually reads_. The build bullets below are **sequenced steps of one coordinated commit series in one PR**, ordered **goal decoupling → turn-scoped gate → checker precision → envelope fidelity → assets**, not five independent tasks. Steps 1 and 2 both re-point the same two seams (`completionMode` provenance, and which message array the gate/checker receive) and each is inert in isolation against the other's half; step 3 changes the evidence contract the step-4 envelopes narrate. ## Objective

The verify subsystem must return to **declared = implemented**: the checker reads what it claims to read, the gate sees only the current turn, every envelope says what its record actually says, and the goal feature is an opt-in module that no longer owns the core loop's terminal vocabulary.

Three concrete failures drive this. **(1) The gate is conversation-scoped, not turn-scoped.** `shouldTriggerVerify({ messages: opts.current.result.messages })` (`src/harness/verify/verify-loop.ts:978`) receives the array loop-engine seeds from `priorMessages` (`src/harness/loop-engine.ts:4127`, `:4141`), so it spans prior user turns. A turn whose prior turn ran a green suite and which itself only explains the result is gated **on** and renders 「✓ 验证通过」 — the exact non-fact `specs/verify-status-contract.md` Success Criterion 8, `docs/CONTEXT.md:622` (「决定**一轮**是否进入 verify 子系统的内容谓词」) and the `shouldTriggerVerify` docstring's own word "this turn" (`src/harness/verify/evidence-checker.ts:498`) all say it must not be. This is implementation-vs-spec deviation, **not a new design** — SC8 and Open Question 3 of the inherited spec are the authority, and step 2 closes the gap. **(2) The checker reads fabrications as evidence.** `FRAMEWORK_RULES[].green` (`src/harness/verify/evidence-checker.ts:104-137`) has no line anchor and `SWALLOWED_PATTERNS` (`:148-158`) blocks exit-code masking but not writes into stdout, so `npx vitest run; echo "Tests  42 passed"` reads SUFFICIENT with a green `exitCode` that belongs to the `echo`. **(3) The envelopes narrate a source that did not run.** A goal-mode CONTRADICTED emits `[VALIDATION FAILED] … source=classifier` (`src/harness/verify/inject.ts:132`) with `reason: classifier reported failure` (`src/harness/verify/verify-loop.ts:1359`) although the judge was never called, and a HITL CONTRADICTED is told 「No verify command is configured for this project」 (`src/harness/verify/inject.ts:299-304`) although the record's own `evidenceVerdict` is `EVIDENCE_CONTRADICTED` — a conflict, not a missing command.

**User**: iknow is single-user and local; the TUI is the main acceptance surface. A human reading the banner must be able to tell "verified green" from "nobody checked" **and** from "somebody else said green"; a model reading an envelope must not be told it claimed something, or pointed at a command, when neither is true.

**What to build**:

1. **Goal decoupling.** The rule "`goal` present → `auto`" is written twice, independently, at `src/session-api/hub.ts:2650-2654` and `src/cli/chat-session.ts:908-923`; the goal feature module therefore owns the core loop's completion-judge switch by a convention repeated at each call site. One activation predicate, owned by the goal layer, consumed by both hosts. Each of the two modes that today share the word `"auto"` is then renamed after the axis it actually reads — the banner's after the permission axis, verify-loop's `completionMode` after the goal-feature axis (ADR-0032, CONTEXT.md:854: the axes are orthogonal).
2. **Turn-scoped gate.** `isTurnQuery` (`src/session-api/turn-projection.ts:102-112`) becomes the boundary the gate and the checker slice from, so both read the current turn's messages and nothing earlier.
3. **Checker precision hardening.** Line anchors on the green-summary regexes; a compound-command output-fabrication void; staleness at tool_use block granularity instead of message granularity.
4. **Envelope fidelity.** §4 attribution goes to the source that produced it; the not-verified envelope stops claiming there is no configured command when the record says the evidence conflicted; the rerun heading stops asserting an unverified completion claim; the probe reader stops reading a key production never sends.

**Success shape**: a cross-turn conversation can no longer produce a verify record, a `; echo "<green line>"` command can no longer produce SUFFICIENT, a CONTRADICTED envelope names the checker, and one module — not two call-site copies — decides whether the goal feature is running.

One rule, one expression, one direction.
  - **(3) Checker precision hardening.** Four independent hardenings inside the existing pure module:
    - **Line anchors on green summary lines.** `FRAMEWORK_RULES[].green` (`:104-137`) matches anywhere in stdout today, so an echoed line matches. Each `green` regex is anchored to a line (the `go` rule already is, `:130`); the anchor must tolerate the real summary-line byte shape per framework, which the existing fixtures pin: vitest is `" ✓ Tests  3 passed (3)\n"` (glyph + space, `tests/harness/verify/evidence-checker/_fixtures.ts:51`), jest is `"Tests:       14 passed, 14 total\n"` (`tests/harness/verify/evidence-checker/frameworks.test.ts:33`). Anchoring to `^\s*` without the glyph is acceptable for vitest but must not admit a mid-line occurrence; the criterion is asserted against those exact fixture strings, so the implementer reads the real bytes from the fixtures rather than guessing the shape.

The walk threads the intra-message block ordinal; `TestRunEvidence` (`src/harness/verify/types.ts:160-175`) gains it alongside `messageIndex`; and ordering compares `(messageIndex, blockOrdinal)` pairs. Comparing at the same granularity on the right edge needs the claim's own block position, so `lastNonEmptyAssistant` (`src/harness/last-nonempty-assistant.ts:7-21`) **additively** returns the content-block index of the last non-empty text block (its existing consumers keep their signatures: `deriveFinalText` in `src/harness/loop-engine.ts:1861-1864` and `deriveClaimIndex` in `src/harness/last-nonempty-assistant.ts:24-28`; a new claim-position helper returns both coordinates). The window's right edge is then "the last non-empty text block", not "the whole claim message", so an edit in the same message is judged in-window.

## Success Criteria

Each criterion is binary and names its test surface.

1. **The goal-activation rule is written once, and both hosts read it.** No source file outside the goal layer evaluates `goal !== undefined && goal.text.length > 0` to decide verify dispatch; a grep for that condition over `src/session-api/hub.ts` and `src/cli/chat-session.ts` returns nothing, while the predicate itself lives in the goal module. Behaviorally: a user-pinned non-empty goal still binds `userText === goal.text` and `completionMode === "goal"` in both hosts; absent goal, empty-text goal, and store-load-throw keep the current HITL + `userText = query` paths (the throw path is fail-open-forbidden per `src/cli/chat-session.ts:920-922`). Test: `tests/session-api/goal-seam.test.ts` (the existing goal/userText cases stay green, unchanged) and `tests/cli/chat-session-user-text.test.ts` (the dispatch cases stay green, unchanged), plus `npm run typecheck`.
2. **Each mode is named after the axis it reads.** Two renames, no wire change: the banner's `VerifyBannerMode` (`src/tui/verify-banner.tsx:37`, TUI-local — `verifyFromWire` at `:162` parses only `outcome` / `rounds` / `notRunReason`, so no mode crosses the wire) is spelled with the **permission** axis's vocabulary, and verify-loop's `completionMode` is spelled with the **goal-feature** axis's vocabulary. Neither value is written with the other axis's word. A `full_auto` session with no goal renders the permission marker, which is a fact about permissions, not an assertion that a goal-feature judge ran. The render path still produces exactly one line for every slot kind, and the two `not_run` rows' glyph / color / label are byte-identical to the inherited spec's locked copy. Test: `tests/tui/verify-banner.test.ts` (existing render cases stay green against the renamed union, plus a case asserting the permission-axis marker renders from `permMode` alone — independent of goal presence).
3. **The goal-mode `not_run` arms are untouched and still asserted.** `npm run typecheck` passes, which requires the `not_run: "active"` arm of `OUTCOME_TO_STATUS` (`src/session-api/hub.ts:582-590`); a `not_run` turn with a user-pinned active goal leaves the persisted `goal.status` `"active"` and never `"achieved"`; and `decideAutoGoalAfterTurn` on a `not_run` turn with `idleCompletedStreak: 2` returns `continueAuto: true`, `clearGoal: false`, and `idleCompletedStreak` **unchanged at 2**. Test: `tests/session-api/goal-status-writeback.test.ts` and `tests/session-api/goal-auto.test.ts` — these are the inherited spec's criterion-5 cases and must pass **unmodified**; this criterion fails if implementing step 1 touched either file's expectations.
4. **The gate is turn-scoped, in both directions.** A two-turn transcript — prior turn with a green test run, current turn with an assistant explanation and no tool calls — yields the transparent no-op result (`enabled: false`, `outcome: "disabled"`, `rounds: 0`, `records: []`, no `verify` key on the wire DTO), byte-identical to a `verify.command`-absent bare run. The converse is also pinned: the same transcript with the green run moved into the **current** turn still gates open and still reaches SUFFICIENT. `claimIndex` is computed against the same sliced array, so no assertion anywhere indexes the pre-slice array. Test: new cases in `tests/harness/verify/verify-loop.test.ts` (loop-level, both directions) and a turn-slicing unit case for the relocated boundary rule.
5. **Same-message and inside-claim edits are visible to the staleness window.** An assistant message carrying a green `bash` test `tool_use` and, as a **sibling block in the same message**, an `edit_file` on `src/foo.ts` yields `EVIDENCE_INSUFFICIENT` with `stale: true` (today: `SUFFICIENT`, `stale: false`). An `edit_file` in a block **after** the claim text block but inside the claim message yields the same. `TestRunEvidence` exposes the block ordinal it was extracted at, and the doc-only exemption still holds at the new granularity (a `.md` sibling of a green run in the same message stays SUFFICIENT). Test: new cases in `tests/harness/verify/evidence-checker/three-guards.test.ts` (the staleness family already lives there).
6. **Fabricated green cannot reach SUFFICIENT, and honest compound commands still can.** `npx vitest run; echo "Tests  42 passed"` with `{code: 0}` → `EVIDENCE_INSUFFICIENT` with `swallowed: true`; the same for `npx jest || echo "Tests: 42 passed"` and `pytest -q || echo "42 passed in 0.5s"`. Line anchoring is asserted directly: a stdout line that merely **contains** a summary phrase without being one (`FAIL src/foo.test.ts > x (Tests 1 failed, 41 passed)` rendered mid-line, or a summary phrase embedded in a longer non-summary line) does not set `greenSummary`. Non-fabricating compounds are **not** voided: `npx vitest run && echo done` with a real vitest summary line stays SUFFICIENT — this is the assertion that fails for a bare `\b(echo|printf)\b` pattern. Test: new cases in `tests/harness/verify/evidence-checker/exit-code.test.ts` (the swallowed family) and `tests/harness/verify/evidence-checker/frameworks.test.ts` (the green-anchor family).
7. **The not-verified envelope reports the record's actual fact.** `buildNotRunEnvelope` invoked with `evidenceVerdict: "EVIDENCE_CONTRADICTED"` and the checker's reasons does **not** contain the substring `No verify command is configured` and does contain the contradiction reason; invoked with `EVIDENCE_INSUFFICIENT` and a configured command, it names that command; invoked with no command and INSUFFICIENT it keeps today's honest "no command configured" branch. The `[VERIFY: not verified]` prefix and the not-run copy locked by the inherited spec are byte-stable. Test: new cases in `tests/harness/verify/inject.test.ts`; the existing `buildNotRunEnvelope` cases are updated only where they assert the false configuration sentence, and never weakened.
8. **A CONTRADICTED envelope names the checker, not the classifier.** On a goal-mode turn where the checker returns `EVIDENCE_CONTRADICTED` and the classifier is never invoked (`runClassifier` counts zero calls), the injected `[VALIDATION FAILED]` envelope does **not** contain `source=classifier`, names the checker as the source, and carries the checker's reason string (`test files cleared or removed (binary contradiction)`). A genuine classifier-reported failure still renders `source=classifier` and `reason: <judge one-line>`. Test: new cases in `tests/harness/verify/inject.test.ts` (the `source` field) plus a loop-level case in `tests/harness/verify/verify-loop.test.ts` asserting the envelope on the real CONTRADICTED path.
9. **Envelope copy asserts only what the system checked.** No injected envelope asserts a completion claim: the strings `You claimed completion` and `You reported the task as complete` do not appear in any `buildEvidenceRerunEnvelope` / `buildNotRunEnvelope` output, while the "run the command and show the green-summary line" obligation and the `[VERIFY: rerun needed]` / `[VERIFY: not verified]` prefixes are unchanged. ## 待写入 (to-persist)

New domain terms this spec would introduce, for `docs/CONTEXT.md` — **not persisted by this change** (`arthurpower:domain-modeling` is not invoked here; recorded as candidates only):

- **tool_use block ordinal** — the intra-message position of a `tool_use` block, used as the ordering coordinate of evidence and staleness alongside the message index. Today both are message-granular, which is why a sibling edit inside the green message is invisible. The new definition must state the two-coordinate comparison and that ordering never uses mtime/diff/git (the existing rule at `src/harness/verify/types.ts:156-160`).
- **envelope fidelity** — the principle that a model-facing verify envelope names only what the system actually observed and the actor that actually produced it: the real source of a CONTRADICTED (checker, not a judge that never ran), the real configuration fact, and no asserted completion claim the system never tested. Proposed as a principle term in the same family as 补跑信封.
- **goal feature activation** — the single predicate over a loaded session that decides whether the goal feature is running (a non-empty user-pinned `goal.text`), distinct from both the permission mode `full_auto` and the verify loop's `completionMode` field. The `_Avoid_` line must carry the collision explicitly: an opt-in feature's activation state is not a completion-judge switch, and a feature's absence is not an evidence fact.
- **output-fabricated evidence** (candidate alongside the existing **pipeline-masked evidence**) — a test run whose command writes a framework-summary-shaped string into stdout after the runner (`; echo "Tests 42 passed"`, `|| echo …`, `printf`), so the reported exit code and the green line both belong to the fabricated step. Distinct from `pipeline-masked evidence` (which loses the exit code) and from the existing 弱绿 family (which reports a genuinely narrow run). The `SWALLOWED_PATTERNS` entry for it is the SSOT. The compound rule's shape constraint comes from this definition: a bare `echo done` after `&&` is not summary-shaped and must stay green, so the regex must test the emitted text's shape, not just the presence of `echo`/`printf`.

**One-way-door ADR: _verify reads the goal feature's activation state; the goal feature does not own the core loop's terminal vocabulary._ Opened by step 1. The boundary it fixes is _who may read whose activation state_ — a module boundary that no current file states in a form that survives a second call site, and one that ADR-0024 line 6 already states in product wording while the code contradicted. If the implementer of step 1 finds any further consumer that wants a "mode" word from either axis, that consumer is the ADR's evidence that the boundary was never written down.

**The candidate is promoted to confirmed — the fourth reader already exists.** A repo-wide enumeration of the goal-activation condition returns **four** live copies, not the three this spec named: `src/cli/chat-session.ts:915`, `src/session-api/hub.ts:2536` (compact task-excerpt suppression), `src/session-api/hub.ts:2652` + `:2657` (the verify dispatch ternary), and `src/session-api/continue-pending.ts:98` — `isPinnedUserGoal`, which is the fourth and the only one that also requires `goal.source === "user_pin"`. Four copies is no longer de-duplication, it is a missing module, so **step 1 opens the ADR**: the boundary is _who may read whose activation state_, and the two predicates (`isPinnedUserGoal` vs the bare `text.length > 0`) are not the same predicate, which is the concrete evidence that the rule was never written down anywhere. The ADR records the module boundary; it does not decide whether `isPinnedUserGoal`'s extra `source` clause is folded into the shared predicate or kept as a deliberately narrower question — that is a **decision bullet** in the plan, and folding it is the default only if it does not change any observable `/continue` behavior.
