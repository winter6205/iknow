# Spec: Effect-boundary protection — protected filesystem / credential effects that no command spelling can bypass

**Status:** draft

**REVISION NOTE (issue #1159; real-bwrap evidence in issue #1163) — the cleanup-receipt mechanism is withdrawn, not deferred.** This spec previously defined an authorized-cleanup **receipt** (issues #1156/#1158) and pinned it through SC3, SC7(b), SC9, Open Question 2, and a dedicated section. **That cleanup contract was NOT fulfilled, and must not be described as delivered.** A real-`bwrap` feasibility run proved the mechanism cannot work on a real kernel: `--bind <path> <path>` makes the path a mount point, and `unlink` on a mount point returns `EBUSY`, so the receipt route cannot delete anything at all (evidence filed in issue #1163). The operator's decision in issue #1159 therefore withdraws the route and supersedes the receipt assumptions in the #1156/#1158 decisions and in the SC3 / SC9 / SC7(b) / OQ2 contract. This revision is deliberately **visible** — the withdrawal is recorded here, the affected criteria say so in place, and SC9's number is left vacant rather than renumbered away. **No protection guarantee is weakened by this revision**: SC1, SC2, SC4, SC5, SC6, SC7, SC8, and SC10 stand as written, hard-wall denies stay non-overridable, and credential read denial and the leak guards stay in force. What is removed is an _authorization mechanism_, not a protection.

**Scope note — one cohesive capability, one PR, a coordinated commit series; the cleanup route is gone from it.** The capability is the **inventory**, the **mount layer**, the **credential read-side control**, and the **`[fs_denied]` feedback template** — still **one** interpreter-independent effect boundary, still deliberately **not** split across specs: an inventory with no mount layer protects nothing, and a mount layer with no inventory protects nothing specific. What issue #1159 changes is the former fourth part: the authorized-cleanup receipt is withdrawn, so the series is inventory+model → mount layer → read-side → copy edits, and the "these parts are useless apart" framing no longer hinges on a fifth part that will not exist. Sequencing inside the series follows the dependency split recorded on the Open Questions: **Open Question 1 (inventory form) blocked the mount layer, the credential read-side control, and SC4** (the read-side control consumes the inventory's credential-source arm, and the message template's `targetClass` is named from the inventory — both are downstream of the inventory-shape decision) and is now **RESOLVED** (issue #1155); **Open Question 2 (authorization signal) is resolved by withdrawal** and no longer gates anything; while **the copy constraints (SC2, and the `[fs_denied]` message-template scaffolding — its prefix/trigger/cap-and-count mechanics, not its target-class wording) proceed independently** and were never held hostage to those decisions.
**Basis:** ADR-0129 (this spec's decision source — protect effects beyond shell intent filtering); ADR-0068 (hard-wall stays a pre-execution intent filter, not a second sandbox); ADR-0092 (fs isolation tiers; global mode's broad-write meaning is unchanged); wayfinder ticket `docs/wayfinder/tickets/hsr-2-command-protection.md`
**Incident:** a denied `rm -f /tmp/iknow-probe-backup` followed by a successful `python3 -c 'import os; os.remove(...)'` of the same file; a denied direct secret-presence probe followed by a successful indirect one. Measured on the current tree: `findDangerousPattern("python3 -c \"import os; os.remove('/tmp/iknow-probe-backup')\"")` returns `null` and `analyzeSecurityReview(...).verdict === "clean"`, while `rm -f /tmp/iknow-probe-backup` yields the `destructive-rm` id. The shell parser sees an operand, not an interpreter API.
**Surfaces (read, not invented):** `src/harness/permission/hard-walls.ts` (`findDangerousPattern` :1103, `commandContainsSensitivePath` :3047, `analyzeSecurityReview` :3286, `hardWalls()` :3325, `SENSITIVE_PATH_FRAGMENTS` :135), `src/harness/permission/shell-parse.ts` (`parseForSecurity` :585), `src/harness/permission/command-roster.ts` (`INTERPRETER_COMMAND_NAMES` :164), `src/harness/permission/policy.ts` (`securityReviewOutcome` :195), `src/harness/sandbox/bwrap.ts` (`createBwrapFence` :377, `workspaceMountArgs`, `unboundFenceArgs`, `egressBindArgs`), `src/harness/sandbox/fs-policy.ts` (`createFsPolicy` :93, `READ_ONLY_SYSTEM_PATHS` :12), `src/harness/sandbox/fs-mode.ts` (`createFsModeContext` :68), `src/harness/sandbox/runner.ts` (`runInSandbox`), `src/harness/aci/permission.ts` (compatibility re-export surface), `src/harness/permission/prefixes.ts` (`[fs_denied]`, `[hard_wall]`)

## Objective

Make the protected filesystem and credential **effects** — not the protected **command spellings** — impossible regardless of whether the agent reaches them through `bash`, through `python3 -c`, or through any other interpreter the fence admits. The shell hard-wall keeps its pre-execution role unchanged (a matched deny stays non-overridable), but a clean static scan is never allowed to stand as proof that a runtime effect is safe. Enforcement moves down to a boundary an interpreter cannot route around by spelling: the mount layer assembled by `createBwrapFence`, the process/session layer in `runInSandbox`, and the controlled-capability layer where a protected credential is only ever handed out as a masked value.

Why: ADR-0129 records the operator's accepted position that the shell permission gate cannot establish that `rm -f X` and `os.remove("X")` have the same deletion effect. Today the protection is real but partial — the hard-wall denies the shell spelling, and nothing downstream denies the interpreter spelling of the same effect. The gap is exactly the class of event the ticket observed, and it is a _spelling_ gap, not a _determination_ gap: the correct answer to "may this file be deleted?" already exists in the operator's head, but the fence cannot express it. _(Revised, issue #1159: the fence still cannot express a *conditional* answer — and, per the revision, no longer tries. The only answer the fence is asked to give is unconditional: protected targets are removable by no spelling, and everything else is governed by ordinary filesystem permissions outside the protected layer.)_

Who: the local operator running a single-user iknow session (the person who must be able to say "that target is protected, no matter how you spell it"), and the model, which must get a truthful signal — blocked at the boundary, with actionable wording — instead of discovering an unpoliced hole.

Success looks like: the same protected target is refused identically by `rm -f`, by `os.remove`, and by any other admitted interpreter; an ordinary backup in a permitted writable location is still removable, by either spelling, through ordinary filesystem permissions with no fence involvement; and no surface in the product ever tells the model or the operator "safe" on the strength of a scan that did not observe the effect.

## Boundaries

- **Does:**
  - **Inventory the protected targets.** One SSOT list of (a) filesystem paths that must stay protected across languages and (b) credential sources that must stay protected across languages. Seed it from what the product already protects by name — the `SENSITIVE_PATH_FRAGMENTS` roster in `hard-walls.ts:135` (`.ssh/`, `.aws/`, `.gnupg/`, `.config/gh/`, `.kube/`, `.docker/config.json`, `.netrc`, `.env*`, `*.pem`, `*.key`, `*.p12`, `id_rsa`, `id_ed25519`, `/etc/passwd`, `/etc/shadow`, `/proc/self/environ`) and the system read-only prefix list `READ_ONLY_SYSTEM_PATHS` in `fs-policy.ts:12` — expressed as resolved, comparable targets rather than as command-text substrings, so the same entry answers a mount-layer question and a read-side question. The inventory is one exported structure; the hard-wall's text roster and the fence's protected-target layer are two consumers of it, not two hand-maintained copies.
  - **Enforce the inventory at the boundary, not in the parser.** The protected targets get a physical, interpreter-independent denial: a mount-layer layer in the `createBwrapFence` argv (the same last-mount-wins discipline as `workspaceMountArgs` and `unboundFenceArgs` — a `--ro-bind` over the protected subtree emitted after the writable binds, so the kernel returns `EROFS` regardless of which program inside the fence attempts the write) and, for reads at credential sources, a process/capability-layer control so a protected credential is only ever reachable as a masked value or not at all. Both live in `src/harness/sandbox/`, where ADR-0068 already put the physical enforcement, and neither lives in `shell-parse.ts`.
  - **Keep the hard-wall exactly where it is.** A matched deny stays non-overridable by session grant. The hard-wall does not gain interpreter-API semantics; `os.remove` is not added to the destructive roster as a string. What changes is the _claim_: the review layer's `clean` verdict is documented and copied everywhere it surfaces as a statement about the command's syntax, never as a statement about its effects.
  - **Keep ordinary backups ordinary — no fence involvement in their cleanup.** _(Revised: issue #1159. This replaces the withdrawn authorized-cleanup-receipt route.)_ A backup the agent itself created lives in an **already-authorized writable location** — one the session was permitted to write before any of this was considered — and carries **ordinary filesystem permissions**. It is removable through shell (`rm -f`) or through an interpreter (`python3 -c 'import os; os.remove(...)'`) **subject to the existing execution rules**, exactly like any other file in a directory the session may write. There is nothing to exempt and nothing to authorize, because **the protected-target layer never opened that backup's parent directory in the first place**; a location outside every protected subtree is governed by the ordinary write rules alone, so both spellings resolve identically and the fence is not a participant in the authorization. Both `rm -f` and `os.remove` on that same ordinary backup must be allowed, and the two must be indistinguishable in outcome.
    - **Hard constraint, non-negotiable: cleanup must never temporarily open a protected path's parent directory, and must never disable or relax a protected path's mask** to make a deletion succeed. This is not a tunable, a cleanup-window, or an escalation path — there is no window at all. A deletion that would require unwrapping protection is refused, full stop, under every spelling.
    - **Non-goal (stated so it is not later read as an omission): this spec does not automatically back up credentials or protected sensitive files**, and defines no sensitive-backup service, backup storage subsystem, or cleanup helper. Backup _creation_ is out of scope; only the fact that ordinary backups remain ordinary is in scope.
  - **Define the failure direction.** A boundary refusal must be reported as a boundary refusal: the `[fs_denied]`-prefixed, EROFS-shaped feedback path that ADR-0109's unbound fence established is the shape to follow — kernel refuses, the message names the target class and states plainly that this session cannot remove the protected target at all (issue #1159 withdrew the cleanup route, so there is no authorized route left to name; advertising one would be untruthful guidance) — and a refusal must never be reported as a hard-wall deny when the hard-wall did not fire. **The reuse is the shape, not the string.** `unboundFenceErofsGuidance` (`src/harness/isolation/worktree-gate.ts:153`) is **not** reused verbatim and its hard-wired text is not edited: its wording is worktree-unbind-specific ("worktree isolation is ON and this session is not yet bound to a task worktree … call `create_worktree` first"), which is a _different boundary_ (the read-only main checkout of an unbound session) and is wrong on its face for a protected-credential refusal — telling a model whose write was refused at `~/.ssh/id_ed25519` to "call create_worktree first" sends it to a fix that cannot possibly help. This spec adds a **new** message template for the protected-target boundary, in the `[fs_denied]` family with its own wording, and the worktree text stays exactly where it is. See "Error handling" below for the template and for the assembly-time failure direction.
    - **Amendment 2026-10-06 (ADR-0140) — two refusals share this prefix and must not share a sentence.** The paragraph above defines the **protected-target** refusal: physical, unconditional, no route, and truthfully so. A _second_ refusal now reaches the same channel — a call that left what the current `fsMode` permits is **answerable**: the operator is asked once whether that call may cross (ADR-0140). It is a different boundary with a different truth condition, so the two arms carry **different sentences under the same `[fs_denied]` prefix**, exactly as the EROFS / non-EROFS arms already do. The existing template's assertion that a target "stays read-only for the whole session" (`src/harness/sandbox/protected-target-feedback.ts`) is **true of a protected target and false of a mode boundary**; a mode-boundary refusal therefore does not reuse it. This matters to the agent, not just to the reader: a permanent-sounding refusal about a temporary condition tells the model there is no narrower spelling to try, which is the one thing it needs to know. Fixing the two templates' wording is the **first** implementation step — this contract moves before any code does.
    - **The mode-boundary question joins the permission decision path, not a second mechanism.** It is decided where every other "does this call need the operator" question is decided, and carried by the product's existing ask route — the operator is asked about a boundary crossing the same way they are asked about a permission. It is **not** a second boundary authority beside the fence, which ADR-0092 rejected ("two implementations that can each drift"): the fence still physically enforces the mode's reach, and this is an additional refusal source, not a substitute. It must be decided **before** the call runs — an answer arriving after the kernel refused cannot widen that call. The full axis contract, including every reachable posture, lives in `specs/permission-axis-semantics.md`.
  - **Test effect-equivalence, not spelling-equivalence.** Every protected-target test runs the shell spelling and the Python spelling (and another interpreter where it is meaningfully different) against the **same** target path and asserts the same boundary outcome. A shell-parse test does not count toward acceptance, no matter how thorough.
- **Confirms with human:**
  - **The exact protected-target inventory.** Whether `SENSITIVE_PATH_FRAGMENTS` as written is the right inventory (it is a _name_ roster, not a _path_ roster: `.env$` and `\.env\.` describe a suffix, `id_rsa` names a file in several homes), and whether the protected set is exactly this roster or a subset/superset of it. This is the one decision this spec cannot make from the code. _(Resolved in shape by "Name patterns" below, issue #1155; the exact roster membership remains the operator's.)_
- **Withdrawn from human confirmation (issue #1159):** the **cleanup authorization signal**. That question no longer needs an answer — there is no boundary-recognized authorization signal, because there is no boundary-recognized cleanup route. Ordinary backups are removable by ordinary filesystem permissions in already-authorized writable locations, and protected targets are removable by no spelling at all. See the REVISION NOTE at the top.
- **Out of this spec:**
  - **Changing the broad-write meaning of global mode.** ADR-0129's second consequence is explicit: preventing every possible deletion in global mode is a mode-level decision, and it is not this spec's. Global mode keeps meaning "host real paths readable and writable below the physically protected targets" (`docs/CONTEXT.md` 全局档 already says exactly this). This spec adds the protected-target layer; it does not narrow anything else.
  - **A new no-delete fs mode.** Not proposed, not prototyped here.
  - **Re-deciding the unified shell parser.** Stages 0–4 (`specs/shell-parse-foundation.md`, `specs/substitution-hard-walls.md`, `specs/hard-wall-ast-migration.md`, ADR-0123/0124/0125) are existing decisions. This spec consumes their verdict; it does not reopen `parseForSecurity`, the six-verdict contract, the substitution matrix, or the command roster. `INTERPRETER_COMMAND_NAMES` stays what it is.
  - **Extending the destructive roster with interpreter API strings** (`os.remove`, `shutil.rmtree`, `fs.unlink`, …). Enumerating interpreter semantics is the failure mode ADR-0129 identified; a bigger string roster is the same door.
  - **The egress / credential-sentinel substitution layer** (`specs/egress-credential-sentinel.md`, ADR-0105/0107). Where that spec already masks a credential before it enters the fence, this spec's read-side control must not contradict it; where it is not enabled, this spec's protected-source control is what stands. Coordination, not re-design.
  - **New ADR work.** ADR-0129 is accepted and is the decision source.

## Error handling

### The refusal message template (new, protected-target boundary)

`unboundFenceErofsGuidance` is a **different boundary** and its text is not the template for this one. What carries over from it is the _shape_, four parts of which are already established: the typed `VIOLATION_PREFIXES.fsDenied` prefix (`src/harness/permission/prefixes.ts:26`, the SSOT the categorizer in `sandbox/violation-handling.ts` also recognizes), the EROFS-stderr trigger, the cap-and-count rendering of the attempted-path clues, and the contract that a stderr with no **fence-attributable refusal signature** returns `undefined` so the result stays byte-identical. That signature has exactly two qualifying triggers, not one: the EROFS marker above, and the bounded EBUSY case pinned in "EBUSY on an exact-file mask" below. Every other nonzero exit — EBUSY included, unless it attributes to a mask this same fence emitted — still returns `undefined`.

What does **not** carry over is the message body. The worktree text asserts a specific state ("worktree isolation is ON and this session is not yet bound…") and prescribes a specific remedy (`create_worktree`); on a protected-credential refusal both are false, and a wrong remedy is worse than no remedy because it sends the model down a path that cannot work. The new template is a distinct function alongside it, not a parameterization of it — no shared string, no shared sentence, so neither boundary's wording can drift into the other.

The template states four things, in this order:

1. the typed `[fs_denied]` prefix;
2. **the protected target class** that was refused, named from the inventory (e.g. "an SSH private key" / "a cloud credential file" / "an environment file"), never a bare path with no class — the model must learn the _category_, not just this one path;
3. that the write was refused **at the filesystem layer by the sandbox fence** (kernel EROFS), i.e. this is a boundary refusal and **not** a command-syntax judgment, and re-spelling the command will not help;
4. **that this session cannot remove this protected target at all** — stated unconditionally, with no condition attached and no route advertised. _(Revised, issue #1159: this item used to promise "the authorized route" under a cleanup signal that no longer exists. It must not mention a receipt, a claim, a cleanup window, or any other cleanup path, and must not imply that a different spelling, a different tool, or a different session state would succeed.)_

Attempted-path clues are rendered exactly as ADR-0109 does (first 5 EROFS lines, then `(+N more EROFS lines)`), reusing that formatting and not inventing a second one. _Test surface:_ a unit test beside `tests/harness/isolation/` that feeds a synthetic EROFS stderr and asserts (a) the output is `[fs_denied]`-prefixed, (b) it contains the target class and the fence-layer attribution, (c) it does **not** contain the worktree-only substrings `create_worktree` / "worktree isolation is ON" / "not yet bound to a task worktree", and (d) a stderr with no EROFS line and no fence-attributable EBUSY yields `undefined`. A second case pins that the worktree guidance is **unchanged** by this spec — the same wrong-text regression asserted from the other direction.

### EBUSY on an exact-file mask — second, bounded `[fs_denied]` trigger (issue #1157)

A protected **exact-file** entry is materialized as an exact-file `/dev/null` mask, not as a read-only bind of the file itself (`classifyProtectedEntry`, `src/harness/sandbox/bwrap.ts:409`; the mask reaches argv through `boundaryMountSegments`, `bwrap.ts:709`). On such a target an unlink is refused by the kernel with **EBUSY**, because the path is an active mountpoint — not with EROFS. A refusal there is therefore invisible to `protectedTargetErofsGuidance` (`src/harness/sandbox/protected-target-feedback.ts:101`), whose only trigger today is the EROFS marker (`EROFS_LINE_PATTERN`, `protected-target-feedback.ts:43`). Without a second trigger the model sees an unmasked `EBUSY` from the program, which reads as an ordinary host condition rather than as a boundary refusal — the same hole ADR-0109's EROFS guidance closed, reopened on the exact-file arm.

**The trigger, stated exactly.** On a nonzero exit, `[fs_denied]` guidance is emitted **only** when the EBUSY diagnostic names a path that matches an **exact-file mask actually emitted for that same fence**. Every other EBUSY, and every stderr with no fence-attributable signature, is returned byte-for-byte unchanged. The correlation is against the fence's **effective masks after final mount ordering**, and it **excludes** (a) targets that were absent on the host and therefore emitted no mask, and (b) masks superseded by an authorized override — a mask the fence did not end up applying cannot explain a refusal it did not cause.

**Three limits on what the match proves.** The correlation runs against the mask list the fence actually emitted, not against a reconstruction of what it might have meant to emit. Command-produced stderr matching a mask is a **diagnostic clue, not proof of a kernel event** — the string `EBUSY` can equally be a program's own text — and it is **not an authorization signal**: matching must never widen, narrow, or imply cleanup authority, and a matching EBUSY must not by itself relax or tighten any protected target. And the guidance is **advisory**: it explains an already-failing execution, it never relabels an unrelated execution failure as a protected-target violation, and it never substitutes for the exit status or stderr the caller already reports.

**Wording stays distinct.** The EBUSY template is a separate function from `protectedTargetErofsGuidance`, not a parameterization of it, and its wording must not reuse the EROFS template's kernel attribution — EBUSY text says the target is masked by the fence such that the file cannot be unlinked; it must not claim the kernel refused a write with EROFS, which did not happen. The two bodies share no sentence, so neither can drift into the other. The existing worktree EROFS guidance is untouched by this section.

_Test surface:_ unit tests beside the EROFS guidance surface, over synthetic stderr: (a) an EBUSY line naming a path that **is** in that fence's emitted exact-file mask set → `[fs_denied]`-prefixed guidance naming the target class and the physical boundary; (b) an EBUSY line naming a path that is **not** in that mask set (including a mask that was absent-on-host, and a mask superseded by an authorized override) → output byte-identical to today, no prefix, no guidance; (c) a mixed stderr where the EBUSY is unmatched but an EROFS line is present → EROFS guidance only, EBUSY ignored; (d) an EBUSY template that asserts no EROFS wording, pinned from both directions alongside the worktree regression pin already required above.

### Assembly-time failure: a protected target absent on the host — EXIT, fail-closed

This is the failure the inventory will actually hit, and today it is unspecified. `bwrap` **rejects a missing bind source** — a `--ro-bind` naming an absent path aborts the whole fence, taking the session down with it. That hazard is already documented in this codebase for the analogous case: `OPTIONAL_HOST_RO_PREFIXES` (`src/harness/sandbox/fs-policy.ts:26`) is existence-checked at assembly with the comment "Absent prefixes stay off argv because bwrap rejects a missing bind source." An inventory entry for `~/.aws/credentials` behaves identically on a host where the operator has no `~/.aws` at all, and unlike `/opt` there is no user to ask.

**Direction: fail-closed, and specifically _not_ crash, and specifically _not_ silently de-protect.** The three candidate directions are all wrong in different ways, so the spec picks one and names why:

- **Crash / abort the fence (rejected).** A missing `~/.gnupg` on a host that does not use GPG would deny the session its sandbox entirely. Availability must not depend on which protected targets happen to exist on this particular host — that is a crash dressed as safety.
- **Silently skip the entry (rejected — this is the real hazard).** Skipping a missing target is correct in isolation, and it becomes dangerous the moment a _present_ target's protection is what gets dropped to accommodate the skip. Fail-closed here means the surviving targets keep their protection.
- **Chosen: skip the missing bind, keep every other entry, refuse writes to the resolved protected paths that do exist, and say so.** Specifically:
  1. the assembly step existence-checks each resolved protected target and omits exactly those whose source is absent (same discipline and same reason as `optionalHostRoBindArgs`, `bwrap.ts:18`);
  2. **the omission is scoped to that one entry** — it never causes a sibling, present target to be dropped from the argv, and never shortens or reorders the ro-bind block as a whole;
  3. a target that is absent is not thereby _unprotected_ in any meaningful sense: the path does not exist, so there are no bytes to write. The guarantee is conditioned on existence, and a path that appears later is protected by the **next** fence assembly, not silently grandfathered;
  4. the **reads** of a protected target that exists still resolve to masked-value-or-nothing, and an absent target's read is an ordinary ENOENT, never a fabricated "no such credential" success;
  5. the fence **assembles and runs**; the session is not denied a sandbox.

**Diagnostic shape.** A skipped entry is a **warning, not a typed failure**, and the distinction is load-bearing. The failure direction here is "this target is not on this host", which is a normal condition for a cross-machine inventory and must not be counted as a policy violation — the same reasoning that keeps the ADR-0109 guidance on the ok-envelope stderr rather than in `categorizeResult`'s `execution_failed` counting. So: emit through the existing **warn-level diagnostic channel** on the sandbox module's logger, with a **typed warning discriminant** rather than a bare string, carrying at minimum:

```ts
interface ProtectedTargetSkippedWarning {
  readonly kind: "protected_target_absent_on_host";
  readonly target: string; // the resolved path that was not found
  readonly targetClass: string; // the inventory class, for the same reason as (2) above
  readonly remainingProtected: number; // entries still enforced — makes "one" vs "all" observable
}
```

The `remainingProtected` field exists so the "never silently de-protect a sibling" rule above is checkable from the diagnostic alone, and not only by inspecting argv. It surfaces to the operator log; it does **not** surface to the model as a per-command notice, because nothing about the model's task changed — a protected target that does not exist on this host is not the model's business, and surfacing it would be noise that trains the model to ignore the class. If, however, a target the session is actively trying to clean up turns out to be absent from the inventory, or to be protected, that **is** surfaced — as a typed refusal from the ordinary boundary-refusal path (not by this assembly-time rule, which is about an absent _inventory entry_ at fence assembly, not about an absent inventory entry discovered later). _(Revised, issue #1159: this sentence previously routed to "an authorization receipt is missing or unreadable … covered by SC7(b) and SC9". The receipt no longer exists, so those arms were deleted; the surface-to-the-model obligation is retained and now points at the boundary refusal that actually applies.)_

**Test surface:** a unit test over `createBwrapFence` argv in the style of `tests/harness/sandbox/bwrap-rebind.test.ts`, with one inventory entry pointed at a `mkdtemp`-absent path and the rest at fixture paths that do exist — asserting (a) the fence **assembles** (no throw), (b) the absent entry contributes no argv tokens, (c) every present entry's `--ro-bind` is still present and still ordered after the writable binds, and (d) the warning carries the fields above with a non-zero `remainingProtected`. Plus a real-`bwrap` case, in the same real-`bwrap` suite as SC1, where one protected target is absent from the fixture home: the fence starts, writes to the _present_ protected targets are refused with EROFS, and the write to the workspace still succeeds — i.e. "one absent entry" degrades exactly one target and nothing else.

### Name patterns: materialization at each fence assembly (issue #1155)

`ProtectedTargetRule` carries three shapes: `subtree` and `exact` hold a single resolved `bindPath`, while `name` holds a `root` plus a `ProtectedNamePattern` and **no** bind path (`src/harness/sandbox/protected-targets.ts:53`) — `protectedTargetRoBindArgs` emits only from `bindPath`, so a name rule is a rule shape and can never become a half-formed bind pair (`protected-targets.ts:69`). `seedEntries` seeds the roster's suffix arms (`*.pem`, `*.key`, `*.p12`, `.env*`, `id_rsa`, `id_ed25519`) as `name` rules rooted at the resolved `home` (`protected-targets.ts:290`). _(That seed root is what the code does today — read, not invented. The contract below revises the scan root to the workspace directory, issue #1155 scope revision, operator decision; the implementation follows the contract, and this sentence records the current tree only.)_

**The contract.** _(Second revision, issue #1155 — scan scope revised per operator decision. The first revision rooted materialization under the current user's home; that home-wide scope is withdrawn here, visibly. Walking the entire home at every fence assembly measured 4.1 s per bash call (791,575 entries on the reference machine, ~11 s cold), and the 2M-entry fail-closed bound would refuse every bash call on a larger home; narrowing the scope is the fix, and the enumerator is not — see "Exclusions are not implied" below.)_ A name pattern is **not** a mount target; it is materialized to concrete matches **under the scan scope defined below, at each fence assembly**, and each concrete match present at that moment must be represented by an effective physical target in the same fence. Materialization is per-assembly, so a file created after assembly is covered by the **next** assembly, not grandfathered in (same next-assembly rule as an absent target, above). A protected location **outside** the scan scope is out of scope for name-pattern materialization entirely: it requires an **explicit concrete target** in the inventory, because the scan scope below is the only root the pattern semantics are defined over.

**Scan scope.** The name-rule scan root is **the workspace directory resolved by the existing `resolveWorkspaceRoot`** (`src/config/workspace-root.ts:161`) — one root, shared by **both** fs modes: global mode and workspace mode materialize over the same directory, and the scan root is **never** derived from global mode's `/` writable mounts, from `HOME`, or from runtime temp directories. **No new configuration surface exists**: the root is whatever the resolver already returns; no flag, env var, or settings key widens, moves, or adds to it. The scan entry validates that the resolved root **is an existing directory** — a check `resolveWorkspaceRoot` itself does not make (`assertAbsoluteExists` verifies existence only, `workspace-root.ts:186`, and its cwd arm performs no filesystem validation at all, `:183`) — and an absent or non-directory root is a **typed fail-loud refusal at assembly** under SC7(a)'s discipline: the scan arm is never silently skipped, and the fence never assembles with the name arm missing while reporting success. What the scan is **not** for: the fixed sensitive paths (the subtree and exact seeds such as `~/.ssh`) and every explicit concrete target in the inventory are protected **directly by mounting**, exactly as before, and are **not** enumerated by the name scan — the scan exists only for the name-shape arms.

**Exclusions are not implied.** Materialization does not skip hidden directories, `node_modules`, build caches, VCS directories, or any other subtree on speed or volume grounds — `node_modules/server.pem` inside the workspace must be materialized and protected. The narrowed scan scope above is the source of speed; there is no second source, and skipping directories is not one of them. If the workspace contains a directory tree where pattern matching is too expensive to complete, that is a **limit-exhaustion** outcome below — a typed refusal — not a silent skip and not an implied exclusion. No additional scan directories are configurable: extra scan roots are **out of scope for this round** and are recorded here as a named gap, so a future round that widens the scope must do so by an explicit contract decision, not by an undocumented widening. The spec pins this contract — scope, root validation, fail-closed direction, no exclusions — and deliberately **not the enumerator**: any tool (e.g. ripgrep) is a non-contractual performance candidate, acceptable to adopt or reject only by measuring against the contract above, never as a change to it.

**Coverage floor under the narrowed scope — stated plainly, not papered over.** The scope revision is a deliberate operator trade, and its cost is named here. A name match **outside** the scan scope — `~/elsewhere/server.pem` in global mode, or any `*.pem` in the home but not in the workspace — receives **nothing physical from the name arm**: no mount is emitted for it, the fence does not protect its bytes, and neither spelling is refused at the boundary for it. That is the coverage floor this revision accepts. What remains true for such a path: the hard-wall's **text arm** still denies naming it in command text (a `rm -f ~/elsewhere/server.pem` spelling is refused by `commandContainsSensitivePath` exactly as before, `hard-walls.ts:3047` — the static arm never depended on the scan), and an **explicit concrete target** registered in the inventory still gets its mount — the escape hatch for any location the operator wants physically protected is unchanged, and adding one is the designated remedy, not a workaround. The spec does not describe this as "home-wide coverage with an implementation detail"; the earlier home-wide claim is withdrawn above, and every downstream sentence in this file that said "under the current user's home" must be read at the narrowed scope.

**Membership is not coverage.** `entryCovers` answers "does this entry govern this path", which is a different question from "is this path behind a bind" (`protected-targets.ts:174`). Concretely: `~/.ssh/id_rsa` is a legitimate _member_ of the `id_rsa` name rule, but its physical protection comes from the **`.ssh` ancestor subtree bind**, because the name rule has no single bind path of its own. A name match with no bind path **must not erase** an ancestor concrete rule's existing coverage — the ancestor's ro-bind stands on its own and the member match adds nothing to it. The inverse is equally a defect: a name match that resolves to a real, bindable file must not be left with no effective protection on the theory that "a name rule covered it". Membership is a classification; coverage is a mount fact; the two are tracked separately and never substituted for each other.

**Deterministic typed fail-closed outcomes.** Materialization can fail, and every failure is a **typed refusal at assembly** — never a crash, never a partially-materialized fence that assembles with fewer protections than the roster implies, and never a silently dropped match. Six classes:

1. **Traversal error** — a match subtree that cannot be walked (`EACCES`, `ELOOP`, or any other traversal error) is a typed refusal naming the root and the error code. Fail-closed means _refuse_, not _skip the subtree and protect the rest_: a subtree we cannot enumerate may contain matches, so "the ones we did reach" is not a complete answer.
2. **Symlink cycle** — including cycles reachable only through links whose targets leave the declared root; a cycle is `ELOOP` under (1) and is likewise refused, not resolved by a link-count heuristic or a visited-set cutoff.
3. **Symlink escape** — a match whose resolution leaves the declared root is a typed refusal, never silently clamped back inside and never followed. The declared root is the boundary of the pattern's semantics; a path outside it needs an explicit concrete target (above).
4. **Target disappearance between discovery and bind** — a match found by traversal and gone by the time the bind is emitted. This one is a **warn-level typed diagnostic** on the same channel as the absent-target warning above, reusing that discriminant's shape: the target is not on this host, protection is conditioned on existence, and **every present sibling and every ancestor concrete rule stays protected and mounted in the required order**. It is not the refusal of classes 1–3 precisely because the target provably does not exist, so there are no bytes to protect; that distinction is the reason it does not share their direction.
5. **Replacement / TOCTOU** — the bind source being swapped to a _different_ object between discovery and bind (the path still exists, but now resolves to something the roster never enumerated) is a typed refusal, never an accept-and-bind. Protection is scoped to an enumerated object identity, not to a pathname that happens to be spelled correctly.

6. **Match-count / traversal-work limit exhaustion** — hitting the configured bound on matches or on traversal work is a typed refusal naming the limit reached. This is the explicit answer to the `node_modules` pressure described above: the bound produces a **visible failure the operator can widen**, which is the opposite of an invisible exclusion that changes protection based on what happens to be installed.

_Test surface:_ _(revised with the scope above, issue #1155 — fixtures root at a fixture workspace, not a fixture home.)_ unit tests over materialization, beside the existing `createBwrapFence` argv pins: a fixture workspace containing one match per pattern shape (`*.pem`, `.env*`, `id_rsa`) asserting each appears as an effective physical target in the emitted argv; the `~/.ssh/id_rsa` case asserting the ancestor `.ssh` ro-bind is present and unaffected by the name match; explicit-concrete-target cases outside the workspace scan root; a `chmod 000` subtree asserting the typed traversal refusal; a symlink cycle and a symlink pointing outside the scan root asserting the typed refusals; a match removed between discovery and bind asserting the warn diagnostic plus surviving siblings; a swapped bind source asserting the typed refusal; a low work-limit fixture asserting the typed limit refusal and that **no** argv tokens were emitted for the truncated portion, so "refused" stays distinguishable from "silently excluded"; and the scan-entry validation cases — a workspace root that is absent and one that exists but is not a directory — each asserting the typed fail-loud refusal of the scan arm, never a silently skipped scan.

**Cross-references.** SC1 (the materialized match is refused by both spellings, and the covered set spans a name-pattern arm and an external concrete target), SC4 (the same enumeration feeds the credential read-side control), SC5 (materialization subtracts only protected targets and widens no grant; this section narrows global mode by exactly the protected layer and nothing else), SC7 (a blank, unset, or invalid scan root is a typed fail-loud, never an empty match set — under the revised scope the scan root is the workspace directory, and the entry's directory validation is what makes "invalid" observable), SC8 (the `PATH_MAX` and `ARG_MAX` bounds apply to a materialized match exactly as to a concrete target, and apply to the post-materialization argv), and SC10 (a name rule matching zero files on this host, and a match that disappears before bind, both take the warn-and-continue direction above and leave every present sibling and ancestor subtree rule emitted and ordered after the writable binds).

## Success Criteria

Each criterion is binary and names the surface that can falsify it.

1. **Same target, both spellings, both blocked.** For at least three protected targets drawn from the confirmed inventory, a denied `rm -f <target>` and an equivalent `python3 -c 'import os; os.remove("<target>")'` are **both** refused at the boundary, and the refusal is physically observable: the target's bytes on the host are unchanged after the attempt, in both cases. _Test surface:_ sandbox tests beside `tests/harness/sandbox/ssh-key-fs-modes.test.ts` and `fs-mode-workspace.test.ts` (real `bwrap`, fixture dirs generated in a `mkdtemp` scratch root, `HOME` redirected to a fixture home, the operator's real `~/.ssh` and real credential files never read or written — same discipline as that file's header). The argv shape itself is pinned by a `deepEqual` on `createBwrapFence` output in the style of `tests/harness/sandbox/bwrap-rebind.test.ts`. The hard-wall half of the pair stays pinned by the existing unit surface (`tests/harness/permission/destructive-roster-ast.test.ts`, `deny-reason-golden.test.ts`) — those pins keep passing, and none of them is deleted or weakened to make the new ones pass.

   _Resolved by "Name patterns" above:_ the inventory form question is **RESOLVED**. Name rules materialize to concrete matches under the **workspace directory resolved by `resolveWorkspaceRoot`** — one scan root shared by both fs modes, never derived from `HOME`, global mode's `/` writable mounts, or a runtime temp dir — at each assembly; locations outside that scan scope require explicit concrete targets (and see "Coverage floor" for the trade this narrows). SC1's covered set includes at least one name-pattern arm materialized from that workspace root and at least one explicit-concrete-target arm outside it, so the resolution is observable in the acceptance evidence rather than only in this text.

2. **A clean scan is never surfaced as effect-level safety.** No user-visible or model-visible string asserts or implies that a command is safe because it passed a scan. Concretely: the reason strings reachable from `hardWalls()` (`hard-walls.ts:3325`) and from `securityReviewOutcome` (`policy.ts:195`), the ask/deny copy in the permission executor, and the shell tool's result text contain no "clean" / "safe" / "passed" phrasing that is not scoped to the command's syntax. _Test surface:_ a unit test under `tests/harness/permission/` that enumerates the deny and ask reason strings for a matched and an unmatched command and asserts the vocabulary constraint; plus the existing golden table `tests/harness/permission/deny-reason-golden.test.ts` extended with the interpreter-spelling rows rather than bypassed.

3. **Ordinary backups are removable by both spellings; protected targets by neither — the rows differ by LOCATION, never by spelling.** _(Revised, issue #1159: this criterion no longer exercises any receipt, authorization signal, or cleanup route; it is restated against ordinary filesystem permissions.)_

   **(a) Ordinary backup.** A backup the agent created in a **permitted writable location** — outside every protected subtree, carrying ordinary filesystem permissions — is removed successfully by `rm -f <backup>` and by `python3 -c 'import os; os.remove("<backup>")'`, with the file gone from the host in both cases. **No fence artifact participates in the authorization of either deletion**: the protected-target layer never opened that location's parent directory, so there is nothing to check, nothing to claim, and nothing to exempt. The deletion succeeds because the session was already permitted to write there, exactly as for any other file in that directory.

   **(b) Protected target.** The same two operations against a protected target are **refused in both spellings**, and the refusal is physically observable: the protected file's bytes on the host are unchanged after each attempt. The fence's masks are not relaxed, its parent directories are not opened, and no cleanup window exists that could be raced or claimed.

   **The two rows differ only in _where the file is_ and _whether it is protected_** — never in how the removal is spelled, never in which tool performs it, and never in how many preconditions an authorization lookup requires. A model that learns `rm` succeeds therefore learns nothing about `os.remove`, and vice versa; that equivalence is the point.

   _Test surface:_ the same real-`bwrap` sandbox test file as SC1, with a per-case fresh scratch root, covering both rows in both spellings. The ordinary-backup row asserts removal succeeded **and** that no receipt, claim, cleanup-window, or authorization artifact was created or consulted. The protected-target row asserts refusal in both spellings with bytes unchanged. This criterion no longer has any receipt-specific unit assertion.

4. **Credential-source reads are blocked for shell and for an interpreter.** A direct read of a protected credential source (`test -r "$HOME/.ssh/id_ed25519"`, `cat "$HOME/.aws/credentials"`) and an interpreter-mediated read of the same source (`python3 -c 'open("...").read()'`, and a second interpreter where available) are both denied at the boundary; a secret-presence probe that is itself indirect is denied on the same footing as the direct one. The credential source's on-disk bytes are unchanged, and the real value never appears in any tool result, stderr, or violation message. _Test surface:_ the credential half of the real-`bwrap` sandbox suite (extending the fixture-key discipline of `tests/harness/sandbox/ssh-key-fs-modes.test.ts`) plus the existing leak-guard surface `tests/harness/sandbox/secrets-no-leak.test.ts` and `tests/harness/permission/secrets-guard.test.ts`, which stay green unmodified.

   _Resolved by "Name patterns" above:_ the credential-source arm is fed by the same workspace-scoped materialization — the same `resolveWorkspaceRoot` scan root and the same per-assembly enumeration as the write side — so a `*.pem` / `id_rsa` / `.env*` match present at assembly under that root is covered on the read side as well as the write side, by the same enumeration. The coverage floor is identical on both sides: a match outside the scan scope gets no read-side mask from the name arm either.

5. **Global mode's meaning is unchanged apart from the protected layer.** In global mode a write to a non-protected host path still succeeds, spelled either way; the protected-target layer is the only tightening this spec introduces, and it is a narrowing of a narrow set rather than a redefinition of the tier. _Test surface:_ a `createBwrapFence` argv regression pin — global-mode argv with no protected targets configured is byte-identical to its pre-spec shape, in the style of the existing "global 档下传入三个新 opt 仍与不传时逐字节相同（硬约束回归钉）" pin in `tests/harness/sandbox/fs-mode-workspace.test.ts`. This criterion is what keeps the spec from quietly becoming the mode-level change ADR-0129 put out of scope.

   _Pinned against "Name patterns" above:_ materialization subtracts only the materialized protected targets. It must not be implemented as a subtree-wide read-only or writable-window grant on the home to reach the matches, and it must not narrow any permitted write root; global-mode reads and writes outside the materialized targets are unchanged.

6. **The acceptance command is green.** `npm test` passes with no test deleted, skipped, or weakened by this spec, and the sandbox surface's real-`bwrap` group is either exercised (host has `bwrap`) or skipped by the existing `hasBwrap()` guard with that skip reported as `Not run` in the completion note — never claimed as passed.

### Boundary-class criteria

SC1–SC6 pin normal, denied, and both-spelling behavior. SC7, SC8, and SC10 pin the input-boundary classes the boundary must survive; SC9 is withdrawn (issue #1159) and its slot is left vacant; each live criterion is binary, names its test surface, and states the failure direction rather than only the happy one. The shared rule across all of them: **a boundary input that is empty, oversized, or unexpected never yields a crash and never yields an unguarded allow** — the two unacceptable outcomes. A typed refusal is the correct outcome for every one of them. _(The "racing" clause that used to close this list pointed at SC9's receipt-consumption race; that subject is withdrawn, and the rule it illustrated survives unchanged for every remaining input class — a race, if one is ever reintroduced under a future contract decision, must fail closed on the same terms.)_

7. **Empty input — deny / fail-closed, never a crash.** _(Revised, issue #1159: the former arm (b), "an empty or unreadable authorization receipt must be treated as no authorization", is **deleted** — there is no receipt, so there is no empty-receipt input class. Its fail-closed *intent* is preserved by arm (c).)_ (a) a protected-target entry that resolves to an **empty or blank** path (from an unset `HOME`, a config value that is `""`, or a roster entry that expands to nothing) must be rejected as a **typed fail-loud** at inventory/assembly — the same discipline as `workspaceHomeRoBindArgs` and `unboundFenceArgs` (`bwrap.ts:214`), which already throw `ToolExecutionError` on an empty `mainCheckout` rather than degrade — and must **never** be dropped, because a silently-dropped empty entry is an inventory entry that looks enforced and is not. _(b) is withdrawn; the number is retained as a visible gap, and the remaining cases are lettered (a) and (c) so the deletion is legible rather than renumbered away.)_ (c) the same fail-closed direction continues to hold for the boundary as a whole: an empty, absent, or unresolvable **target** is refused, never treated as a permissive no-op, and no removal of a protected target is ever permitted on the strength of an input this boundary could not parse. Neither case throws an untyped error, and neither is silently skipped. _Test surface:_ unit tests in `tests/harness/` asserting that each live arm produces a typed refusal (the concrete error/return shape named in "Error handling") rather than a dropped entry or an allow, with the argv asserted to contain no half-formed `--ro-bind "" ""` token pair.

8. **Oversized input — a typed refusal, never a crash and never an unguarded allow.** At or above the platform's expressible limits the boundary must refuse with a **typed error**, not truncate, not pass through, and not crash. Two shapes: (a) a **path** at or over the host's `PATH_MAX` (typically 4096 bytes) — an over-long protected-target path that `existsSync`/resolution cannot express must be refused at inventory/assembly with a typed error, never partially resolved to a truncated prefix that happens to exist and is then protected under a name the model never saw (a truncation to a _real, different_ path is worse than a refusal: it looks enforced and protects the wrong thing); (b) an **argv** that exceeds what the mount layer can express — `E2BIG` territory once the protected-target ro-bind block plus the command and its arguments exceed the kernel `ARG_MAX` — must be detected before spawn and refused with a typed error naming the overflow, never handed to `spawn` to fail opaquely. The refusal in both cases is a typed refusal surfaced through the same channel as the SC1 boundary refusal: the fence does not assemble in a weakened form and the session does not run **unguarded** in either case. _Test surface:_ unit tests in `tests/harness/sandbox/` feeding a synthetic over-long path and a synthetic argv-length overflow to the assembly/validation entry point and asserting a typed error (not a truncation, not a spawn); plus a `deepEqual` argv pin asserting that the over-long case emits **no** argv tokens at all, so "the entry was dropped" is distinguishable from "the entry was refused". _Name-pattern arm:_ the platform `PATH_MAX` bound applies to a **materialized match** exactly as it applies to a concrete target — a match whose resolved path cannot be expressed is a typed refusal, never truncated to a prefix that happens to exist and then protected under a name the model never saw; and the `ARG_MAX` half applies to the post-materialization argv, so materialization is the step that must detect the overflow before spawn.

9. **WITHDRAWN — concurrent receipt consumption (issue #1159). The number is intentionally left vacant and the surrounding criteria are NOT renumbered.** The subject of this criterion no longer exists: there is no receipt, so there is no consumption race, no exactly-one-winner invariant to uphold, and no consumed/half-consumed state to make atomic. Concurrent removal of an _ordinary_ backup remains a question of **ordinary filesystem semantics** (the kernel's own `unlink` behavior on a name two processes race to remove), which this spec deliberately does not redefine — inventing a fence-level arbitration for a file the fence never touched would reintroduce exactly the mechanism being withdrawn. This slot is reserved rather than closed: reinstating any cleanup authorization mechanism requires an explicit contract decision (per issue #1163, the real-kernel evidence) and would claim a criterion number here.

10. **A protected target absent on the host at assembly time — fail-closed, fence still assembles.** A protected target in the inventory that does not exist on this host must not take the session down and must not silently drop protection for the targets that **are** present. The direction and its full rationale are pinned in "Error handling → Assembly-time failure" above; in brief: the fence **assembles and runs**, the missing bind is **omitted** (bwrap rejects a missing bind source), every other inventory entry's ro-bind is **still emitted and still ordered after the writable binds**, writes to the resolved protected paths that **do** exist are still refused with EROFS, an ordinary write to the workspace still succeeds, and a **typed warning diagnostic** naming the skipped entry is emitted on the warn channel (not as a counted failure, not surfaced to the model as per-command noise). _Test surface:_ the two named in "Error handling" — a `createBwrapFence` argv unit test (mixed present/absent inventory, asserting assembly succeeds, the absent entry contributes no tokens, siblings survive intact) and a real-`bwrap` case in the SC1 suite (one fixture protected target absent from the fixture home). Because this is a `bwrap`-rejects-a-missing-source hazard, the real-`bwrap` half is the load-bearing one; the argv unit test is the cheap regression pin around it, and both are required.

### System read-only targets stay read-only (issue #1158 — authorization half withdrawn, issue #1159)

System read-only targets — the `READ_ONLY_SYSTEM_PATHS` roster and the `system_readonly_tree` class that `seedEntries` derives from it (`src/harness/sandbox/protected-targets.ts:290`; the source list is `src/harness/sandbox/fs-policy.ts:12`) — stay read-only. That part is unchanged and is not reopened here. It remains part of the inventory/mount description above: a `system_readonly_tree` entry is a physical `--ro-bind` that no spelling relaxes.

**What is withdrawn (issue #1159).** The original #1158 contract concerned _unspendable_ cleanup authorization: whether a system read-only target should receive a receipt it could never spend, how issuance eligibility and cleanup eligibility would agree on **observable spendability**, and how a stale pending receipt would be reported. **Every one of those questions is dissolved by the withdrawal of the receipt mechanism** — there is no receipt to issue, none to spend, and no spendability distinction to report. That whole subsection is deleted, and with it the `AgentBackupReceipt` / `authorizeCleanup` / `claimCleanup` / `cleanupState` analysis at `src/harness/sandbox/backup-receipts.ts:53`, `:122`, `:183`, `:276`. Reinstatement would require the explicit contract decision named in the REVISION NOTE (issue #1163 evidence).

**What survives unchanged — and is explicitly re-asserted here.** No system read-only mount is altered, relaxed, moved, or made writable; **no path is ever opened or unwrapped to make a deletion succeed**; and the read-only tier keeps its existing argv shape. Nor does any of this narrow global mode: the protected layer itself is unchanged, so **SC5 holds as written**, and SC3's protected-target row holds as written. The feedback for an attempted write or removal at such a target is the ordinary `[fs_denied]` boundary refusal, which — per "Error handling" item 4 — states that the session cannot remove it at all rather than naming a route that does not exist.

_Test surface:_ the `createBwrapFence` argv pin asserting that system read-only targets' mount shape is unchanged, plus SC1/SC3's protected-target rows. The former issuance-eligibility and cleanup-eligibility tests are deleted with the mechanism; **no test is deleted to make a build pass** — their subject was removed by an operator decision (issue #1159), not by weakening.

## Open Questions

1. **The exact protected-target inventory.** — **RESOLVED (issue #1155, scope revised per operator decision).** The decision is recorded in "Name patterns: materialization at each fence assembly": the `SENSITIVE_PATH_FRAGMENTS` suffix arms stay **name rules**, materialized to concrete matches **under the workspace directory resolved by `resolveWorkspaceRoot`** — one scan root shared by both fs modes — at each fence assembly; protected locations outside that scan scope require an **explicit concrete target**. The question this answers was whether `id_rsa` / `id_ed25519` — bare basenames the hard-wall matches anywhere in command text — are meant to protect every path ending in those names anywhere on the host: **no**, only matches under the resolved workspace directory, plus any external location the operator registers as an explicit concrete target. The second revision narrowed the first revision's home-wide root to the workspace (see "Coverage floor under the narrowed scope" for what that trade costs and what still stands). A suffix-shape fragment and a path-shape mount target are different objects; the inventory now names which is which. This discharged the blocking relationship the question carried over the mount layer, the credential read-side control, and SC4 — and through the mount layer, SC1, SC5, SC8, and SC10 — all of which are now implementable. SC2, SC7(a), and the `[fs_denied]` message-template scaffolding were never blocked by it.
2. ~~**The cleanup authorization signal.**~~ — **RESOLVED BY WITHDRAWAL (issue #1159). Not decided — removed.** The question asked _by what mechanism the boundary recognizes an agent-created backup as removable_. That question was about choosing among candidate signal shapes (a session-owned receipt directory, a manifest the agent registers into, a path-shape rule), and it is **moot**: a real-`bwrap` feasibility run showed the mechanism class cannot function on a real kernel (issue #1163 — `--bind <path> <path>` makes the path a mount point, `unlink` on a mount point returns `EBUSY`), and the operator withdrew the route rather than pick a different signal. The answer is therefore not "shape X" but: **there is no boundary-side authorization signal.** Ordinary backups are removable by ordinary filesystem permissions in already-authorized writable locations, where the protected-target layer was never involved; protected targets are removable by no spelling. Its downstream consequences were discharged the same way, not carried forward: **SC3 was restated** against ordinary filesystem permissions, **SC7(b) was deleted** (no receipt, no empty-receipt input class), and **SC9 was withdrawn** (no receipt, no consumption race). Nothing in this spec blocks implementation on this question any longer, and nothing may reintroduce it without an explicit contract decision backed by real-kernel evidence.

## Inherits / Changes

- **ADR-0129 (primary, quoted):** "Keep the hard-wall as a pre-execution guardrail whose matched denies remain non-overridable, without treating a clean scan as proof that an action is safe. Paths and credential sources that must remain protected across languages require enforcement at the filesystem, process, or controlled-capability boundary; legitimate cleanup of an agent-created backup should be allowed when its target is authorized, regardless of the command spelling." Its consequences are adopted in full: identify protected targets and allowed write roots; test equivalent shell, Python, and other interpreter operations against the same target; shell parsing tests alone cannot satisfy the acceptance point; a global-mode operator's broad host-write capability stays broad subject to the physical protected-path boundary.
- **ADR-0068 (clarified, not changed):** "The hard-wall does only pre-spawn intent filtering: intents the fence cannot see or cannot stop (destructive argv against the writable root, command substitution, sensitive paths, fork bombs)." That sentence is the statement this spec operationalizes rather than contradicts. The layer split is unchanged — the hard-wall remains a pre-spawn intent filter, **not a second sandbox**; the interpreter-independent protection lands in the sandbox, which is where ADR-0068 already located physical enforcement. The ADR-0068 clause that an AST "is a different door, out of scope for this ADR" remains retired by ADR-0123 and is not revived here. This spec **clarifies** ADR-0068 by naming which intents are known to fall outside the fence's view and what covers them instead; it changes no ADR-0068 ruling, no roster, and no verdict.
- **ADR-0092 (unchanged, named):** "The default is the global mode: real host paths are readable and writable; write interception relies on the permission layer + hard-wall; home is not hidden." The protected-target layer is a _subtraction_ from the writable set, exactly the shape ADR-0092's workspace tier already subtracts with `--ro-bind <home> <home>`, and the argv ordering discipline is that tier's (`workspaceMountArgs` / `unboundFenceArgs` last-mount-wins placement, ro-bind after the writable binds, before `--proc` / `--dev-bind`). Global mode's meaning is preserved byte-for-byte apart from the protected layer — see SC5.
- **Inherited unchanged:** ADR-0123/0124/0125 (parse foundation, six-verdict contract, substitution matrix) and their stage specs; ADR-0107/0105 (egress seam and credential sentinel — coordination only); ADR-0109 (unbound-fence `--ro-bind` + `[fs_denied]` EROFS feedback — the _shape_ this spec's boundary refusal follows; its message **text** stays with the worktree boundary, see "Error handling"); ADR-0119 (yolo retires the fence wholesale; the protected layer is inside that fence and therefore inherits yolo's exemption posture, and a spec that claimed otherwise would contradict the yolo exemption).
- **Ticket:** `docs/wayfinder/tickets/hsr-2-command-protection.md`, status `closed`, resolution accepted by the operator. Its acceptance points are carried here as SC1/SC2/SC3/SC5 and the Open Questions; SC7–SC10 are this spec's own boundary-class additions on top of the ticket's points, not ticket-derived. _(Revised, issue #1159: OQ2 is resolved by withdrawal rather than by decision, and SC9 is withdrawn, so "SC7–SC10" here denotes a number range with one vacant slot, not ten live criteria.)_
