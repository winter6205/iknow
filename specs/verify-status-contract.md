# Spec: verify-status-contract — three honest completion outcomes + upstream verify gate + pipeline-tail stopgap

> Input = wayfinder ticket `docs/wayfinder/tickets/hsr-3-completion-evidence.md` (decision recorded, status `closed`) and the stopgap clause of `docs/wayfinder/tickets/hsr-6-pipeline-exit-code.md` (status `open`; the pipefail root-cause is explicitly deferred out of this slice).
> Basis = ADR-0073 (claim window + HITL not bounced back by a checker CONTRADICTED); `docs/guides/prompt-development.md` (golden-set roster rule).
> Operator-approved assumptions below are **locked** — implementation does not re-open them.

> **Delivery shape — one capability, one PR.** This is a single cohesive capability: _honest verify status_. The build bullets below are **sequenced steps of one coordinated commit series in one PR**, ordered **outcome vocabulary + presentation → gate → stopgap**, not three independent tasks. The seam between steps is mechanical (a widened union propagating to typed consumers), and every step is inert until the vocabulary step lands, so splitting them into separate PRs would produce intermediate commits that typecheck only against a half-migrated union. The **"Ordering within the PR"** note under Success Criteria pins the sequence, and the exhaustive consumer list in "Changes — the outcome vocabulary" is the answer to "which files does the union change touch" — not a license to ship them apart. Each step is separately reviewable at its own commit; the capability is not.

## Objective

The completion system must stop reporting one outcome where it has three facts, and must stop running at all on turns that never asked to be verified.

Today the wire has four outcome values (`passed` / `failed` / `unstable` / `escalated`, `src/session-api/contract.ts:196-199`) and a **hiding hack**: the loop persists `final_outcome=passed` next to `evidence_verdict=EVIDENCE_INSUFFICIENT` and `reason=hitl_skip_completion_judge`, and `projectVerifyHumanView` (`src/session-api/verify-human-view.ts:33-35`) drops the whole field by returning `undefined`. Conversation `aa6c2a69-6c5d-4caa-978b-e93d5a2f697b` carries three such records — a label that is a lie, filtered by an absence. In the same transcript, `npm test 2>&1 | tail -5` exits 0 with a green summary line, because the sandbox runs bare `bash -c` with no `set -o pipefail` (`src/harness/aci/tools/bash.ts`, `src/harness/verify/sandbox-run.ts`), so `computeVerdict` (`src/harness/verify/evidence-checker.ts`) reads the pipeline tail's exit 0 as the suite's own and returns `EVIDENCE_SUFFICIENT` for a failed suite.

**User**: iknow is single-user and local; the TUI is the main acceptance surface. A human reading the banner must be able to tell "verified green" from "nobody checked" without knowing the record schema — and a model reading an envelope must not be told it passed when nothing ran.

**What to build**:

1. **`not_run` as a first-class outcome.** Add `"not_run"` to `VerifyAnswerView.outcome` and to `VerifyLoopOutcome`, carried on the wire by the optional `notRunReason: "insufficient" | "contradicted"` discriminator so the two locked strings stay distinguishable. The HITL-skip-after-INSUFFICIENT/CONTRADICTED shape (`src/harness/verify/verify-loop.ts:1190-1200`) stops being `passed`-plus-hiding and becomes an honest `not_run`. The success case is **not** returned to the model — the model already knows its own command exited 0; only the not-verified case is injected ("not verified, consider running tests").
2. **An upstream content gate.** Verification triggers IFF (a test command was run) ∨ (a non-doc source file was edited). The presence of `verify.command` config alone does NOT open the gate. Pure chit-chat never enters the verify subsystem: zero `VerificationRecord`, zero wire `verify` field, zero model injection.
3. **A pipeline-tail stopgap.** `| tail` / `| head` join `SWALLOWED_PATTERNS` (`src/harness/verify/evidence-checker.ts:148-153`), so masked evidence is voided to INSUFFICIENT instead of yielding a false pass.

**Success shape**: three honest outcomes (`passed` / `not_run` / the failed family), zero verify artifacts on non-code turns, and a `npm test | tail` that can never read green. The `not_run` copy is locked (Open Question 1); the only question still open at authoring time was the model-facing injection _shape_ (Open Question 2), which did not gate the vocabulary, the gate, or the stopgap — and which the shipped envelope has since closed.

## Boundaries

- **Does**:
  - Add `not_run` to the `VerifyAnswerView.outcome` union (`src/session-api/contract.ts`) **and** to `VerifyLoopOutcome` (`src/harness/verify/verify-loop.ts:247`), so the loop's terminal vocabulary carries it rather than only the wire projection. This **replaces** the `projectVerifyHumanView`-returns-`undefined` hack as the only way that shape becomes invisible — the projection now _emits_ `not_run`.
  - **Discriminator (locked, Q-A).** `not_run` on the wire is two distinguishable states, not one. `VerifyAnswerView` gains an optional field carrying the insufficiency kind:
    ```ts
    interface VerifyAnswerView {
      readonly outcome:
        "failed" | "unstable" | "escalated" | "passed" | "not_run";
      readonly rounds: number;
      /** Present iff outcome === "not_run". Carries which locked copy to render. */
      readonly notRunReason?: "insufficient" | "contradicted";
    }
    ```
    Field name is pinned here as `notRunReason`; it is optional and absent for every other outcome, so it is byte-invisible on the four existing outcomes. `projectVerifyHumanView` derives it from the same terminal record it already reads (`reason === REASON_HITL_SKIP_COMPLETION_JUDGE` ∧ `evidenceVerdict`): `EVIDENCE_INSUFFICIENT → "insufficient"`, `EVIDENCE_CONTRADICTED → "contradicted"`. The two values must **never** be collapsed onto a single string — 「未验证（证据不足）」 and 「未验证（证据冲突）」 are different facts and the human must be able to tell them apart.
  - Make `projectVerifyHumanView` (`src/session-api/verify-human-view.ts`) map the legacy and new HITL-skip shapes to `not_run` + `notRunReason` on the wire, and keep the failed family unchanged.
  - Update both presentation dispatchers to read the discriminator rather than keying on `outcome` alone:
    - `verifyFromWire` (`src/tui/verify-banner.tsx:95`) accepts `"not_run"` in its outcome allowlist **and** validates `notRunReason`: for `outcome === "not_run"` an absent or non-`insufficient|contradicted` value is `malformed_view`; for any other outcome a _present_ `notRunReason` is also `malformed_view` (the two are coupled on the wire). Returns `{kind: "ok", verify: {outcome, rounds, notRunReason?}}`.
    - `formatVerifyReport` / `formatChatVerifyReport` (`src/cli/format.ts:265-297`) take the reason and emit the matching label; both signatures widen from `outcome: string` to an options object carrying `notRunReason?`, so the reason is threaded rather than re-derived.
    - `VERIFY_OUTCOME_PRESENTATION` (`src/tui/verify-banner.tsx:74+`) gains the two `not_run` rows — glyph `⚠` (shared with `unstable`), `fg: tuiPalette.running` (amber, shared with `unstable`).
  - Add the upstream content gate **at the evidence pre-stage inside `runVerifyLoopBody`** (`src/harness/verify/verify-loop.ts:931`, immediately before `checkEvidence`), not at the `runVerifyLoop` entry. See "The gate seam" below for why, and for who supplies the messages.
  - Add `| tail` / `| head` to `SWALLOWED_PATTERNS` in `src/harness/verify/evidence-checker.ts` so pipeline-masked evidence is voided to `EVIDENCE_INSUFFICIENT`.
  - Build the trajectory golden set for the three-value outcome (offline fixtures + real-model half), and register it in the roster table of `docs/guides/prompt-development.md`.
- **The gate seam (settled).** The gate needs the _turn's_ message array — the test-run and edit evidence it reads. `VerifyLoopOptions` has no such field and cannot grow one usefully: the prior-turn messages are already supplied to `runFn` by the **caller** (`src/session-api/hub.ts:2188` and `src/cli/chat-session.ts:1586` both compute `priorMessages` and fall back to it when `runFn` is called without one), so widening the option surface would duplicate a value that lives one layer up and would make the loop responsible for a message array it does not own. Instead:
  - The predicate is a **pure function over the message array**, living in the verify bounded context beside the checker — `shouldTriggerVerify({ messages })` in `src/harness/verify/evidence-checker.ts` (the only module that already owns the message walker, `isTestCommand`, and `isDocOnlyPath`; the gate reuses all three rather than re-implementing a second message scan).
  - It is **invoked with the post-run messages**: after round 1's `runFn` returns `current.result.messages`, at the top of the loop body, immediately before `checkEvidence({ messages: current.result.messages, claimIndex: ... })` (`src/harness/verify/verify-loop.ts:931`). `current.result.messages` is the full turn-plus-history array the checker already receives, so **the wiring needs no new option and no new caller plumbing** — the seam is exactly the argument `checkEvidence` is already given.
  - A non-triggering turn returns immediately with the transparent no-op result — `enabled: false`, `outcome: "disabled"`, `rounds: 0`, `records: []` — via the same `buildResult` (`src/harness/verify/verify-loop.ts:708`) the existing `disabled` path uses, so it is byte-identical to a `verifyConfig`-absent bare run, which is the discipline already in `runVerifyLoopBody`. Because round 1's `runFn` has already run, `result` is the model's real output; only the verify bookkeeping (`rounds` / `enabled` / `outcome` / `records`) is the no-op shape.
  - This placement is also the only one that is correct for the loop's round-2+ iterations: the predicate is re-evaluated against the current round's messages on every pass, so an edit that appears in round 2 is seen.
- **Confirms with human**:
  - **Nothing outstanding on the copy.** The `not_run` TUI / CLI copy is **locked** (Open Question 1): 「未验证（证据不足）」and 「未验证（证据冲突）」on amber (`tuiPalette.running`, matching the existing `unstable` amber), not on red (red means a verified failure) and not on green. It is repeated here only so the Boundaries and the Open Questions do not drift; the Open Questions entry is the SSOT.
  - Whether `not_run` is model-facing as a **distinct envelope** (a new `inject.ts` template, e.g. "你声称完成，但没有真实测试证据 — 建议先跑 <命令> 并展示通过摘要") or only a human projection that the model never sees. The ticket's confirmed assumption is that the **not-run case is injected** and the success case is not; the _shape_ of that injection is unconfirmed. See Open Question 2.
- **Out of this spec**:
  - **The pipefail root-cause** (`docs/wayfinder/tickets/hsr-6-pipeline-exit-code.md`): changing sandbox execution semantics to `set -o pipefail`, or a structured per-stage pipeline result schema. This spec only voids the evidence; it does not make `| tail` report the real exit code. hsr-6 stays open.
  - Any change to the `verify.command` **sandbox path** (`makeDefaultRunVerify` / `sandbox-run.ts` / the command correction loop) — its tests must stay green unchanged.
  - Migrating old `VerificationRecord`s. Records written by earlier versions keep `final_outcome=passed` + `hitl_skip_completion_judge`; the **projection** maps that legacy shape to `not_run` at read time, so historic sessions render honestly without a data migration.
  - Tracking in-bash file mutation (`sed -i`, `echo >`) as code edits — a known v1 limitation already documented at `src/harness/verify/evidence-checker.ts:199-203`; the gate inherits it unchanged.
  - Goal mode (`completionMode: "auto"`) _judging_ semantics: CONTRADICTED still hard-vetoes there (ADR-0073 rule 2), and the gate does not weaken the goal feature's defense against "delete tests to fake green". **`not_run` does join `VerifyLoopOutcome`, so the two exhaustive goal-mode consumers must be pinned — that mapping is settled here, not deferred** (Q-B):
    - **`OUTCOME_TO_STATUS` (`src/session-api/hub.ts:550`)** is a `Record<VerifyLoopOutcome, GoalStatus | undefined>` and is therefore **type-incomplete** the moment `not_run` joins the union. `not_run` maps to **`"active"`** — the same non-achieved, non-aborted status `failed` and `unstable` use. It must never map to `"achieved"`, and it must not map to `undefined` either: `"active"` is the target that `applyTransition` sees as a self-transition no-op on an already-active goal (so the stored status is unchanged, which is the desired conservative result), while `recordGoal` still fires for the trace record. Either way the observable is the same and the criterion asserts the observable: a `not_run` turn leaves the goal `active`, never `achieved`.
    - **`earlyStopDecision` (`src/session-api/goal-auto.ts:170-197`)** is a chain of `if`s that **falls through to `undefined` when nothing matches**, so an unlisted `not_run` does not error — it silently re-joins the normal streak computation. That is the mis-branch this spec must not leave open: an unlisted `not_run` would be indistinguishable from a turn with no verify outcome at all. `not_run` must be handled **explicitly**: same shape as `"aborted"` / `"escalated"` on goal-clearing and the streak, but deliberately **one way different** — the `aborted`/`escalated` arm passes `continueAuto: false` (stop the auto loop, keep the goal), whereas a `not_run` turn must keep the loop running: `return makeResponse(true, false, autoTurnsRan, input.idleCompletedStreak)` — i.e. **continue the loop, do not clear the goal, and do not reset the idle streak**. The turn is not a success, but `not_run` is not evidence of a hard failure either, so it must not fire a `clearGoal` early stop. The idle streak is passed through unchanged (not reset to 0) so a `not_run` turn does not launder a near-threshold idle streak into a stop on the following turn.
    - Net effect for goal mode: a `not_run` turn **continues the auto loop**, leaves the goal `active`, and the goal can still be achieved by a later turn that actually verifies.

## Success Criteria

Each criterion is binary and names its test surface.

1. **`not_run` is accepted end to end.** `VerifyAnswerView.outcome` typechecks with `"not_run"`, and `verifyFromWire` (`src/tui/verify-banner.tsx:95`) accepts it as `{kind: "ok"}` rather than degrading to `unavailable`. Test: `tests/tui/verify-banner.test.ts` (wire-shape cases), `npm run typecheck`.
2. **The two `not_run` variants render distinctly, and the discriminator is validated in both directions.** `projectVerifyHumanView` on a HITL-skip + `EVIDENCE_INSUFFICIENT` record emits `{outcome: "not_run", notRunReason: "insufficient"}`; on HITL-skip + `EVIDENCE_CONTRADICTED` it emits `{outcome: "not_run", notRunReason: "contradicted"}`. The two render to the two **different** strings 「未验证（证据不足）」 and 「未验证（证据冲突）」 — an assertion that the two rendered strings are not equal is part of the case, so a future collapse to one string fails loudly. `verifyFromWire` returns `unavailable`/`malformed_view` for `{outcome: "not_run"}` **without** `notRunReason`, and for `{outcome: "not_run", notRunReason: "garbage"}`, and for `{outcome: "passed", notRunReason: "insufficient"}` (a present reason on a non-`not_run` outcome is malformed). Test: `tests/tui/verify-banner.test.ts` (both the render-distinctness case and the three malformed-wire cases), `tests/cli/format.test.ts` (the two `formatVerifyReport` strings differ).
3. **HITL skip after INSUFFICIENT / CONTRADICTED projects `not_run`, not a hidden `undefined`.** `projectVerifyHumanView({outcome: <loop outcome>, records: [{reason: REASON_HITL_SKIP_COMPLETION_JUDGE, evidenceVerdict: "EVIDENCE_INSUFFICIENT"}]})` returns an object carrying `not_run`; the banner renders exactly 1 amber line and the line is not 「验证通过」. The pre-existing assertions that assert `undefined` / `{kind: "none"}` are updated (replaced by a strictly stronger assertion, never weakened or deleted). Test: `tests/tui/verify-banner.test.ts:480+`, `tests/cli/format.test.ts:760+`, `tests/harness/verify/hitl-completion-module.test.ts:249/281/309`.
4. **Legacy records project to `not_run` without migration.** A record array with `final_outcome=passed` + `hitl_skip_completion_judge` + `EVIDENCE_INSUFFICIENT` (the exact shape in conversation `aa6c2a69…`) projects `not_run`; the SUFFICIENT short-circuit still projects `passed`. Test: `tests/cli/format.test.ts` (the "HITL SUFFICIENT 短路（无 skip+INSUFFICIENT）→ 仍 passed" case stays green) plus a new legacy-shape case.
5. **Both goal-mode consumers are exhaustive over the new union (Q-B).** `npm run typecheck` passes, which is only possible because `OUTCOME_TO_STATUS` (`src/session-api/hub.ts:550`) gained a `not_run` arm mapping to `"active"` — asserted directly against the real hub write-back path, not just by compilation: a `not_run` turn with a user-pinned active goal leaves the persisted `goal.status` `"active"` and never `"achieved"` (and still writes its `recordGoal` trace line, matching the `failed` / `unstable` arms). `earlyStopDecision` gained an explicit `not_run` arm, asserted through the exported `decideAutoGoalAfterTurn` entry: on a `not_run` turn with `idleCompletedStreak: 2` and no error/impossible signal, the decision is `continueAuto: true`, `clearGoal: false`, and `idleCompletedStreak` returned **unchanged at 2** — not reset to 0, and not an early stop. This is the criterion that fails if `not_run` were merely left unlisted and fell through to the streak computation. Test: `tests/session-api/goal-status-writeback.test.ts` (the `OUTCOME_TO_STATUS` arm, using its existing user-pinned-goal fixture) and `tests/session-api/goal-auto.test.ts` (the `earlyStopDecision` arm), plus `npm run typecheck`.
6. **The gate is evaluated on the post-run messages at the loop body's pre-stage, not at `runVerifyLoop` entry.** A test asserts the seam: a chit-chat turn reaching `runVerifyLoop` **does** execute round 1's `runFn` (so the post-run message array exists) and only then returns the transparent `disabled` result — i.e. the loop's `runFn` is observed to be called exactly once for a non-triggering turn, and the result is byte-identical to a `verifyConfig`-absent bare run. Test: `tests/harness/verify/verify-loop.test.ts`.
7. **The gate predicate is fail-closed on malformed input.** `shouldTriggerVerify` does not throw on any of: a non-object message, a non-array `content`, a `null`/non-string `filePath` on an `edit_file`/`write_file` block, and a `bash` block whose `input.command` is missing or not a string. Each resolves to **"no usable signal" → does not open the gate** (a malformed edit or test signal must never be read as a positive trigger, and an unparseable turn must never enter the verify subsystem). The predicate reuses the existing defensive shapes in the same module rather than re-implementing a second message walker:
   - the `!message || typeof message !== "object"` / `!Array.isArray(content)` / `!block || typeof block !== "object"` guards of `hasStaleEdit` (`src/harness/verify/evidence-checker.ts:204-215`) and `extractTestRuns` (`:253-266`);
   - `isDocOnlyPath(filePath: unknown)` (`:193-196`) — already typed to take `unknown` and already returning `false` for a non-string, so an unparseable `filePath` is _not_ a code edit;
   - `extractCommand(input: unknown)` (`:89-95`) — already returns `""` for a missing/non-string `command`, and `isTestCommand("")` is `false`, so a malformed bash block contributes no test signal.

   Test: `tests/harness/verify/evidence-checker/fail-closed.test.ts` (the natural home — the file already carries the "畸形 message → 不 crash" family) plus the `_fixtures.ts` builders.

8. **Pure chit-chat produces nothing.** A turn with no test command and no `edit_file`/`write_file` yields `records: []`, no `verify` key on the turn DTO, and no injected envelope — **even when `verify.command` is configured**. Test: `tests/harness/verify/verify-loop.test.ts` (loop-level, asserting the result is byte-identical to the `disabled` path) and a hub-level case in `tests/harness/verify/hitl-completion-module.test.ts` asserting `projectVerifyHumanView` output is absent.
9. **Non-doc edit with no test run yields `not_run` with an insufficiency reason, never `passed`.** `edit_file` on `src/foo.ts` with zero test runs → the gate opens, the checker returns `EVIDENCE_INSUFFICIENT`, and the loop's terminal outcome for that turn is `not_run` (not `passed`), with `notRunReason: "insufficient"` on the wire. Test: `tests/harness/verify/evidence-checker/fail-closed.test.ts` (or a new case in `tests/harness/verify/verify-loop.test.ts`).
10. **A doc-only edit does not count as a code edit.** `write_file` targeting `README.md`, `notes.txt`, and `docs/x.md` is treated as chit-chat: no trigger, no record, no projection — the same observable result as criterion 8. `isDocOnlyPath` (`src/harness/verify/evidence-checker.ts:193-196`) is the SSOT and is reused, not re-implemented. Test: a new case in `tests/harness/verify/evidence-checker/` (the `three-guards.test.ts` family is the natural home).
11. **Pipeline-tail evidence is voided.** `npm test 2>&1 | tail -5` with `{code: 0}` and a vitest green summary line → `swallowed: true` → `EVIDENCE_INSUFFICIENT`, never `EVIDENCE_SUFFICIENT`. Same for `| head`. Test: new cases in `tests/harness/verify/evidence-checker/exit-code.test.ts`.
12. **The three-value outcome is decided by a golden set.** Offline half green via `npm test`, **and** the real-model half `real-llm/verify-status-contract.test.ts` run via `npm run test:real-llm`. Missing credentials are recorded as `Not run` with the reason — an offline-only green is never reported as a set green. The new file is added to `TRACKED_INCLUDE` in `vitest.real-llm.config.ts` so its existence is checkable from a clone.
13. **The upstream gate and the pipeline stopgap are unit-tested, not trajectory-tested.** Both are deterministic predicates over the message array; the roster gain is exactly one row (the 3-value outcome). No second trajectory set is created.
14. **No regression on the `verify.command` path.** `tests/harness/verify/sandbox-run.test.ts`, `command-probe.test.ts`, `verify-loop.test.ts`, `three-stage-flow.test.ts`, `workspace-mode-fence.test.ts`, and `yolo-sandbox-run.test.ts` stay green unchanged. Command: `npm test`.

**Ordering within the PR** (the delivery-shape note in the header): steps land **vocabulary + presentation (criteria 1-5) → gate (criteria 6-10) → stopgap (criterion 11)**, with the golden set (criterion 12) riding the vocabulary step since the injection it covers is a `not_run` surface. 3. ~~Does the gate also suppress the `verify.command` path?~~ — **RESOLVED, and no longer a question.** **Settled (operator decision ii): the content gate OVERRIDES `verify.command` presence.** Pure chit-chat (no test run, no non-doc edit) NEVER enters the verify subsystem, even on a project with `verify.command` configured. The gate is: **trigger IFF (test command run ∨ non-doc source edit)**. The presence of `verify.command` alone does not open the gate. This is a deliberate change from the prior "configured project verifies every turn" behavior and is pinned in Success Criterion 8. Implementation does not re-open it: no branch anywhere in this spec may treat `verify.command` as gate-opening.

## Inherits / Changes

**Inherits — ADR-0073** (`docs/adr/0073-verify-claim-window-and-hitl-contradicted.md`), unchanged:

> 3. Under HITL, when evidence is insufficient and the completion judge is skipped, the human-facing UI must not show "verification passed".

This spec satisfies rule 3 by _naming_ the state (`not_run`) instead of hiding the field, which is a strictly stronger realization of the same requirement. Rule 2 (the goal feature still hard-vetoes on CONTRADICTED) and rule 1 (`claimIndex` = the messages index) are untouched.

**Inherits — the five-condition evidence contract** (`computeVerdict`, `src/harness/verify/evidence-checker.ts:426-439`). A `passed` claim still requires all five: exit 0 ∧ green summary ∧ not weak green ∧ not swallowed ∧ no code edit in the staleness window. This spec only widens condition 4 (`not swallowed`) to cover pipeline tails; it does not relax any condition. Fail-closed holds: anything unparseable still yields `EVIDENCE_INSUFFICIENT`.

**Inherits — the verify loop shape** (`runVerifyLoop` → `runVerifyLoopBody`, `src/harness/verify/verify-loop.ts:1275` / `:864`): the loop already has a transparent, byte-identical no-op path (`enabled: false`, `outcome: "disabled"`, `records: []`). The upstream gate reuses that discipline rather than inventing a second disabled shape. It is placed at the **pre-stage inside `runVerifyLoopBody`** (`:931`, next to `checkEvidence`) rather than at the `runVerifyLoop` entry, because that is the first point where `current.result.messages` — the array the gate must read — exists; see "The gate seam" in Boundaries.

**Changes — the outcome vocabulary (exhaustive consumer list).** Two unions widen, and they widen for different reasons:

- **`VerifyLoopOutcome`** (`src/harness/verify/verify-loop.ts:247`) gains `"not_run"`. Its two consumers are both **goal-mode**, and they fail in different ways — one is type-total, one is not:
  1. `OUTCOME_TO_STATUS: Record<VerifyLoopOutcome, GoalStatus | undefined>` — `src/session-api/hub.ts:550`. This one **is** type-total: a missing `not_run` arm is a compile error, not a silent mis-branch. New arm `not_run: "active"`. Never `"achieved"`. (Q-B; criterion 5.)
  2. `earlyStopDecision` — `src/session-api/goal-auto.ts:170-197`. This one is **not** type-total — it is a chain of `if`s that falls through to `undefined` when nothing matches, so an unlisted `not_run` does not error, it silently re-joins the normal streak computation. It must therefore be upgraded **by hand** and is covered by a direct `decideAutoGoalAfterTurn` assertion, not by `typecheck`. Explicit `not_run` arm returning `makeResponse(true, false, autoTurnsRan, input.idleCompletedStreak)` — like the `aborted`/`escalated` arm it does not clear the goal and does not reset the streak, but unlike it the auto loop **continues** (`continueAuto: true`): a `not_run` turn is not evidence of a hard failure. (Q-B; criterion 5.)
- **`VerifyAnswerView["outcome"]`** (`src/session-api/contract.ts:196-199`) gains `"not_run"` plus the optional `notRunReason` discriminator. Its five consumers are all **partial** — explicit allowlists or arm chains — so a missing arm is silent: 3. `projectVerifyHumanView`'s allowlist — `src/session-api/verify-human-view.ts:26-32`. Now **emits** `not_run` (replacing the `return undefined` hiding hack) and computes `notRunReason` from the terminal record. 4. `verifyFromWire`'s explicit `!==` guards — `src/tui/verify-banner.tsx:106-112`. Accepts `"not_run"`, and cross-validates `notRunReason` in both directions (absent/on-`not_run` and present/on-other are both `malformed_view`). 5. `VERIFY_OUTCOME_PRESENTATION` — `src/tui/verify-banner.tsx:74-87`. Two `not_run` rows, amber `tuiPalette.running`, glyph `⚠`. 6. `formatVerifyReport`'s four-arm ternary — `src/cli/format.ts:280-297`. Signature widens to accept `notRunReason?`; label branches on it. 7. `formatChatVerifyReport` — `src/cli/format.ts:265-277`. Widens in lockstep with 6 and routes `not_run` into `formatVerifyReport` (it currently returns `undefined` for everything outside the failure triad).

Consumers 3-7 left un-upgraded degrade to `unavailable` (TUI), an unhandled value (CLI), or — for 3 — the _old_ hiding behavior, which is the bug this spec exists to remove. Each is covered by a named test in Success Criteria 1, 2 and 3. Consumer 1 is covered by `typecheck` plus a direct write-back assertion, and consumer 2 by a direct decision assertion — both in Success Criterion 5.

**Deferred — hsr-6.** `docs/wayfinder/tickets/hsr-6-pipeline-exit-code.md` remains open. This spec's stopgap makes a masked pipeline _unprovable_ rather than _provable-and-correct_: `| tail` evidence is voided to INSUFFICIENT, so the loop degrades to `not_run` / a correction round instead of a false pass. The exit code that actually ran is still invisible, and `grep` / `tee` / `jq`-style masks are still uncovered. hsr-6 owns the real fix (pipefail vs. structured per-stage results, both cross-module).

## 待写入 (to-persist)

New domain terms this spec introduces, for `docs/CONTEXT.md` (not persisted by this change — `arthurpower:domain-modeling` is not invoked here):

- **`not_run` outcome** — the fifth `VerifyAnswerView.outcome` value: verification was skipped or judged insufficient, the human is the authority (HITL), and no pass may be implied. Distinct from `unstable` (a suite that failed then passed) and from the absence of the `verify` field (the gate's chit-chat case). In goal mode it is conservative: goal stays `active`, the auto loop continues.
- **`notRunReason` discriminator** — the optional `VerifyAnswerView` field carrying which insufficiency produced a `not_run`: `insufficient` (「未验证（证据不足）」) or `contradicted` (「未验证（证据冲突）」). Present iff `outcome === "not_run"`; the two are coupled on the wire, so a present reason on any other outcome (or an absent reason on `not_run`) is a malformed wire view. Its purpose is to keep the two human-readable strings from collapsing onto one value at the projection boundary.
- **upstream verify gate** — the content predicate deciding whether a turn enters the verify subsystem at all: (test command run ∨ non-doc source edit). `verify.command` presence alone does NOT open the gate. A non-triggering turn is transparent (no record, no wire field, no injection), distinct from `not_run` (which means the turn _did_ enter and produced no evidence).
- **pipeline-masked evidence** — a test run whose command ends in `| tail` / `| head`, so the reported exit code is the pipeline tail's, not the test runner's. Treated as swallowed (fail-closed) in v1; the true exit code is not recovered (hsr-6).
- **doc-only edit** — an `edit_file` / `write_file` whose target is `.md` / `.txt` / under `docs/`; per the existing `isDocOnlyPath`, this is not a code edit and does not trip the gate or the staleness window.
