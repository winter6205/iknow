1. MCP 架构：Host ↔ Server 拆边界

Stage 0 + Stage 1

graphrag-memory 是独立 MCP server（graphrag-memory/ workspace），与 iknow 主项目共享 stdio transport、不共享进程。Host 端（Claude Code / 参考 Host）通过工具注册协议发现 ingest 和 retrieve，再以 JSON schema 校验输入。

Host（Claude Code / 参考 Host）
运行 MCP 客户端，按工具名 + Zod schema 调起 stdin。
tools/call → ingest
tools/call → retrieve
tools/list（注册发现）
Server：graphrag-memory
独立 workspace，不 import iknow src/，不读 _upstream_gbrain/。
src/index.ts（注册 + 统一 catch）
src/tools/ingest.ts + retrieve.ts
src/core/{chunker,cosine,embedder,storage/*}
stdio JSON-RPC → listTools : ["ingest", "retrieve", "echo"] → callTool(name, args) ← textResult(json, isError?) · 错误：GraphragError（5 codes）

关键约束：Host ↔ Server 之间是进程边界。日志走 stderr，stdout 留给 stdio transport；任何在 Server 里 import iknow 源码都会被解耦契约挡掉。

2. ingest / retrieve 流水线

写路径：把一段文本变成可检索的 chunks，并按 valid_window 落盘。5 个阶段，全部在 graphrag-memory 进程内。

Step 1 validate Zod schema：content 非空、source_ref 非空、valid_* 可选 ISO 8601 IngestInputSchema
→
Step 2 chunk 固定窗口滑动切块（默认 2048 chars / 256 overlap） chunker.ts
→
Step 3 embed EmbeddingClient.embed(chunks) → 1536 维向量 NineRouterEmbedder / FakeEmbedder
→
Step 4 store StorageBackend.upsert(chunks, embeddings) → chunk ids Memory / pgvector

读路径：把 query 投到同一向量空间，按 cosine 排序并按 valid_window 过滤。

Step 1 embed query EmbeddingClient.embed([query]) → 1536 维向量 retrieve.ts
→
Step 2 vector search cosine 排序 + valid_window 过滤 + limit（≤100） StorageBackend.search
→
Step 3 project 投影成 {id, content, source_ref, valid_window, score} RetrievedChunk
→
Step 4 wire shape textResult(JSON.stringify({ chunks })) index.ts → stdio
validate chunk embed store query rank

3. 切块：固定窗口滑动

chunker.ts

阶段 1 用无句读感知的固定窗口：chunkSize=2048 chars，overlap=256 chars，step = chunkSize - overlap。重载切片位置以避免句子内断字。

源文本（高亮 = chunk 起始 / 延续）

    默认 ≈ 512 tokens（英文文本 4 chars/token），与 text-embedding-3-small 的 8192 token 上下文预算留出余量。Overlap 让相邻 chunk 共享 256 字符上下文，召回时不会"切词"。

    4. 余弦相似度：cos(θ) = (a·b) / (‖a‖·‖b‖)

    cosine.ts

    内存模式直接遍历所有 chunks，用纯函数 cosineSimilarity(a, b) 排序。零向量当作"无信号"返回 0，避免 NaN 干扰；长度不一致抛 RangeError（调用方 bug，不是相似度 0）。

    向量 A（query 投影）

    A = embed(query)

    向量 B（候选 chunk）

    B = embed(chunk)
    cos(A, B)
    0.0000%

    示例语料：query "GraphRAG 阶段 1 怎么落盘" 的 top-K

    5. valid_window：时间切片

    SearchOptions.validAt

    每个 chunk 都有 valid_from / valid_until。检索时按 valid_at 切片： valid_from ≤ valid_at < valid_until（valid_until = null 表示"永远有效"）。

    6. Memory vs pgvector

    StorageBackend

    接口一致（upsert/search/close），实现可换。dev/test 用内存，prod 用 pgvector。两者都不感知 embedding 算法，只消费 1536 维向量。

    MemoryBackend T4 · dev / test

    结构
    Map<string, ChunkRecord>，进程内
    搜索
    暴力 cosine（O(N·D)），N = chunks，D = 1536
    过滤
    同接口，valid_window 在内存里逐条比对
    持久化
    无（重启清空）
    CI
    Vitest 集成测试默认用它
    • 零依赖、零环境
    • 上限 ≈ 万级 chunks（之后 O(N·D) 会成为瓶颈）
    • 作为接口 reference impl，方便 pgvector 对照

    PgvectorBackend T8 · prod

    数据库
    PostgreSQL 16 + pgvector ≥ 0.7
    列
    embedding vector(1536)
    距离
    <=> cosine distance（1 − cos）
    索引
    IVFFlat / HNSW（按数据量选）
    连接
    node 内置 pg，无独立 SDK
    • 持久化、跨进程、可水平扩展
    • valid_window 落在 SQL 端，可与 ANN 索引组合
    • 集成测试需本地 Postgres，CI 默认跳过
