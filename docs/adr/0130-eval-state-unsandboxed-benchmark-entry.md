# 0130. Eval state: unsandboxed headless entry for benchmark runs

Date: 2026-09-29
Status: accepted

> **AMENDED by ADR-0141 (2026-10-15).** Scoped amendment at three sites: §1's permission sentence ("eval's own, not a shared carrier") is corrected to a yolo-preset declaration; §2's `bwrap.ts` branch citations gain a rename plus stale-line-number note; §6's and §7's claims about what `--yolo` does are re-scoped — the entry enumeration and typed refusals stand, the posture content of the word changes. §2's measurement scope and §5's reporting invariant do not move. The full record is §8.

Benchmark evaluation (Terminal-Bench via Harbor) needs the agent to install packages, clone repositories and reach the network from `bash`. Our fence denies all of that by construction, because `--unshare-net` is constant. The operator has ruled that **evaluation itself has no need for the fence**, so the permission and sandbox axes opening for eval is not a trade-off to weigh but a precondition. This ADR records the shape of that opening: a distinct, named **eval state** whose runtime posture is identical to yolo's, reached headlessly — deliberately **not** by making `--yolo` legal on the non-TUI entries.

### 1. A named second exception, not a widened entry enumeration

Eval state applies yolo's **fence** state-combination exactly: `fsMode: workspace` → `global` (holders only, user-layer settings untouched), the bwrap fence retires wholesale, all four routes (foreground bash / background spawn / verify sandbox-run / subagent worker) run bare, egress seam retired. Its **permission** posture is `full_auto`, but that write is **eval's own, not a shared carrier** — see ADR-0139 §3, which re-adjudicates this section: the structural-parity guarantee covers the fence carrier and fence shape, not the permission holder, because an operator cannot answer per-call questions mid-benchmark. It is entered by an **explicit, non-default, named opt-in available to the headless entries** — never by adding `--yolo` to `chat` / `serve` / `ask` / `oneshot` / `trace`, and never as a default, a settings value, or an env var that flips silently.

> **AMENDED by ADR-0141 (2026-10-15).** This section's permission sentence is corrected, not deleted. "that write is **eval's own, not a shared carrier**" held under ADR-0139 §3; under ADR-0141 ruling 1, `--eval-state` is the **declarative application of the yolo preset** at startup, the yolo preset **includes** `full_auto` by declaration, and the entry's own write (`src/harness/sandbox/eval-state.ts:234`) is absorbed into the preset rather than standing beside it as a second carrier. What survives of ADR-0139's reading is its **drift argument** — the parity it defends against is a _fence-shape_ drift, which the shared preset definition prevents at least as well — and the operator-facing reason for the explicit write (an operator cannot answer questions mid-run); what is retired is only the "second carrier" description. The resulting posture triple — `full_auto` + `global` + fence retired — is **unchanged**, pinned by `tests/harness/sandbox/eval-state-entry.test.ts:111` (the triple itself) and `:130` (the permission posture is not a side effect of the fence). §2's measurement scope and §5's reporting invariant therefore do not move, and published eval-state numbers stay comparable with runs already published. See §8.

**Basis:** ADR-0119 §ruling 7 (`docs/adr/0119-yolo-no-sandbox-mode.md:77`) restricts the flag to the TUI, and its recorded basis is an operator lock ("only before entering the TUI"), not a security proof — the operator has now ruled otherwise for this use. But that same ADR's risk line (`docs/adr/0119-yolo-no-sandbox-mode.md:175`) says the exception kills the discipline the moment it is _copied or silently extended_ to non-TUI entries, and names the entry enumeration plus parity tests as the defense. A separate named entry honors that: the exception stays a face you can grep, log and refuse to confuse with a user session, and `--yolo` keeps its original meaning. _(**False as to the flag's content, true as to this ADR's mechanism**: `--yolo`'s meaning has since moved twice — ADR-0139 narrowed it to the fence axis, ADR-0141 re-widened it to the yolo preset — while the property this Basis relies on, that an eval run is a **separately named face** rather than a widened flag, is untouched. ADR-0141 §1 in fact leans on it the other way: eval state is named and headless, which is precisely why the preset can be applied to it **declaratively**, without an interactive controller or exit semantics.)_ The defense line moves from "five commands reject it" to "five commands reject it + the eval opt-in is named, explicit and visible".

### 2. What survives, what retires (this is the measurement scope)

**Survives:** the **hard-wall** — a matched deny is non-overridable and intercepts before `full_auto` grants anything (`src/harness/sandbox/yolo.ts:42`, `src/harness/permission/policy.ts:50`); the **which-tree axis** — writes still resolve against the live **taskRoot**; the worktree gate, which is fence-independent. _(Unchanged by ADR-0141 (2026-10-15): a preset is an axis combination, never a guardrail bypass — ADR-0141 ruling 1 cites this list as its basis for that.)_

**Retires with the fence:** workspace / global mount layers, protected-target `--ro-bind` blocks, the credential read mask, and the egress seam. Network reachability becomes the container's property, not ours.

**Route scope of the eval entry.** The retirement above is structural, but the _measurement_ claim is narrower than it first reads. The one eval entry is `surface: "ask"`, which mounts the **foreground bash route only**. The background manager and the subagent manager are gated `surface !== "ask"` (`src/harness/build-engine.ts:1260-1261` background, `:1082-1083` subagent), so `background: true` throws "no background manager configured" and `spawn_subagent` is never registered; the verify `sandbox-run` route is constructed only from `src/cli/chat-session.ts:1852` / `src/session-api/hub.ts:2898` (the two `runVerifyLoop(` call sites; their imports are `src/cli/chat-session.ts:16-17` and `src/session-api/hub.ts:30`), never from the one-shot entry. Those three routes are therefore **structurally absent** in eval state, not retired-and-observed. No number from this benchmark is evidence about background spawn, subagent or verify execution; publishing one as such is exactly the misattribution §5 exists to prevent. `EVAL_STATE_NOTICE` states this on stderr, and `tests/cli/cli-eval-state-bare-run.test.ts` asserts only the foreground route. _(Unchanged by ADR-0141 (2026-10-15): route scope and the misattribution guard stand as measured; only the carrier's spelling changes, per the §2 Basis note and §8.)_

**Basis:** yolo's own definition — bare argv, `requireBwrap` skipped at assembly, egress retires entirely (`src/harness/aci/tools/registry.ts:470-474`); ADR-0119's two-axis distinction, where the ro-bind axis rides the fence and the which-tree axis does not. The retirement is structural, not a per-item opt-out: the fence factory returns bare argv (`src/harness/sandbox/bwrap.ts:712`) **before** `boundaryMountSegments` is called (`src/harness/sandbox/bwrap.ts:741`), and that block is the only place the protected-target ro-binds and the credential mask are assembled. _(ADR-0141 (2026-10-15): structure intact, spelling renamed. The same sole early-return branch reads `fenceRetired` once `BwrapFenceOptions.yolo` (`src/harness/sandbox/bwrap.ts:215`) is renamed per ADR-0141 ruling 6; on base f8e56652 the branch and the `boundaryMountSegments` call sit at `src/harness/sandbox/bwrap.ts:724` and `:753` (ADR-0141's verified numbers) — the `:712` / `:741` cited above are stale line references, recorded as a discrepancy here rather than edited into the historical text.)_

Eval state is therefore **not** "no guardrails": the spelling-sensitive pre-execution guardrail stays armed. Expect it to fire on legitimate benchmark commands; that is a finding about the wall's false-positive rate, which is one of the few things this benchmark can tell us about our own harness.

### 3. Consequence recorded: the injected model key loses its mask

The credential read mask is a fence-layer artifact, so in eval state it is gone, and anything running in the task container can read the API key we injected. Note, not a gate: a **scoped, revocable key with a spend cap** remains a sensible precaution for real runs, because the mask that would otherwise hide it is not present.

**Basis:** the mask is emitted by the fence — `credentialReadMaskArgs` (`src/harness/sandbox/credential-read-mask.ts:387`) has exactly one consumer, `src/harness/sandbox/bwrap.ts:678`, inside the boundary block the yolo return skips — so it is exempt by construction the same way the protected ro-binds are; the **effect boundary** it belongs to has no other carrier inside a disposable task image.

**Amendment 2026-09-29 (operator ruling).** An earlier revision of this section stated the scoped-key requirement as "non-negotiable for the first real run". The operator has ruled that no such restriction applies here: the local key already carries the full test suite's traffic (`npm run test:real-llm`, 11458 tests) and carries nothing that an eval trial does not. The technical consequence recorded above — the mask is gone, the key is readable in the task container — stands unchanged; only the gate strength is revised. The requirement is now advisory, not a preflight blocker, and it is not enforced or tested anywhere in the product surface.

### 4. Rejected options

- **Keep the fence on.** `--unshare-net` has no conditional and no escape hatch (`src/harness/sandbox/bwrap.ts:542-547`, ADR-0097). Install-dependent tasks would fail for a reason unrelated to the model, and the resulting number would measure our netns policy. Misattribution is worse than measuring something wide.
- **Drive `iknow tui --yolo` over a pty.** The TUI is a terminal application; a harness needs one command and parseable output. It buys no guarantee that a named eval opt-in does not already give.
- **`full_auto` alone.** Fixes approvals, not the fence: every non-yolo bash call still runs `requireBwrap` (`src/harness/aci/tools/bash.ts:902`), and the command is wrapped regardless of fs mode.

### 5. Reporting invariant

Every number produced in eval state is published with the state named in the same artifact. An eval-state score is not evidence about the fence, and the fence is not what it measures. Naming the entry separately exists precisely so this sentence can always be written.

**Precedent worth recording:** one of the benchmark's built-in agent adapters — the one whose shape is closest to ours — runs with a fixed runtime flag that switches off both its per-command sandbox (landlock/seccomp on Linux) and its approvals; across the ~35 built-in adapters, none attempts to keep private isolation inside a task container. The container is the sandbox, so the benchmark measures the agent, not the agent's private sandbox.

**Evidence:** `src/harness/sandbox/yolo.ts:79` (the typed non-TUI refusal this ADR declines to widen); `docs/CONTEXT.md` entries 沙箱纪律, yolo mode, 全局档, hard-wall, effect boundary. Measurements 2026-09-29: Harbor 0.23.0 oracle pilot on `terminal-bench/terminal-bench-2-1` scored reward 1.0 with 0 exceptions; `IKNOW_PERMISSION_MODE=full_auto` on `ask` performed a real write; container egress to the model endpoint returned 301 without any proxy injection.

### 6. Amendment 2026-09-29: flag-combination refusal, and the `=true` / `=false` spellings

**`--resume` conflict.** `ask --resume <id> --eval-state` is refused with `eval_state_flag_conflict`; `ask --resume <id>` alone is silently ignored, because the one-shot entry mints a fresh conversation id unconditionally (`src/cli.ts:363`) and `resumeId` is consumed only by `runChat`. The asymmetry is deliberate, not an oversight: §1's fail-loud line ("carrying the flag there is a typed refusal rather than a silent ignore") is the defense ADR-0119 §ruling 7 names against a dangerous flag being quietly swallowed. Under eval state the caller is a harness, so a silently dropped argument is a misattributed run; refusing keeps the entry honest about what it can honor. A code-review pass flagged this as scope creep — no clause above required it. It is recorded here instead of removed, because dropping it would reintroduce the silent-drop the same clause forbids. Covering tests: `tests/cli/parse-args-eval-state.test.ts`, `tests/cli/cli-eval-state-non-entry-reject.test.ts`.

**`--eval-state=true` / `=false`.** Both spellings are recognized. `=true` enters the posture; `=false` is the named non-posture spelling and reports no posture requested. The alternative — leaving the literal unrecognized so it falls through into the query text — was rejected: the operator's task text would carry `--eval-state=true` to the model, which is neither what was asked nor a refusal.

**Known defect, deferred.** The posture flag is still detected by enumerating the value-taking options that must reject it (`--host`, `--trace-out`, `--data-dir`, `--workspace-root`), rather than by a rule that derives the safe behavior from the parser's own structure. This is the wrong shape: a registry that must be updated whenever a flag is added cannot be complete, and completeness is the property being asked for. It is replaced-by-design, not accepted — see the handoff for the required shape, and §7 for the shape that replaced it. `--yolo` carries the same defect and is additionally live on `ask` today: `iknow ask grep --yolo in src` flips the fence-retiring posture _and_ deletes the word from the query. _(ADR-0141 (2026-10-15): the posture `--yolo` flips is now the full yolo **preset** — fence retired, `fsMode → global`, `full_auto` — not the fence retirement alone; the defect itself and the refusal shape are unchanged (`src/cli/parse-args.ts:890-895`, `src/cli.ts:986-998`), and `--no-sandbox` joins the same refused set. See §8.)_

### 7. Amendment 2026-09-29: posture detection derives from parser consumption, not an enumeration

**The §6 deferral is RESOLVED**, and resolved the way §6 said it would be — replaced-by-design, not accepted. The paragraph above stays as the decision record; this section is what closed it.

**The invariant, in the operator's terms.** Allow only what we have implemented; everything else fails outright. Concretely, and this is the whole rule: **a token that the parser is not consuming as a flag cannot change the posture.** The discriminator is the parser's own consumption, so no flag-name registry exists to keep current, and a flag added later is correct by construction.

**Basis — the property is structural, so it needs no table.** `parseArgs`'s scan loop is a single `if/else` chain, and a token it consumes — a valueless flag matched in the chain, or a value read with `argv[++i]` — lands in neither the locals nor the positional stream. On the query-bearing path the operator's word is therefore the only thing left in the stream that is not the posture flag, so any posture spelling appearing _between_ two of the operator's words is one of their words and stays in the query, while one before the first or after the last is an option. There is no third case to enumerate. The display path is a separate stream and a separate rule — see the registry paragraph below.

**What the rule still reads a name from, disclosed.** One: `SUBCOMMAND_HEADS`. The span needs to know that positional 0 may be a subcommand head rather than an operator word, so it consults the same six-token set the dispatch chain matches on (`chat` / `serve` / `trace` / `tui` / `ask` / `help`). The claim above is therefore "no flag-name registry", not "no names at all". The distinction that matters: this is a **closed dispatch vocabulary, not an open-ended flag set** — every entry is a head the chain at the bottom of `parseArgs` must match anyway, so it is a list that is finished by construction rather than one that drifts, and the "an enumerated list is never finished" objection does not apply to it the same way. The obligation it does carry is concrete: a head added to the dispatch without a `SUBCOMMAND_HEADS` entry would shift the span. This dependency is **pre-existing** — it is the same set the old valueless-flag registry sat beside — and is recorded here rather than removed, since deduplicating it against the dispatch chain is a separate refactor this amendment does not make.

**The name registry is deleted, and what replaced it is positional, not a better list.** The valueless-flag literal set that previously participated in marking the operator-word span was doing real work, and deleting it alone was a regression. The span is computed over two different streams: the scan loop's `rest`, and — for a display path — the **raw argv**, because `-h` / `-V` return from inside the loop. Valueless flags never reach `rest`, but they _are_ present on the display path, so the registry was load-bearing there: with it removed, `-h --eval-state --json` classified `--json` as an operator word, which moved the span's end and silently downgraded the posture flag to free text. The replacement states the answer positionally instead of by recognizing flags: **a display path produces no query and no session, so it has no operator words at all** — the span question has a known answer that does not depend on what any token looks like, and a new valueless flag, or one appearing after the posture flag, cannot change it. Recognizing flags was a proxy for that answer, and a proxy is what drifts. The posture spelling remains the single source of truth, and no flag-name registry remains.

**The value-slot rule is now a function, not a list.** One `slotValue(flag, argv, index, missing)` reader throws `Invalid <flag>: <raw>` when the slot holds a posture spelling, and it is called by every value-taking branch **except one**. This is the form the required shape asked for: a rule about **slots** ("a slot expects a value, and no posture spelling is ever a legal value") rather than a rule about which flags have slots. A value-taking flag added later inherits the rule by calling it — no registry to update. `--port` / `--max-bytes` / `--max-turns` are covered by it, where before they were protected only as a side effect of their own `Number()` validation.

**The one exclusion, stated rather than smoothed over.** `--resume` is a value-taking branch that does not call `slotValue`: it reads `argv[++i]` itself and routes the token through `readResumeSlot`, which reports a posture in that slot as ADR-0130 §6's typed `eval_state_flag_conflict` rather than throwing. So the earlier phrasing — "`slotValue` is called by every value-taking branch", used to justify "no second site to forget" — over-claimed in exactly the direction that mattered: the one branch that does _not_ call it is the one branch a later change can forget. The honest form is "every value-taking branch except `--resume`, which reports instead of refusing", and the honest property is correspondingly weaker than it looked: the exclusion is a **convention the code documents** (`readResumeSlot`'s doc, ADR-0130 §6), **not something the type system enforces** — nothing makes the next author pick `slotValue` over `argv[++i]`. `tests/cli/parse-args-eval-state.test.ts` reads the source of `parseArgs` and asserts both halves — that the arms advancing the loop index are exactly the slot table plus `--resume`, and that every one of them calls `slotValue` except `--resume` — which turns the convention into a checked one without changing the parser.

**`--eval-state=false` in a value slot is refused, on purpose.** The test is on the _spelling_, so `=false` fails in a slot the same as `=true` and as the bare literal: `iknow ask --data-dir --eval-state=false <task>` → `Invalid --data-dir: --eval-state=false`. This is correct rather than an over-strict bug, and is stated so a later reader does not "fix" it into acceptance: the `=false` form is a spelling **of the posture flag** (ADR-0130 §6), not a value, and taking it as a data root would make one token mean a posture and a path simultaneously. Whether the request means "not in eval state" is the parser's call to make in a flag position; inside a value slot the only defensible reading is "that was not a value".

**One live defect fixed here, previously unrecorded.** `readResumeSlot` matched only the bare literal, so `iknow ask --resume --eval-state=true <id>` silently resumed a session whose id was the string `--eval-state=true`: no posture, and no refusal. The bare literal was correctly refused; the `=`-form was not. This is a surface behavior change, so it is stated rather than folded in: the guard is now on the spelling, so both forms take ADR-0130's existing typed `eval_state_flag_conflict` path.

**What does not change.**

- `--yolo` handling is untouched. ADR-0119 §ruling 7 is **qualified, not overturned**: `--yolo` is still a parse-time typed refusal on `chat` / `serve` / `ask` / `oneshot` / `trace`, and `iknow tui --yolo` remains the sole legal surface. _(Re-scoped in part by ADR-0141 (2026-10-15): true of the **handling** — the entry enumeration and the typed refusals stand as written (`src/cli/parse-args.ts:890-895`, dispatched at `src/cli.ts:986-998`), and `iknow tui --yolo` remains `--yolo`'s sole legal surface — but ADR-0141 changes the **content** of the word: `--yolo` now names the yolo preset, retiring the fence, declaring `global`, and setting `full_auto`, while `--no-sandbox` joins the same refused set as its own fence-only preset. The eval entry itself does not move and is still the only headless route to the posture. See §8.)_
- A pre-existing, out-of-scope wart is recorded here so it is not later mistaken for a regression: `--yolo` and the other valueless flags are read by a different mechanism than `--eval-state` and are not position-checked. Probing the landed code, `iknow ask grep --yolo in src` sets the yolo posture **and** deletes `--yolo` from the query, so the model is handed a different question than the operator typed; the typed `yolo_non_tui_entry` refusal still fires and exits 1, so nothing runs, but the query text is corrupted. `ask grep --json in src` likewise sets `json` and drops `--json` from the query. `--eval-state` is position-checked and the other valueless flags are not, so this asymmetry is now **visible rather than accidental** — it was the shape the enumeration was hiding. Changing the other valueless flags is an ADR-0119 question (it changes what `--yolo` does inside a query on a non-TUI entry), not an ADR-0130 one, and was not decided here. It is recorded as a follow-up; this amendment proposes no fix. _(ADR-0141 (2026-10-15): "sets the yolo posture" here now reads as the preset triple; the wart, the typed `yolo_non_tui_entry` refusal and the exit-1 behavior are otherwise unchanged.)_

**Acceptance surface (both must hold).** Free text that happens to spell the posture flag is task text and must survive verbatim; a posture spelling in a value slot must fail outright.

- `iknow ask grep --eval-state in src/config` → query is `grep --eval-state in src/config`, verbatim, no posture
- `iknow ask --data-dir --eval-state <task>` → fails with `Invalid --data-dir: --eval-state`

Covering tests: `tests/cli/parse-args-eval-state.test.ts` (every claim in this section — the acceptance surface, the slot rule, the `--resume` fix, the source-derived tripwire, the display-path reading). An earlier revision of this line also named `tests/cli/parse-args-yolo.test.ts`; that file contains no `--eval-state` case and does not cover anything here, so the name was removed rather than left standing. The yolo face is covered where it lives, by `tests/cli/parse-args-yolo.test.ts` on its own terms; the two dispatch-time faces of eval state are certified by `tests/cli/cli-eval-state-non-entry-reject.test.ts` and `tests/cli/cli-eval-state-bare-run.test.ts`.

### 8. Amendment 2026-10-15 (ADR-0141: presets, the session overlay, and `fenceRetired`)

ADR-0141 recasts the postures this ADR names as **presets** applied over one memory-only session overlay, and renames the fence carrier this ADR rides. What moves and what does not, in one place (the amendment at the foot of this file records the eval-side product ruling; this section is the spine entry and carries the rename rulings):

- **Eval is the yolo preset applied headlessly.** `--eval-state` stays an explicit, non-default, named opt-in, writing the overlay declaratively, never through the interactive controller, with no exit semantics (`src/harness/sandbox/eval-state.ts:210-214`) — §1's entry discipline survives intact. The §1 correction above changes only the **description** of eval's `full_auto`: the resulting triple (`full_auto` + `global` + fence retired) is what `tests/harness/sandbox/eval-state-entry.test.ts:111` pins and `:130` qualifies — the permission posture is never a side effect of the fence, which is precisely the property ADR-0141 keeps true of the fence layer while the preset layer writes both axes. §2's measurement scope and §5's reporting invariant therefore do not move, and published eval-state numbers stay comparable with runs already published.
- **The env wire renames; its contract does not.** The channel by which the subagent worker joins §1's four bare routes is the parent→worker env key `IKNOW_YOLO` (`src/harness/sandbox/yolo.ts:106`), renamed to **`IKNOW_FENCE_RETIRED`** (ADR-0141 ruling 6). The value domain and the fail-closed direction are byte-identical: `"1"` / `"0"` both written whenever the posture is known (`src/harness/subagent/spawn.ts:253-255`), the key absent when the holder is absent, an ambient value always scrubbed before the write (`src/harness/subagent/spawn.ts:237`), an absent or unparsable value keeping the child fenced (`src/harness/subagent/worker.ts:542-545`). The worker inherits the retirement via env either way — the claim only changes spelling.
- **`BwrapFenceOptions.yolo` → `fenceRetired`.** The factory's one bare-argv branch (§2's Basis, and the early return §3's boundary-block skip relies on) is the same branch under the renamed option — field `src/harness/sandbox/bwrap.ts:215`, branch verified at `:724` on base f8e56652; §2's `:712` / `:741` are stale line numbers, noted at the source rather than edited.
- **Untouched:** §2's survives/retires split — the hard wall intercepts in every preset and outside one ("a preset is an axis combination, never a guardrail bypass", ADR-0141 ruling 1, citing §2's list), the which-tree axis still resolves writes against the live taskRoot, the worktree gate stays fence-independent; §3's lost-mask consequence, §4's rejected options, §5's reporting invariant, and §6's and §7's parser rulings stand as recorded. ADR-0141 changes what the word `--yolo` **means**; it does not change what eval state **does**.

**What does not move, item by item.** §2's survives/retires list (hard wall, which-tree axis, worktree gate on one side; mount layers, ro-bind blocks, credential mask, egress seam on the other) is unchanged. §2's **route scope** finding — the eval entry is `surface: "ask"`, which mounts the foreground bash route only, so background spawn, subagent and verify are structurally absent rather than retired-and-observed — is unchanged, and is the part of this ADR an implementer is most likely to disturb by accident: the preset widens what a retired fence means for the other three routes, and none of that is reachable from the eval entry. §3's consequence (the injected key loses its mask) is unchanged. §5's reporting invariant is unchanged and becomes **easier** to satisfy, since the state label now names a preset with a defined triple rather than a posture assembled from two writes; `runState="eval_state"` stays the spelling. §4's rejected options stay rejected, including "`full_auto` alone", which ADR-0141 makes _more_ clearly rejected: with `--auto-mode` still a permission-axis-only entry, a benchmark run that wants the fence gone cannot get there by `full_auto` and must name the preset.

**The comparability claim, stated so it can be checked.** Every published eval-state number (Harbor 0.23.0 oracle pilot, reward 1.0, and the pilots under `docs/evidence/adr-0130/`) was produced by the triple `full_auto` + `global` + fence retired on the foreground bash route. The amendment preserves all four of those facts, so the numbers stay comparable across the change. If a later revision alters the preset's content, §5 — not this amendment — is the clause that requires the artifact to say so.
