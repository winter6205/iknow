# 0130. Eval state: unsandboxed headless entry for benchmark runs

Date: 2026-09-29
Status: accepted

Benchmark evaluation (Terminal-Bench via Harbor) needs the agent to install packages, clone repositories and reach the network from `bash`. Our fence denies all of that by construction, because `--unshare-net` is constant. The operator has ruled that **evaluation itself has no need for the fence**, so the permission and sandbox axes opening for eval is not a trade-off to weigh but a precondition. This ADR records the shape of that opening: a distinct, named **eval state** whose runtime posture is identical to yolo's, reached headlessly — deliberately **not** by making `--yolo` legal on the non-TUI entries.

### 1. A named second exception, not a widened entry enumeration

Eval state applies yolo's entry state-combination exactly: permission → `full_auto`, `fsMode: workspace` → `global` (holders only, user-layer settings untouched), the bwrap fence retires wholesale, all four routes (foreground bash / background spawn / verify sandbox-run / subagent worker) run bare, egress seam retired. It is entered by an **explicit, non-default, named opt-in available to the headless entries** — never by adding `--yolo` to `chat` / `serve` / `ask` / `oneshot` / `trace`, and never as a default, a settings value, or an env var that flips silently.

**Basis:** ADR-0119 §ruling 7 (`docs/adr/0119-yolo-no-sandbox-mode.md:69`) restricts the flag to the TUI, and its recorded basis is an operator lock ("only before entering the TUI"), not a security proof — the operator has now ruled otherwise for this use. But that same ADR's risk line (`docs/adr/0119-yolo-no-sandbox-mode.md:131`) says the exception kills the discipline the moment it is _copied or silently extended_ to non-TUI entries, and names the entry enumeration plus parity tests as the defense. A separate named entry honors that: the exception stays a face you can grep, log and refuse to confuse with a user session, and `--yolo` keeps its original meaning. The defense line moves from "five commands reject it" to "five commands reject it + the eval opt-in is named, explicit and visible".

### 2. What survives, what retires (this is the measurement scope)

**Survives:** the **hard-wall** — a matched deny is non-overridable and intercepts before `full_auto` grants anything (`src/harness/sandbox/yolo.ts:42`, `src/harness/permission/policy.ts:50`); the **which-tree axis** — writes still resolve against the live **taskRoot**; the worktree gate, which is fence-independent.

**Retires with the fence:** workspace / global mount layers, protected-target `--ro-bind` blocks, the credential read mask, and the egress seam. Network reachability becomes the container's property, not ours.

**Route scope of the eval entry.** The retirement above is structural, but the _measurement_ claim is narrower than it first reads. The one eval entry is `surface: "ask"`, which mounts the **foreground bash route only**. The background manager and the subagent manager are gated `surface !== "ask"` (`src/harness/build-engine.ts:1175-1176`, `:998-1000`), so `background: true` throws "no background manager configured" and `spawn_subagent` is never registered; the verify `sandbox-run` route is constructed only from `chat-session.ts:16-17` / `hub.ts:2220-2230`, never from the one-shot entry. Those three routes are therefore **structurally absent** in eval state, not retired-and-observed. No number from this benchmark is evidence about background spawn, subagent or verify execution; publishing one as such is exactly the misattribution §5 exists to prevent. `EVAL_STATE_NOTICE` states this on stderr, and `tests/cli/cli-eval-state-bare-run.test.ts` asserts only the foreground route.

**Basis:** yolo's own definition — bare argv, `requireBwrap` skipped at assembly, egress retires entirely (`src/harness/aci/tools/registry.ts:470-474`); ADR-0119's two-axis distinction, where the ro-bind axis rides the fence and the which-tree axis does not. The retirement is structural, not a per-item opt-out: the fence factory returns bare argv (`src/harness/sandbox/bwrap.ts:712`) **before** `boundaryMountSegments` is called (`src/harness/sandbox/bwrap.ts:741`), and that block is the only place the protected-target ro-binds and the credential mask are assembled.

Eval state is therefore **not** "no guardrails": the spelling-sensitive pre-execution guardrail stays armed. Expect it to fire on legitimate benchmark commands; that is a finding about the wall's false-positive rate, which is one of the few things this benchmark can tell us about our own harness.

### 3. Consequence recorded: the injected model key loses its mask

The credential read mask is a fence-layer artifact, so in eval state it is gone, and anything running in the task container can read the API key we injected. Note, not a gate: a **scoped, revocable key with a spend cap** remains a sensible precaution for real runs, because the mask that would otherwise hide it is not present.

**Basis:** the mask is emitted by the fence — `credentialReadMaskArgs` (`src/harness/sandbox/credential-read-mask.ts:387`) has exactly one consumer, `src/harness/sandbox/bwrap.ts:678`, inside the boundary block the yolo return skips — so it is exempt by construction the same way the protected ro-binds are; the **effect boundary** it belongs to has no other carrier inside a disposable task image.

**Amendment 2026-09-29 (operator ruling).** An earlier revision of this section stated the scoped-key requirement as "non-negotiable for the first real run". The operator has ruled that no such restriction applies here: the local key already carries the full test suite's traffic (`npm run test:real-llm`, 11458 tests) and carries nothing that an eval trial does not. The technical consequence recorded above — the mask is gone, the key is readable in the task container — stands unchanged; only the gate strength is revised. The requirement is now advisory, not a preflight blocker, and it is not enforced or tested anywhere in the product surface.

### 4. Rejected options

- **Keep the fence on.** `--unshare-net` has no conditional and no escape hatch (`src/harness/sandbox/bwrap.ts:542-547`, ADR-0097). Install-dependent tasks would fail for a reason unrelated to the model, and the resulting number would measure our netns policy. Misattribution is worse than measuring something wide.
- **Drive `iknow tui --yolo` over a pty.** The TUI is a terminal application; a harness needs one command and parseable output. It buys no guarantee that a named eval opt-in does not already give.
- **`full_auto` alone.** Fixes approvals, not the fence: every non-yolo bash call still runs `requireBwrap` (`src/harness/aci/tools/bash.ts:902`), and the command is wrapped regardless of fs mode.

### 5. Reporting invariant

Every number produced in eval state is published with the state named in the same artifact. An eval-state score is not evidence about the fence, and the fence is not what it measures. Naming the entry separately exists precisely so this sentence can always be written.

**Precedent worth recording:** Harbor's codex adapter runs with `--dangerously-bypass-approvals-and-sandbox` as a fixed runtime argument — one flag switching off both its own per-command sandbox (landlock/seccomp on Linux) and its approvals. Codex is the closest built-in peer to our shape, and it does not attempt to keep its isolation inside a task container; across the ~35 built-in adapters, none does. The container is the sandbox, so the benchmark measures the agent, not the agent's private sandbox.

**Evidence:** `src/harness/sandbox/yolo.ts:79` (the typed non-TUI refusal this ADR declines to widen); `docs/CONTEXT.md` entries 沙箱纪律, yolo mode, 全局档, hard-wall, effect boundary. Measurements 2026-09-29: Harbor 0.23.0 oracle pilot on `terminal-bench/terminal-bench-2-1` scored reward 1.0 with 0 exceptions; `IKNOW_PERMISSION_MODE=full_auto` on `ask` performed a real write; container egress to the model endpoint returned 301 without any proxy injection.

### 6. Amendment 2026-09-29: flag-combination refusal, and the `=true` / `=false` spellings

**`--resume` conflict.** `ask --resume <id> --eval-state` is refused with `eval_state_flag_conflict`; `ask --resume <id>` alone is silently ignored, because the one-shot entry mints a fresh conversation id unconditionally (`src/cli.ts:363`) and `resumeId` is consumed only by `runChat`. The asymmetry is deliberate, not an oversight: §1's fail-loud line ("carrying the flag there is a typed refusal rather than a silent ignore") is the defense ADR-0119 §ruling 7 names against a dangerous flag being quietly swallowed. Under eval state the caller is a harness, so a silently dropped argument is a misattributed run; refusing keeps the entry honest about what it can honor. A code-review pass flagged this as scope creep — no clause above required it. It is recorded here instead of removed, because dropping it would reintroduce the silent-drop the same clause forbids. Covering tests: `tests/cli/parse-args-eval-state.test.ts`, `tests/cli/cli-eval-state-non-entry-reject.test.ts`.

**`--eval-state=true` / `=false`.** Both spellings are recognized. `=true` enters the posture; `=false` is the named non-posture spelling and reports no posture requested. The alternative — leaving the literal unrecognized so it falls through into the query text — was rejected: the operator's task text would carry `--eval-state=true` to the model, which is neither what was asked nor a refusal.

**Known defect, deferred.** The posture flag is still detected by enumerating the value-taking options that must reject it (`--host`, `--trace-out`, `--data-dir`, `--workspace-root`), rather than by a rule that derives the safe behavior from the parser's own structure. This is the wrong shape: a registry that must be updated whenever a flag is added cannot be complete, and completeness is the property being asked for. It is replaced-by-design, not accepted — see the handoff for the required shape, and §7 for the shape that replaced it. `--yolo` carries the same defect and is additionally live on `ask` today: `iknow ask grep --yolo in src` flips the fence-retiring posture _and_ deletes the word from the query.

### 7. Amendment 2026-09-29: posture detection derives from parser consumption, not an enumeration

**The §6 deferral is RESOLVED**, and resolved the way §6 said it would be — replaced-by-design, not accepted. The paragraph above stays as the decision record; this section is what closed it.

**The invariant, in the operator's terms.** Allow only what we have implemented; everything else fails outright. Concretely, and this is the whole rule: **a token that the parser is not consuming as a flag cannot change the posture.** The discriminator is the parser's own consumption, so no flag-name registry exists to keep current, and a flag added later is correct by construction.

**Basis — the property is structural, so it needs no table.** `parseArgs`'s scan loop is a single `if/else` chain, and a token it consumes — a valueless flag matched in the chain, or a value read with `argv[++i]` — lands in neither the locals nor the positional stream. On the query-bearing path the operator's word is therefore the only thing left in the stream that is not the posture flag, so any posture spelling appearing _between_ two of the operator's words is one of their words and stays in the query, while one before the first or after the last is an option. There is no third case to enumerate. The display path is a separate stream and a separate rule — see the registry paragraph below.

**What the rule still reads a name from, disclosed.** One: `SUBCOMMAND_HEADS`. The span needs to know that positional 0 may be a subcommand head rather than an operator word, so it consults the same six-token set the dispatch chain matches on (`chat` / `serve` / `trace` / `tui` / `ask` / `help`). The claim above is therefore "no flag-name registry", not "no names at all". The distinction that matters: this is a **closed dispatch vocabulary, not an open-ended flag set** — every entry is a head the chain at the bottom of `parseArgs` must match anyway, so it is a list that is finished by construction rather than one that drifts, and the "an enumerated list is never finished" objection does not apply to it the same way. The obligation it does carry is concrete: a head added to the dispatch without a `SUBCOMMAND_HEADS` entry would shift the span. This dependency is **pre-existing** — it is the same set the old valueless-flag registry sat beside — and is recorded here rather than removed, since deduplicating it against the dispatch chain is a separate refactor this amendment does not make.

**The name registry is deleted, and what replaced it is positional, not a better list.** The valueless-flag literal set that previously participated in marking the operator-word span was doing real work, and deleting it alone was a regression. The span is computed over two different streams: the scan loop's `rest`, and — for a display path — the **raw argv**, because `-h` / `-V` return from inside the loop. Valueless flags never reach `rest`, but they _are_ present on the display path, so the registry was load-bearing there: with it removed, `-h --eval-state --json` classified `--json` as an operator word, which moved the span's end and silently downgraded the posture flag to free text. The replacement states the answer positionally instead of by recognizing flags: **a display path produces no query and no session, so it has no operator words at all** — the span question has a known answer that does not depend on what any token looks like, and a new valueless flag, or one appearing after the posture flag, cannot change it. Recognizing flags was a proxy for that answer, and a proxy is what drifts. The posture spelling remains the single source of truth, and no flag-name registry remains.

**The value-slot rule is now a function, not a list.** One `slotValue(flag, argv, index, missing)` reader throws `Invalid <flag>: <raw>` when the slot holds a posture spelling, and it is called by every value-taking branch **except one**. This is the form the required shape asked for: a rule about **slots** ("a slot expects a value, and no posture spelling is ever a legal value") rather than a rule about which flags have slots. A value-taking flag added later inherits the rule by calling it — no registry to update. `--port` / `--max-bytes` / `--max-turns` are covered by it, where before they were protected only as a side effect of their own `Number()` validation.

**The one exclusion, stated rather than smoothed over.** `--resume` is a value-taking branch that does not call `slotValue`: it reads `argv[++i]` itself and routes the token through `readResumeSlot`, which reports a posture in that slot as ADR-0130 §6's typed `eval_state_flag_conflict` rather than throwing. So the earlier phrasing — "`slotValue` is called by every value-taking branch", used to justify "no second site to forget" — over-claimed in exactly the direction that mattered: the one branch that does _not_ call it is the one branch a later change can forget. The honest form is "every value-taking branch except `--resume`, which reports instead of refusing", and the honest property is correspondingly weaker than it looked: the exclusion is a **convention the code documents** (`readResumeSlot`'s doc, ADR-0130 §6), **not something the type system enforces** — nothing makes the next author pick `slotValue` over `argv[++i]`. `tests/cli/parse-args-eval-state.test.ts` reads the source of `parseArgs` and asserts both halves — that the arms advancing the loop index are exactly the slot table plus `--resume`, and that every one of them calls `slotValue` except `--resume` — which turns the convention into a checked one without changing the parser.

**`--eval-state=false` in a value slot is refused, on purpose.** The test is on the _spelling_, so `=false` fails in a slot the same as `=true` and as the bare literal: `iknow ask --data-dir --eval-state=false <task>` → `Invalid --data-dir: --eval-state=false`. This is correct rather than an over-strict bug, and is stated so a later reader does not "fix" it into acceptance: the `=false` form is a spelling **of the posture flag** (ADR-0130 §6), not a value, and taking it as a data root would make one token mean a posture and a path simultaneously. Whether the request means "not in eval state" is the parser's call to make in a flag position; inside a value slot the only defensible reading is "that was not a value".

**One live defect fixed here, previously unrecorded.** `readResumeSlot` matched only the bare literal, so `iknow ask --resume --eval-state=true <id>` silently resumed a session whose id was the string `--eval-state=true`: no posture, and no refusal. The bare literal was correctly refused; the `=`-form was not. This is a surface behavior change, so it is stated rather than folded in: the guard is now on the spelling, so both forms take ADR-0130's existing typed `eval_state_flag_conflict` path.

**What does not change.**

- `--yolo` handling is untouched. ADR-0119 §ruling 7 is **qualified, not overturned**: `--yolo` is still a parse-time typed refusal on `chat` / `serve` / `ask` / `oneshot` / `trace`, and `iknow tui --yolo` remains the sole legal surface.
- A pre-existing, out-of-scope wart is recorded here so it is not later mistaken for a regression: `--yolo` and the other valueless flags are read by a different mechanism than `--eval-state` and are not position-checked. Probing the landed code, `iknow ask grep --yolo in src` sets the yolo posture **and** deletes `--yolo` from the query, so the model is handed a different question than the operator typed; the typed `yolo_non_tui_entry` refusal still fires and exits 1, so nothing runs, but the query text is corrupted. `ask grep --json in src` likewise sets `json` and drops `--json` from the query. `--eval-state` is position-checked and the other valueless flags are not, so this asymmetry is now **visible rather than accidental** — it was the shape the enumeration was hiding. Changing the other valueless flags is an ADR-0119 question (it changes what `--yolo` does inside a query on a non-TUI entry), not an ADR-0130 one, and was not decided here. It is recorded as a follow-up; this amendment proposes no fix.

**Acceptance surface (both must hold).** Free text that happens to spell the posture flag is task text and must survive verbatim; a posture spelling in a value slot must fail outright.

- `iknow ask grep --eval-state in src/config` → query is `grep --eval-state in src/config`, verbatim, no posture
- `iknow ask --data-dir --eval-state <task>` → fails with `Invalid --data-dir: --eval-state`

Covering tests: `tests/cli/parse-args-eval-state.test.ts` (every claim in this section — the acceptance surface, the slot rule, the `--resume` fix, the source-derived tripwire, the display-path reading). An earlier revision of this line also named `tests/cli/parse-args-yolo.test.ts`; that file contains no `--eval-state` case and does not cover anything here, so the name was removed rather than left standing. The yolo face is covered where it lives, by `tests/cli/parse-args-yolo.test.ts` on its own terms; the two dispatch-time faces of eval state are certified by `tests/cli/cli-eval-state-non-entry-reject.test.ts` and `tests/cli/cli-eval-state-bare-run.test.ts`.
