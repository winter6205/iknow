Date: 2026-10-15
Status: accepted
Deciders: operator (locked rulings 1–9 and the F4 repair; ruling 6's convergence surface and the env-wire naming are delegated to this ADR and decided here)
Related: ADR-0119 (yolo no-sandbox mode — this amends its ruling 1, ruling 6's channel, ruling 8's shape, and Amendment 2026-09-20 (ii), and amends a **named carrier inside** ruling 2 (the `IKNOW_YOLO` env wire), ruling 5 (the mode-row projection) and ruling 7 (the refusal roster, extended rather than widened); **rulings 3 and 4 stand verbatim**, and the rest of rulings 2, 5 and 7 stands), ADR-0139 (permission axis is fence-independent — its **mechanism** ruling stands, its **product** consequence for `--yolo` is re-adjudicated), ADR-0130 (eval state — §1's permission sentence is corrected here; §2's measurement scope is untouched), ADR-0140 (`full_auto` is bounded — untouched, cited because the yolo preset now reaches it), ADR-0092 (fs isolation modes, holder-flip discipline), ADR-0084 (user-layer settings discipline), ADR-0090 (the project layer may not self-grant `full_auto`), ADR-0097 / ADR-0109 (the egress and ro-bind exemptions ride the fence), ADR-0068 / ADR-0127 (hard wall and security review sit below both axes)

## Context

**What `--yolo` is today, verified at f8e56652 and re-checked at 1a4ad1b9 (between the two, `src/` changed only in `config/env.ts`, `compress/threshold.ts` and `loop-engine.ts`).** The enter action is one function shared by `/yolo` and the launch path — `applyEnterCombination` (`src/harness/sandbox/yolo.ts:321-333`) — and since ADR-0139 it writes exactly two things: `fsMode` forced to `global` (`src/harness/sandbox/yolo.ts:326-331`, conditional on the current value differing from `FS_ISOLATION_MODE_DEFAULT`, which is `"global"` — `src/harness/sandbox/fs-mode.ts:55`) and the yolo holder (`src/harness/sandbox/yolo.ts:332`). The permission holder is carried on the action face and **deliberately never read, written, snapshotted or restored** (`src/harness/sandbox/yolo.ts:151-159`). So today's `--yolo` is "no fence, questions stay on" — which is precisely the posture ADR-0139 §2 named and opened (`docs/adr/0139-permission-axis-is-fence-independent.md:36-42`). The operator's ruling is that this is a legitimate posture **but not the one the word `--yolo` should mean**: the issue #1035 product intent was "no fence and no questions", and ADR-0139 achieved axis honesty by re-naming the flag's content rather than by adding the posture that was wanted.

**Why every posture keeps arriving pre-paired (findings F1/F2).** The retirement primitive and the user-visible label are the same object. `createBwrapFence` has exactly one bare-argv branch, `if (opts.yolo === true)` (`src/harness/sandbox/bwrap.ts:724`, on the option field `readonly yolo?: boolean;` at `src/harness/sandbox/bwrap.ts:215`), and it precedes the whole boundary block — `boundaryMountSegments` at `src/harness/sandbox/bwrap.ts:753`, the credential mask inside it at `:690`, and the constant `--unshare-net` (`:547`, emitted at `:559`) — so anything wanting an unfenced run must raise the **yolo** flag, and anything raising that flag gets the label whether it earned it or not. `--eval-state` inherits the pairing structurally: `enterEvalState` delegates the fence half to `createYoloController(...).enterAtLaunch()` and then writes its own permission posture (`src/harness/sandbox/eval-state.ts:216-236`, the permission write at `:234`). One switch, two jobs — that is the coupling, and no amount of entry-side special-casing removes it.

**F4, the defect this closes.** The snapshot/restore channel and the `/config` persistence channel have no mutual exclusion. `/config`'s fs row sets the holder **and writes the settings file** (`src/tui/app.tsx:1110-1121`: `fsCtx.set(next)` then `void props.onPersistFsMode?.(next)`, the writer being `src/tui/run.tsx:615-633` → `persistFsModeChanges` at `src/config/persist-settings.ts:537`), while yolo's `exit()` restores the snapshot **unconditionally** (`src/harness/sandbox/yolo.ts:373-375`: `if (snap?.fsMode !== undefined) opts.fsMode?.set(snap.fsMode)`). Entering yolo from `global`, switching `/config` to `workspace` (persisted), then exiting yolo leaves the holder at `global` and the file at `workspace`: runtime and persistence disagree, and the next launch jumps back. The holder cannot distinguish "forced by the posture" from "chosen by the user" because both facts live in the same field. (The written description of F4 lives in a handoff that is **not committed** — see Pending P4.)

**What the operator locked.** Two presets over one session overlay, a derived display boolean instead of an entry-derived label, whole-overlay clearing on any user axis change, one new invariant asserted on every effective-value computation, and the fence layer reduced to a single input it can be audited on. Rulings 1–9 below are that lock, restated with the code surface that implements it.

## Decision

### 1. Two presets share one session overlay; the fence primitive is not a preset

| Preset         | Fence     | `fsMode`  | Permission    | Entries                                                                    |
| -------------- | --------- | --------- | ------------- | -------------------------------------------------------------------------- |
| **yolo**       | retired   | `global`  | `full_auto`   | `--yolo` (launch, **no modal**), `/yolo` + confirmation                    |
| **no-sandbox** | retired   | `global`  | **untouched** | `--no-sandbox` (launch, **no modal**); no in-session command (P6, decided) |
| — not a preset | untouched | untouched | `full_auto`   | `--auto-mode` (`src/cli.ts:1095`)                                          |

- **Confirmation belongs to interactive entry, never to a launch flag.** Verified at f8e56652: the launch path is `applyYoloLaunchSeed` → `controller.enterAtLaunch()` with no modal face anywhere in it (`src/tui/run.tsx:411-416`, `:722`, `src/harness/sandbox/yolo.ts:350-359`), and the modal opens only from `/yolo` (`setters.setYoloConfirming(true)` at `src/tui/app.tsx:2162`, the picker at `src/tui/yolo-picker.tsx:32-51`). A flag the operator typed on the command line **is** the confirmation; a modal there would ask the second time for a decision already made in a shell. So the `Entries` column reads "launch, no modal" for both presets, and this ADR does not add a launch-time modal to `--no-sandbox` that `--yolo` never had.
- **`--no-sandbox` + `--auto-mode` is allowed, and is composition, not the yolo preset.** The pair reaches the yolo preset's _triple_ (`full_auto` + `global` + retired fence) from **two tiers**: the flag sets the startup permission tier (`--auto-mode` → `permissionMode: "full_auto"` at `src/cli.ts:1095` → `resolvePermissionMode`'s explicit arm at `src/tui/run.tsx:684`, chain `src/cli/runtime.ts:60-73`) and `--no-sandbox` declares the fence + tier pair in the overlay. It is refused nowhere, because refusing it would mean ADR-0139's mechanism ruling (the two axes are independent; a flag that touches one does not touch the other) had been reversed, which §"Relations" says it has not. Three consequences are ruled, all of them display-side rather than state-side: **no YOLO badge** (ruling 5 keys the badge to the **yolo** preset alone, and this pair is not that preset — the `--no-sandbox` preset _is_ active; what is absent is `yolo`), **无沙箱 shows** (ruling 5 derives the marker from the effective configuration, which retires the fence), and the mode row shows `Auto` from the startup tier. The pair also **has no joint exit**: the `--no-sandbox` preset keeps its own clear, but no preset in the pair declares the permission axis, so a mid-session permission change clears nothing (it changes a tier the overlay never wrote) and the session simply lands on retired fence + `plan`/`default`, which no invariant forbids — ruling 4 constrains `fsMode` × fence only. That asymmetry is the point: a preset is one declared act with one exit, a pair is two acts with two separate ways back, and the UI must keep saying which the operator is in.
- **The `plan` + retired-fence posture has no flag pair** and is reachable only through the startup permission tier (`IKNOW_PERMISSION_MODE=plan`, or project `defaultMode: "plan"`, whose value domain is `["default", "plan"]` at `src/harness/permission/project-settings.ts:48`; both feed `src/cli/runtime.ts:67-71`). `--no-sandbox` deliberately touches no permission axis, so it cannot produce the posture alone, and there is no `--permission-mode` flag (the explicit arm is set only by `--auto-mode`, `src/cli.ts:1095`). Recorded so the spec's posture table does not imply an entry that does not exist.
- `--auto-mode` stays a **permission-axis-only** startup choice; it is not a preset and touches no fence.
- `--no-sandbox` is what `--yolo` does today (ADR-0139's product), so the flag is named for its content rather than inherited from a label.
- `--eval-state` is **declarative application of the yolo preset at startup**: it writes the overlay directly, never goes through the interactive controller, and has **no exit semantics** (an eval invocation's posture ends with the process — `src/harness/sandbox/eval-state.ts:210-214` records why there is no exit to probe). Because the yolo preset now includes `full_auto`, eval's own permission write (`src/harness/sandbox/eval-state.ts:234`) is **absorbed into the preset** rather than being a second carrier; the resulting posture is the same triple eval applies today (`full_auto` + `global` + fence retired, pinned by `tests/harness/sandbox/eval-state-entry.test.ts:111`), so **no ADR-0130 §2 measurement claim moves** and the eval-state number stays comparable with runs already published.
- **Hard wall and security review intercept as before**, in every preset and outside one. Verified at f8e56652 that both are **pre-filters**, ahead of any mode branch: `const walled = hardWallOutcome(opts.hardWalls, wallCtx)` (`src/harness/permission/policy.ts:413`, commented "Hard-walls FIRST — un-overrideable in any mode") and `const review = securityReviewOutcome(ctx, mode, category)` (`src/harness/permission/policy.ts:422`, per ADR-0127 "neither a stored grant nor `full_auto` may answer a question the parse could not"), then layered rules at `:427`, then the mode branch `modeAndCategoryOutcome` at `:431`. (`src/harness/permission/hard-walls.ts`; ADR-0130 §2's survives list `docs/adr/0130-eval-state-unsandboxed-benchmark-entry.md:20`.) A preset is an axis combination, never a guardrail bypass — which is why the yolo preset adding `full_auto` cannot widen the wall's reach: `full_auto` is consumed at the mode branch (`:431`), two steps below both intercepts.
- **Entry is limited to the TUI** — launch flag or in-session command, with the modal on the in-session half only (first bullet) — plus `--eval-state`, excepted as a headless declarative entry. A non-TUI command carrying either preset flag is a typed error with a non-zero exit and nothing started — the shape already implemented for `--yolo` at `src/cli/parse-args.ts:890-895` and `src/cli.ts:986-998` (`process.exit(1)` at `:996`), extended to `--no-sandbox`.

### 2. Three tiers, and the overlay is memory-only

**Effective value = persisted settings < startup flag < session overlay.** The overlay exists in memory only, is never written to settings or to a session file, and has **no snapshot and no restore** — the snapshot channel that produced F4 is deleted, not guarded.

Tier facts verified at f8e56652 and re-checked at 1a4ad1b9 (between the two, `src/` changed only in `config/env.ts`, `compress/threshold.ts` and `loop-engine.ts`), because the tiers must be stated in terms of what actually exists:

- Persisted `fsMode` is read from settings and nothing else at startup (`src/tui/run.tsx:704` via `resolveFsIsolationMode`, `src/config/settings.ts:646-650`; the declared field is `src/config/settings.ts:495` inside the five-field isolation section `:476-526`). **There is no `--fs-mode` startup flag today**, so the startup-flag tier carries no `fsMode` value. A launch preset (`--yolo`, `--no-sandbox`, `--eval-state`) writes the **session overlay** tier, never settings and never the startup-flag tier: today `--yolo` seeds an in-memory holder and calls `enterAtLaunch` (`src/tui/run.tsx:401-413`, `src/harness/sandbox/yolo.ts:350-359`) without touching user settings; under this ruling it is an overlay seed identical to in-session entry minus the modal.
- Persisted permission has a real four-step chain: explicit flag > `IKNOW_PERMISSION_MODE` > project `defaultMode` > `default` (`src/cli/runtime.ts:60-73`), where the explicit value comes only from `--auto-mode` (`src/cli.ts:1095`).
- `IKNOW_FS_MODE` and `IKNOW_YOLO` are **not** startup layers: they are parent→worker wires written at `src/harness/subagent/spawn.ts:248` / `:253-255` and read only inside the worker (`src/harness/subagent/worker.ts:508`, `:540-546`). A host value cannot seed a session; an ambient one is scrubbed (ruling 6).
- **The overlay never becomes a settings key** (ADR-0119 ruling 8's no-persistence ruling continues to bind, `docs/adr/0119-yolo-no-sandbox-mode.md:83-85`) and, for the avoidance of a real trap: it must not be routed through native session state either, whose exclusion rules already refuse a field matching `/…|yolo/i` (`src/session-api/store/native-state-store.ts:294-297`, enforced by `forbiddenPersistedField` at `:319`) — **and that pattern must be widened to the `no-sandbox` / `fenceRetired` spellings**, or a preset declaration survives into persisted state under a name the guard never heard.

### 3. The overlay clears as a whole, or not at all

Any user change of an axis **the preset declares** **exits the preset** — however it arrives, through the `/config` panel, `/config <set>`, the `/permissions` slash command, or the Shift+Tab wheel: the trigger is _a user applied a value to a preset-owned axis_, not a particular screen (which axes each preset owns is the first bullet below). The entire overlay is cleared, the user's choice is written to settings, effective values are recomputed, and the preset's markers are dropped. Partial clearing is forbidden — it is what manufactures the illegal combination ruling 4 exists to prevent.

This is the mechanism that fixes F4 honestly: after a `/config` write the holder and the file agree by construction, because the write and the overlay clear are one action, and there is no snapshot left to re-apply over the user's choice.

**One narrowing this ADR decides rather than inherits.** The lock's words are "whole-overlay clearing on any user axis change", which is ambiguous between _any axis_ and _any axis the preset declares_; the ADR header lists only ruling 6's surface and the env-wire naming as delegated, so this reading is recorded as this document's own decision and is reversible in place. Two things make the declared-axis reading the one the rest of the lock requires. The first is ruling 3's own purpose: a clear **resolves a contradiction** between the preset's declaration and the user's choice, and where the preset never declared an axis there is no contradiction to resolve — clearing there would silently retire the operator's dangerous-flag act for a reason unrelated to it, which is precisely the outcome ADR-0119's confirmation non-goal (`docs/adr/0119-yolo-no-sandbox-mode.md:162`, "no unconfirmed silent in-session switch") and ruling 6's entry/exit asymmetry (`:69`) exist to prevent. The second is ADR-0139's mechanism ruling, which this narrowing must not appear to breach: the yolo preset's exit-on-permission-change is a **declaration revoked by its author's later act**, not a permission write producing a fence write; the fence primitive still reads one boolean and never inspects permission, and the path from the keystroke to the fence runs through the overlay's lifecycle, where the marker and the badge change in the same action as the state. Axis honesty is preserved because the layering is visible: preset → axes, never axis → axis.

Two implementation obligations follow from verified gaps, not from preference:

- **The clear is triggered per axis, not per screen and not per keystroke.** A preset's identity is its **declaration**, so a user change clears the overlay exactly when it contradicts an axis the preset declares: the yolo preset declares all three (fence, `fsMode`, permission) and so exits on any of them; the no-sandbox preset declares two (fence, `fsMode`) and **does not exit on a permission change**. The reason is decisive rather than stylistic — the posture ADR-0139 §2 named, _no fence and questions still on_, is `--no-sandbox` plus a permission change, and clearing on the second half would make the flag's own meaning **unreachable** one keystroke after the operator asked for it. Under the yolo preset the same keystroke does contradict a declared clause, so the preset exits and its badge goes with it. Concretely, the Shift+Tab wheel must be read as its **result**, not as a press: `nextShiftTabAgentMode` (`src/harness/graph/mode.ts:149-159`) cycles `default → full_auto → full_auto + graph → default`, so the `full_auto → full_auto + graph` step (`:155-157`) changes **only the graph axis**, which no preset owns, and must leave any preset intact; the other two steps change permission and therefore exit the yolo preset. A hook on the keystroke rather than on the resulting permission value would revoke a posture for a reason the posture never claimed.
- **The permission axis has no settings write-back today.** `src/config/persist-settings.ts` exports patches and writers for thinking / memory / fsMode / worktreeOnMutate / subagentCap / model only (`:174`, `:209`, `:278`, `:312`, `:351`, `:429`; `:510`, `:518`, `:537`, `:558`, `:579`, `:599`), and both permission channels flip the **holder alone**: `/permissions set` (`ctx.set(cmd.mode)` at `src/harness/permission/permissions-command.ts:110`, reached from `runPermissionsSlashCommand` `src/tui/app.tsx:1429-1443` and from `chat` at `src/cli/chat-session.ts:2153`) and the Shift+Tab wheel (`permission.set(next.permission)` at `src/harness/graph/mode.ts:189`, `src/tui/app.tsx:5310` / `src/cli/chat-session.ts:3918`). Ruling 3 therefore requires a **new** permission write-back channel, which must respect ADR-0090: the project layer may not self-grant `full_auto` (`src/harness/permission/project-settings.ts:156-164`), so the write is a user-layer write.
- **The clear hook belongs at every site that applies a user's choice to a preset-owned axis** — which is two kinds of site, not one. For `fsMode` they are the persist sites, of which there are exactly two (`src/tui/app.tsx:1117-1118` panel toggle, `src/tui/app.tsx:1356-1360` `/config <set>`). The sibling panel writers for `subagentCap` (`:1157`) and `worktreeOnMutate` (`:1192`) persist axes no preset declares and carry **no** clear hook. For permission there is no persist site to hook **until the new channel exists**, so the hook sits at the two holder-flip surfaces above and the flip, the settings write, and the overlay clear become one action. Covering the holder setters alone would miss the distinction "the user chose this" / "the preset forced it", which is what the persist call conveys; covering the persist sites alone would leave a mid-preset Shift+Tab **silently shadowed** by the overlay, where the mode row either follows the holder (and lies about what the runtime is doing) or follows the effective value (and the keystroke appears dead) — the original F4 in a new axis.
- **One naming trap on the way.** The single-axis helper `applyShiftTabModeFlip` (`src/harness/permission/modes.ts:168-180`, re-exported at `src/harness/permission/index.ts:51`) has **no caller in `src/tui/` or `src/cli/`**: both live surfaces call the two-axis `applyShiftTabAgentModeFlip` (`src/harness/graph/mode.ts:172-191`), whose own doc comment says so while naming the stale one. An implementer who hooks `permission/modes.ts` buys a hook that never fires. Fixing the comment or deleting the dead helper is the implementer's call; hooking the live face is not optional.
- **The wheel must read the _effective_ permission, not the holder.** Its read side is as load-bearing as its write side: `applyShiftTabAgentModeFlip` takes its starting point from the holder (`const current = { permission: permission.get(), … }`, `src/harness/graph/mode.ts:183`) and writes back to the holder (`:189`). Under a preset the two disagree — the row shows the overlay's `full_auto` while the holder still reports the pre-preset value — so a press in a yolo-preset session would step from `default` to `full_auto`, change nothing the operator can see, and still trip the clear, because the press lands on an axis the yolo preset declares: the posture vanishes on a keystroke that displayed no movement. The read is therefore taken from the **effective value**, the same computation the 无沙箱 marker and ruling 4's assertion use, and the flip's write and the overlay clear stay one action. Under the **no-sandbox** preset the same correction keeps the wheel from looking like it skipped a station; either way its `full_auto → full_auto + graph` step touches only the graph axis and clears nothing.

### 4. One invariant, asserted, never corrected

**While the effective `fsMode` is `workspace`, the fence must not be retired.** It is asserted on every effective-value computation; a violation is a **typed error**, never a silent correction.

Current behavior for the case the operator asked to be verified: `--yolo` with `settings.fsMode = workspace` **already lands on `global`** — `applyEnterCombination` forces a non-default tier to `global` (`src/harness/sandbox/yolo.ts:326-331`), and the launch path applies the same combination (`src/harness/sandbox/yolo.ts:350-359`, seeded from the flag at `src/tui/run.tsx:411-416` / `:716-722`, flag source `src/cli.ts:1107`). So the invariant is **not a behavior change** for the reachable entry paths; what changes is the _channel_. Today the force is a silent rewrite of a shared holder whose provenance is unrecoverable, and exit re-applies a stale snapshot over it (F4). Under this ruling both presets **declare** `fsMode: global` in the overlay, so `workspace` and a retired fence are never simultaneously effective, and the assertion has nothing to correct — it fires only if a later change reintroduces a path that retires the fence without declaring the tier.

The assertion is what makes the rejected "single-axis overlay clear" (see Rejected options) unreachable rather than merely discouraged.

### 5. Display is derived from the effective configuration, not from the entry

- **The 无沙箱 marker** is a persistent, independent indicator shown whenever the fence is retired — a boolean **derived from the effective configuration**, never from which entry raised it and never from a `yolo` label. Its light condition is the union: the main process's effective config retires the fence, **or** a live subagent was spawned while the fence was retired, **or** a live background process was spawned while the fence was retired.
- **The YOLO badge means the yolo preset and nothing else.** It is present only while the preset is unmodified; the moment ruling 3 clears the overlay it is gone.
- **Label suppression is keyed to what the visible indicator already states, never to "a preset is active".** Suppressing a per-axis label is legitimate only when some indicator on the row states that axis; otherwise the row hides a fact the operator is living with, which is the dishonesty ADR-0119's conflict resolution (b) exists against. Three consequences: the **unmodified yolo preset** shows **YOLO + 无沙箱** and does **not** concatenate the per-axis labels, because one word (`YOLO`) states all three axes it declares; **`--no-sandbox`** shows **无沙箱 with no badge** — "no badge", never a hidden permission label, since that preset declares no permission axis and the row must go on saying what the session's mode is; and the composition of ruling 1's third bullet (`--no-sandbox` + `--auto-mode`) keeps the permission label: **无沙箱 + `Auto`**. That composition is **not** a preset-free state — `--no-sandbox` is a preset and is active; what is absent is the **yolo** preset, and therefore the badge, which ruling 5 keys to it alone. Today's projection concatenates (`modeRowText` = `modeRowBaseLabel` + marker, `src/tui/app.tsx:910-919`, with the permission/graph face in `modeRowBaseLabel` `:879-887`, the marker `:898-900`, and the render slots `:5965` / `:5972`), so this is a display change, not a re-label.
- The marker's current data source must move: `src/tui/app.tsx:2087-2090` (`seedYoloOn`) reads a holder and the result is cached as component state (`:2640`) written only by the `/yolo` paths (`:2157`, `:2298`) — an entry-derived mirror, which is the thing ruling 5 forbids.
- **Registries carry no spawn-time fence fact today**, so the descendant half of the light condition is new state, and its shape is constrained by what exists: background tasks live in a `Map` that is inserted into (`src/harness/background/manager.ts:1098`) and **never deleted from** — liveness is status-derived (`isLiveTask` `:956-958`, `listLiveTasks` `:959-968`, exposed `:460`/`:1681`); subagent tasks are inserted at `src/harness/subagent/manager.ts:2354` and removed only on the identity-write failure path (`:1696`), with `listSubagents` (`:3228-3270`) projecting live **and** terminal rows. Neither `BackgroundTask` (`:109-176`), its persisted record (`src/harness/background/registry.ts:53-84`), `SubagentInfo` (`src/harness/subagent/manager.ts:155-207`) nor `WorkerIdentityRecord` (`src/harness/subagent/worker-identity-record.ts:74-92`) has a fence field. The spec therefore registers the fence posture **at spawn** and derives it out of existence by the **existing status-based liveness filter**, rather than promising a delete-on-exit hook those registries do not have.
- **The run record and a status surface record the posture.** Neither exists today: `SessionRecord` (`src/harness/trace/types.ts:243-255`, assembled at `src/harness/loop-engine.ts:4506-4514` (the `recordSession` call)), `TurnRecord` (`:213-237`) and `SubagentSpawnRecord` (`:426-444`) carry no posture, and there is **no `/status` command** — the nearest surfaces are `/info` (`src/tui/app.tsx:6174-6211`, line set `:6201-6210`) and the per-axis `<axis> status` subcommands (`src/harness/sandbox/fs-mode.ts:185-186`, `src/harness/permission/permissions-command.ts:102`). **Decided (P1):** the posture is recorded as a new `posture` field on `SessionRecord`, filled at the `recordSession` call (`src/harness/loop-engine.ts:4506-4514`), and surfaced as one added line in `/info` (`src/tui/app.tsx:6201-6210`). No `/status` command is added; `TurnRecord` and `SubagentSpawnRecord` are not extended in this round.

### 6. `fenceRetired` is the fence layer's only input

The sandbox layer reads **one** boolean derived from the effective configuration. `fenceRetired` is **derived at exactly one site**: the overlay module's effective-value computation in `src/harness/sandbox/` (spec `specs/yolo-mode.md` §1). Every convergence site below reads that result; none recomputes it from a holder, a flag or a preset label. The `createBwrapFence` option is renamed from `yolo` to `fenceRetired` (`src/harness/sandbox/bwrap.ts:215` field, `:724` branch, and the comments that assert the old identity at `:200-214`, `:230`, `:678-679`, `:706-723`), and `bwrap.ts` contains no `yolo` judgment at all afterwards.

The scrub site covers **both** spellings during the change so a stray host value can never retire a fence (ADR-0119 ruling 2's wire hygiene, `docs/adr/0119-yolo-no-sandbox-mode.md:47`). The value written at `src/harness/subagent/spawn.ts:253-255` is the parent's **derived** `fenceRetired` at spawn time, never a preset holder: `"1"` iff the parent's effective configuration retires the fence, under either preset or `--eval-state`.

**Layering constraint** (AGENTS.md hard boundary 13): the overlay and the effective-value computation live below the TUI — `src/harness/sandbox` / `src/config` — and `src/tui/` only renders what they derive; `src/harness`, `src/session-api`, `src/config`, `src/shared` must not import `src/tui/`. ### 8. A fence change reaches only commands started after it

Already-running processes are never re-wrapped. Measured granularity, since "after" has to be an exact claim:

| Route                  | Re-read point                                                         | Granularity                                                              |
| ---------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| foreground bash (main) | `src/harness/aci/tools/bash.ts:418`, frozen per call at `:1307-1312`  | the next call; an in-flight call keeps its argv (no re-fencing)          |
| background spawn       | same snapshot, handed on at `src/harness/aci/tools/bash.ts:1535-1538` | per spawn, frozen for that task's life                                   |
| subagent worker        | `src/harness/subagent/spawn.ts:254`, per spawn                        | the next spawn; a live worker keeps its own private holder               |
| verify sandbox-run     | `src/harness/verify/sandbox-run.ts:152`                               | **per `runVerifyLoop` entry (≈ per user turn)** — see the mismatch below |

The verify row contradicts its own comment. `src/harness/verify/sandbox-run.ts:149-151` says "the caller rebuilds this closure per round", and `src/harness/verify/verify-loop.ts:220-221` / `src/session-api/hub.ts:2941-2942` repeat it, but `runVerifyLoop` builds the closure **once** (`src/harness/verify/verify-loop.ts:1556-1557`) and every correction round reuses it (`:1559-1568`, body loop at `:1049`/`:1086`). A mid-loop preset change therefore takes effect on the next turn's verify, not on a later round of the current loop. This is recorded as Pending P2 (a comment-vs-control-flow defect to fix, not a behavior to re-adjudicate).

### 9. What this closes

F4, by construction: the forcing value lives in an overlay tier the user cannot write, the user's choice lives in the settings write that simultaneously clears the overlay, and no snapshot is left to re-apply over either.

## Rejected options

- **A value-comparison guard in `exit()`** (restore only if the holder still holds what the posture forced). Rejected because it cannot distinguish "the user explicitly chose the value that happens to equal the forced one" from "the user never touched it" — it restores or does not restore on a coincidence, and it leaves the two write channels uncoupled, so the settings file and the holder can still disagree.
- **Keep ADR-0139 unchanged** and add the wanted posture somewhere else. Rejected because it preserves the carrier problem: the flag named `--yolo` would keep meaning "fence only", and the posture the operator actually wants would need a _third_ name, so the label keeps diverging from the content and the coupling stays in the fence layer.
- **Clear only the changed axis from the overlay.** Rejected on ruling 4's account: clearing `fsMode` while the overlay still retires the fence produces exactly the illegal `workspace` + retired-fence state; a partial clear makes the invariant a runtime surprise instead of a construction property.
- **A second un-fenced switch with no marker.** Rejected because it is an unnamed exemption, which ADR-0119's conflict resolution (a) and ruling "exemptions must be named" forbid (`docs/adr/0119-yolo-no-sandbox-mode.md:93`, `:97`), and because an unfenced session that does not say so is the UI-dishonesty failure ADR-0139 §Context names as the reason the original coupling existed (`docs/adr/0139-permission-axis-is-fence-independent.md:14`, `:18`).

## Gate check (the three ADR conditions)

- **Hard to reverse** — a public flag changes meaning (`--yolo` now reaches `full_auto`), a new public flag ships (`--no-sandbox`), the fence option and the parent→worker env wire rename (`yolo` → `fenceRetired`, `IKNOW_YOLO` → `IKNOW_FENCE_RETIRED`), and 44 test files pin the old names (`specs/yolo-mode.md` §Test disposition). Undoing it later is a second decision chain over the same surface, not a revert.
- **Surprising without context** — a reader of `policy.ts` and ADR-0139 sees a fence flag writing the permission axis while the mechanism ruling says the axes never write each other, and sees `exit()` clearing state it cannot find a snapshot for. Both look like bugs and would be "fixed" back into the ADR-0139 shape without this record.
- **A real trade-off** — the four rejected options above are live alternatives (value-comparison guard, keeping 0139 and naming a third posture, per-axis clear, an unnamed second switch), and the ruling-3 narrowing is traded against keeping ADR-0139 §2's posture reachable — which is why it is disclosed instead of inherited.

## Consequences

**Positive**

- The fence layer has one auditable input, and the coupling that made every unfenced entry answer to the name `yolo` is gone: `--no-sandbox` spawns inherit the fence state without being labelled YOLO.
- F4 cannot recur by construction rather than by a guard, and the two channels that collided (overlay → memory, `/config` → settings) are now mutually exclusive by ruling 3.
- `--yolo` regains the posture its issue-#1035 name promised while ADR-0139's separation of concerns survives, because the coupling moved to the layer where it is a _declaration_ (the preset) instead of a _side effect_ (the fence).
- The marker is derived from the effective configuration, so a live bare descendant keeps saying "no sandbox" after the preset that spawned it left — which is honest, and was unsayable while one holder bit did both jobs.

**Negative / trade-offs**

- `--yolo` no longer means what it has meant since 2026-10-06: it becomes a strictly more permissive entry, and every sentence that asserted the opposite (`src/cli/usage.ts:119-120`, `:130`, `src/tui/yolo-picker.tsx:32-51`, `YOLO_ENTER_TEXT` / `YOLO_EXIT_TEXT` at `src/harness/sandbox/yolo.ts:217-228`) becomes false in the same change. A mode change that leaves the interface asserting something untrue is not a partial change (ADR-0139 §1's own standard, applied back at it).
- `--no-sandbox` is a new, strictly dangerous flag whose entire defense is the entry enumeration plus the marker, and its name invites exactly the "sandbox was probably optional anyway" reading ADR-0097 exists to prevent. The mitigation is ruling 7's guardrails plus ADR-0130 §5-style naming: any number or log produced under it must name the posture.
- Renaming the fence option and the env wire touches a wide test surface: **44 files** in `tests/` match `yolo` / `YOLO` (41 specs + 3 helpers), of which the field-name and argv-contract pins must be rewritten; the disposition table is in `specs/yolo-mode.md`. Twelve of them are CI-excluded (the six yolo-named ones at `vitest.ci-excludes.ts:355-358`, `:363`, `:368`, plus six incidental bash / egress / pty files at `:56`, `:87`, `:191`, `:193`, `:303`, `:393`), so a rename that leaves the exclude list stale can go unnoticed.
- Two derived markers plus a preset state is more display logic than one red token, and it depends on state that does not exist yet (spawn-time fence registration, ruling 5) — the marker is only as honest as that registry.
- Ruling 3 requires a new permission write-back to settings, i.e. a mode change that used to be memory-only becomes durable. That is the operator's stated intent (a `/config` choice wins), but it puts `full_auto` on disk where ADR-0090's project-layer prohibition must keep holding, so the new channel is user-layer only and its patch value domain needs the fail-loud shape `src/config/persist-settings.ts:278-291` already has for `fsMode`.
