# 0137. Verify and the core loop read goal activation; the goal feature does not own the loop's terminal vocabulary

Date: 2026-10-05
Status: accepted

**Implementation state:** Accepted boundary; the shared activation predicate is landed in the goal layer, the four inlined copies outside `/continue` read it, and `isPinnedUserGoal` remains the deliberately narrower question layered on that predicate rather than a second copy. The active contract is [verify trust boundary and goal decoupling](../../specs/verify-trust-boundary-and-goal-decoupling.md).

## Context

The goal-activation condition is written five times across four files: `src/cli/chat-session.ts:915` (inside `resolveVerifyDispatch`, docstring `:884-901`, the store-load-throw path fail-closed to HITL at `:920-922` with an `EXIT:` comment), `src/session-api/hub.ts:2536` (the negated form gating a compact `boundaryAttachment` task excerpt), `src/session-api/hub.ts:2650-2659` (the same condition evaluated twice in one ternary pair for `completionMode` and `userText`), `src/session-api/continue-pending.ts:96-100` (`isPinnedUserGoal`, the only copy that also requires `goal.source === "user_pin"`, called at `:79` to emit the `goal_active` exit), and `src/session-api/goal-auto.ts:303-307` (`activePinnedGoal`, the fifth copy the spec did not name, used by `withActiveGoal` at `:375`). Two of these are not the same predicate — `isPinnedUserGoal` and the bare `text.length > 0` copies diverge on the `source` clause — and that divergence is the concrete evidence that the rule was never written down anywhere. The code also contradicts the product wording ADR-0024 line 6 set down: `"auto mode" in this document = the goal feature (continuation after a slash-pinned mission), not the permission mode full_auto`; the same collision is named again by ADR-0073 rule 2, `"wired via the flag completionMode === \"auto\" — that is the goal feature module, not an \"automatic mode\"`. `GoalSource = "user_initial" | "user_pin"` (`src/session-api/store/schema.ts:95`), and per `docs/CONTEXT.md:376` a `goal` is written only by `/goal` (`source = user_pin`). This ADR records the missing module boundary; it does not restate the spec's success criteria.

## Decision

1. **One activation predicate, owned by the goal layer.** The goal layer exports a single predicate over the loaded session that answers exactly one question — "is the goal feature running" — defined as a non-empty `goal.text`. Its return also carries the `userText` (`goal.text`) the two dispatch sites currently recompute from the same condition. `resolveVerifyDispatch`, the hub verify dispatch, the compact task-excerpt suppression, and the auto-loop activation all READ this predicate; none inlines the condition a second time. This keeps ADR-0024 line 10's mechanism intact — `"one shared read-only judge system, two logic modules … pinning /goal starts an auto loop where task is only goal.text"` — while changing only how the boundary is reached.

2. **Reading activation never carries terminal vocabulary.** The predicate says only whether the goal feature is running; it never selects or implies the core loop's terminal outcome. Neither the goal layer nor the goal layer's absence may dictate that vocabulary. `not_run` stays an evidence fact produced inside the verify loop (ADR-0073 rule 3; `docs/CONTEXT.md:616`): it maps to persisted `goal.status: "active"` and keeps the auto loop running, and it is not minted by the goal feature or by the goal feature's absence. A goal that is absent, empty-text, or a store-load throw is neither `not_run` nor a pass — it is HITL with `userText = query`, fail-closed on the throw path (`src/cli/chat-session.ts:920-922`). The goal feature is not a mode and does not enter Shift+Tab (`docs/CONTEXT.md:373`), and the permission axis stays orthogonal to it (`docs/CONTEXT.md:854`: `自动模式是权限；goal 功能是斜杠钉使命后的续跑。正交，可同时开`).

3. **`isPinnedUserGoal` is kept a deliberately narrower question, not folded.** The shared activation predicate requires only non-empty `goal.text`; the two dispatch sites read activation today without checking `goal.source`, so a legacy goal carrying `source: "user_initial"` still activates them. `/continue` asks a narrower thing: it rejects continuation with `goal_active` only for a user-pinned goal (`docs/CONTEXT.md:853`: `continue 是 HITL 同一会话 skip-append；/goal 钉着则拒绝（goal_active）…`). `isPinnedUserGoal` therefore stays `activation predicate ∧ goal.source === "user_pin"`, expressed on top of the shared predicate — sharing the non-empty-text rule and adding only the source clause — rather than as a second inlined copy. Folding the clause in either direction changes observable behavior: requiring `user_pin` in the shared predicate would stop the two dispatch sites from firing for legacy `user_initial` sessions, and dropping the clause from `isPinnedUserGoal` would make `/continue` trip `goal_active` on a non-empty `user_initial` goal, contradicting `tests/session-api/continue-pending.test.ts:143` (which asserts a `source: "user_initial", text: "legacy seed"` goal does NOT trip `goal_active`). The current product never writes `user_initial` — the sole goal writer emits `source: "user_pin"` at `src/session-api/store/schema.ts:428` — and it survives load only from legacy files (`src/session-api/store/schema.ts:154-156`), so keeping the source clause narrower leaves every `/continue` exit and every dispatch exit byte-identical.

## Consequences

- The five inlined copies (four files) collapse onto one exported predicate, and the source clause remains one expression layered on that predicate rather than a duplicated copy — so "one rule, one expression" holds even though two consumer questions differ in width.
- Observable behavior is unchanged: the `goal_active` `/continue` exit, the two dispatch `completionMode`/`userText` bindings, and the `not_run` → `goal.status "active"` mapping all stay byte-identical; the goal-mode `not_run` arms (`OUTCOME_TO_STATUS` and `earlyStopDecision`) keep typechecking.
- The boundary is recorded but not enforced by types: any future consumer that wants a "mode" word from either axis is the boundary's own evidence that it was still not written down, per the spec.
- Reversal cost is cross-file and mechanical (renaming the goal-axis vocabulary) with no change to the persisted verify wire DTO, which still parses only `outcome` / `rounds` / `notRunReason`.

## Why this shape

- Five inlined copies across four files, and a `source`-clause divergence that no single copy owns, is a missing module rather than de-duplication: one predicate, read-only by its consumers, is the smallest thing that makes the boundary survive a second call site.
- A feature's activation is not a completion-judge switch, and its absence is not an evidence fact: keeping the terminal vocabulary with the loop prevents the "no goal ⇒ manufactured pass / `not_run`" derivation the code contradicts today.
- Keeping `isPinnedUserGoal` narrower preserves "one rule, one expression" (the source clause is layered on the shared predicate, not duplicated) while guaranteeing the `/continue` and dispatch exits stay byte-identical — `continue-pending.test.ts:143` is the pin that proves the source clause cannot be folded without changing observable behavior.
