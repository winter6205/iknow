# 0131. Classify sensitive-path evidence before denying shell commands

Date: 2026-09-30
Status: accepted

Issue #1170 showed that the command-level sensitive-path wall treats a fragment in `process.env.NODE_OPTIONS` as a file path because it scans the remaining command text as one string. A fragment match is evidence to classify, not by itself a confirmed path target. For an `ok` shell parse, confirmed sensitive-path access or modification intent is a non-overridable hard deny; proven non-path code or inert data returns no finding from this wall and continues through ordinary permission handling; security-relevant content whose target or ownership cannot be established requires ADR-0127's per-call Security review requirement, with a typed deny when no interactive route exists. The shell parser supplies syntax positions, not the effects of arbitrary interpreter source; code-bearing regions are inspected, but their mere inclusion in the scan is not proof of access. Confirmed nested shell commands still deny. ADR-0124's non-`ok` verdict destinations remain unchanged.

This amends the whole-remaining-text judgment in `specs/hard-wall-ast-migration.md` SC-S2-7 and its pinned examples where mere occurrence was treated as access. The existing `SENSITIVE_PATH_FRAGMENTS` roster remains the candidate inventory; this decision does not add fragments, re-anchor end-of-command patterns per operand, or merge the command wall with the canonical read policy or the interpreter-independent effect boundary. The downstream specification must define positive evidence for each confirmed or non-path classification, keep the permission wall and Bash handler on one shared result, and record every changed deny in a differential review. A narrow `.env.` string exception was rejected because it leaves the matching-domain error intact; shell-path-only matching was rejected because it silently drops the current inspection of code-bearing regions.
