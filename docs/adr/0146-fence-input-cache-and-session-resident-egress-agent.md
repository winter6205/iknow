# 0146. Fence-input cache + session-resident egress agent: cache the mask plan, split the egress seam into an agent and a per-call endpoint

Date: 2026-10-19
Status: accepted

## Context

Two costs were paid **per foreground bash call**, both inside the fence assembly:

- The **credential read-mask plan** was recompiled on every assembly. `credentialReadMaskArgs` walks each credential subtree (`~/.ssh`, `~/.aws`, …) with synchronous `readdirSync` / `lstatSync` and re-mints the placeholder cover directories, on every call.
- The **egress seam** was built and destroyed on every call: the durable CA was loaded, a fresh trust-bundle file written, the credential layer minted, a proxy started on a unix socket, and the whole thing torn down at call teardown.

PR #1250 already removed the _blocking_ workspace walk — the protected-target name roster became an awaited enumerator so the UI thread stops freezing — but it explicitly did **not** remove the per-call recomputation. Its own landing note records that `materializeProtectedTargets` still re-reads changed listings synchronously, and that the awaited arm costs wall clock per assembly. #1250 changed _where_ the walk runs, not _how often_ the fence inputs are recomputed. This ADR removes the **credential read-mask plan** recomputation that #1250 left behind: the plan is compiled once per session and reused while its inputs are unchanged. It also removes the **protected-target enumeration's** per-call re-walk: the _walked snapshot_ is now cached per session and checked for freshness on every use (see Decision 1's "What IS cached" and the negative trade-off below) — the enumeration is no longer re-run per call, and the "a newly appearing credential file is protected on the next call" property is kept **literally**: a changed tree discards the snapshot and the assembly walks fresh, so the new credential is masked by that very call.

## Decision

**1. The credential read-mask plan is cached in a session-scoped holder.** The holder is created once per bash-tool instance (the factory closure), and passed **explicitly** to the fence factory as `BwrapFenceOptions.maskCache`. There is no module-level cache: a plan never outlives the session that produced it, and two sessions never share one.

- **Cache key** = a content digest of the plan's _real_ inputs: the inventory's credential-arm entries, the materialized name-rule matches, the egress bind table, and the session tmp root. A changed inventory or a changed materialized set therefore produces a different key — a cache miss, not a stale plan.
- **Invalidation** = the fs identity (`dev`, `ino`, `mtimeNs`, `ctimeNs`, `size`) of every path the plan depends on, re-`lstat`ed on each use. For a subtree rule the identity is captured at **directory** granularity — every directory the walk traversed — because the mask's file _set_ under a subtree is observable through those directories' mtime/ctime (any add, remove, or retype mutates the containing directory). Masking is per-path, so a file's content change cannot change the plan. `lstat` never follows symlinks, and the mask never lists symlinks, so a symlink target is not an observable of the plan. A path whose `lstat` fails for a reason **other** than ENOENT (EACCES / EIO / ENOTDIR …) is an **unknown** observable, never "the path does not exist": it is recorded as unreadable and never validates as unchanged, so the plan is rebuilt instead of being served on top of a path that could not be read (fail-safe direction: any doubt → rebuild).
- **What IS cached (the protected-target walked snapshot)**: the enumeration's _walk_ — the matches it found plus the directory identities it recorded (`dev`/`ino`/`mtimeNs`/`ctimeNs`) — is cached in its own session-scoped holder (`createProtectedTargetSnapshotCache`, `protected-targets.ts`), created once in the bash factory closure and threaded to `prepareProtectedFenceWiring` the same way `maskCache` is. The holder caches the walk, **never a decision**. A reused snapshot is checked for **freshness**, by a **stat-only identity pass** over the walked directories: every walked directory whose fs identity is unchanged has an unchanged listing, so the tree is provably the tree the snapshot was walked from and the snapshot's match set is exactly what a fresh walk would produce — the snapshot is reused, **no listing is re-read** and **nothing is refused**. Any walked directory that changed (a changed listing, a replaced directory, one that vanished) makes the snapshot **stale**: the holder discards it and the assembly takes the ordinary fresh-walk path — the awaited `prewalkProtectedTargets` and then the ordinary materialization — which is exactly the path the fence takes without a holder, so a credential that appeared under the protected subtree is found by that walk and **masked by that very call**, and the call succeeds. **Cache key** = the frozen home root + the frozen workspace root (the name-rule scan scope) + the enumeration bounds; the consume site's existing `sameLimits` check still rejects a snapshot walked under different bounds. The holder re-parks the snapshot for one assembly at a time, so the one-shot contract of the parked walk (`awaitedWalks`) is unchanged: each assembly consumes exactly one parked state, and no state is left behind that a later assembly could consume unnoticed. The holder hands back the **inventory it walked** (not a fresh one) because the materialization compares the snapshot's matches against the assembly's own name-rule objects by identity, so the two must be the same objects for that comparison to mean what it was written to mean.
- **Ordering**: on the **fast path** (the snapshot is fresh) the stat-only identity pass is the last filesystem pass before the bind composition — it runs inside the materialization, synchronously, with **no `await` between it and the binds**, so a credential cannot appear between the check and the mount. On the **slow path** (the snapshot is stale) the awaited pre-walk remains the last await before the fence is built, and the fresh walk's own listing re-read (the walk-race refusals) still runs unchanged. The fresh-walk path's refusal semantics are untouched: "new protected match", "unscanned child directory", "replaced object", the vanished-match handling and the enumeration bound behave exactly as before, because on that path they protect against a credential appearing _during_ the walk.
- **The "newly appearing credential" property, literally**: a credential path that appears under the protected subtree after the walk is **masked by the next call** — the stale snapshot is discarded, the fresh walk finds it, and the assembly binds it. It is never served from a stale match set, and never refused where the uncached fence would have assembled. The plan's invariant ("新增凭据后，下一次调用必须已被遮蔽") therefore holds as written, and the cached path protects **exactly** what the uncached path protects.
- **What is NOT cached**: the bwrap availability probe (re-checked per call), the fence-retirement decision (frozen per call at the handler entry), and **every decision derived from the enumeration** — the mask plan's own compile result is cached as described above, but the protected-target _materialization_ (which paths are bound this assembly) is recomputed from the snapshot on every assembly. The materialized set is what makes "a newly appearing credential file is protected" true, so it is never cached as a set.
- **Deviation from the plan text**: the plan's "secretRegistry version" key component is **dropped**. The secret registry is a _value_ map (command restore + output mask) and never influences which paths get masked; there is no runtime credential-path registry to version. The plan text is wrong here and the code is authoritative. The same ruling applies to the protected-target snapshot holder's key: it has no secret-registry version either.
- `fenceRetired` is **not** part of any cache: it stays frozen per call at the handler entry, and the retired path returns bare argv before the mask or the snapshot holder is consulted at all. The bwrap availability probe is likewise not cached — it is re-checked per call.

**2. The placeholder cover directories are reused, with owner and mode validated.** The deterministic fallback cover directory is created `0700` (today it is default-umask) and the gh default-config directory is validated for owner _and_ mode before reuse. A directory that does not match is never reused and never mutated; a fresh one is minted instead.

**3. The egress seam is split into a session-resident agent and a per-call endpoint.** This is the load-bearing shape:

- The **agent** (`src/harness/sandbox/egress/agent.ts`) is engine-scoped, and its **profile** is lazily started. It owns the expensive half: relay resolution, the ssh-agent verdict, the proxy auth token, the durable CA load + trust-bundle write, and the credential mint (sentinel registry, masked file store, masked binds). It loads that profile **once**; a failed start surfaces the typed error, creates no seam, and never degrades to a direct connection. (The agent OBJECT is created eagerly with the engine; only the profile behind it is loaded on the first call — see the Teardown paragraph below, which states the same thing. "Lazily started" here means the profile, not the object.)
- The **endpoint** (`EgressCallEndpoint`) is per call: a fresh unix socket whose path carries a one-shot call id, mode `0600`, bound into _that_ call's netns; its own proxy instance whose filter closure carries _that_ call's policy; its own violation sink; and its own fence spec.

**Why the split — the plan's own T4 and T5 requirements are mutually unsatisfiable as written.** The upstream package (`@anthropic-ai/sandbox-runtime` 0.0.76, `dist/sandbox/http-proxy.js`) closes over **one** `options` object, therefore **one** `filter` and one sink channel, per proxy-server instance. A single long-lived proxy server therefore cannot carry a per-call policy and per-call violation attribution _unless_ the per-call identity is read out of a request header — and the plan explicitly forbids that ("按调用策略与违规记录挂在子 socket 上，不读请求头标识"). Reconciling the two constraints forces the two-level shape above.

Consequence, accepted and documented: a proxy-server _instance_ is still created per call (it is cheap — `createServer()` + `listen` + `chmod`). What is no longer created and destroyed per call is the expensive profile. The plan's headline acceptance for T4 — "CA 与配置只加载一次" — is met exactly.

**Per-call vs session-level spec fields.** The endpoint's spec differs from the agent's in exactly two fields: `unixSocketPath` and `innerBridgeScript` (the in-fence bridge script embeds the socket path). `env`, `sandboxLocalPort` (3128), `relayAssetsDir` and `sshAuthSockPath` are session-level; `binds` in particular is **session-level** — it is the masked-credential bind set from the single mint, and the credential-read-mask layer consumes it.

**4. The proxy-auth challenge frame is corrected in the adapter layer only.** `src/harness/sandbox/egress/upstream.ts` is the single place allowed to deep-import the package; the 407 fix lives there and nowhere else. The upstream answers a CONNECT without valid `Proxy-Authorization` with a header-only 407 frame and then closes the socket, with neither `Content-Length` nor `Connection: close`. git's transport is libcurl, whose default `http.proxyAuthMethod=anyauth` sends the first CONNECT _without_ credentials and retries _with_ credentials on the same connection per HTTP/1.1 keep-alive semantics — but the proxy has already closed it, so git fails with `Proxy CONNECT aborted`. The curl CLI is unaffected (its credentials ride in the proxy URL userinfo, so its first CONNECT already carries them). The adapter rewrites **only** that one frame to declare an empty body and a finished connection; every other frame (403 deny, 400, 502, the 200 tunnel response, tunnel payload) passes through byte-identical. **Authentication is not relaxed**: a CONNECT without valid credentials still gets 407, and the allowlist still decides which domains are reachable. No dependency was added, no package was patched, and no bypass environment variable (e.g. `GIT_HTTP_PROXY_AUTHMETHOD`) was introduced.

**5. The background task rides the shared agent; the verify route keeps its own path.** The background manager creates a **per-task endpoint** from the shared agent (released at the same points the session was released: task settle, the abnormal spawn paths, and the shutdown fallback) and the agent's profile is loaded once for N tasks. The verify route is deliberately **left as it is**: the plan offers this choice explicitly, the verify route is not production-wired for a policy (neither the hub nor the chat session passes `egressPolicy` into `runVerifyLoop`, so the verify seam never starts a proxy in production), and the verify runner's lifetime is _per verify round_, so an engine-scoped agent would be created and destroyed per round — defeating the purpose. A stale comment in `verify-loop.ts` that described the verify seam as a "module-level per-session singleton" was corrected to describe what the code actually does.

**Teardown.** The engine's composite `shutdown` disposes the agent (closing any still-live endpoints first, then releasing the credential layer). The agent is engine-scoped, not conversation-scoped: in serve/hub the engine is cached per root and shared across conversations, so there the agent is root-scoped. The agent is created eagerly but loads its profile lazily, so an engine that never makes an egress-eligible call pays nothing. A **released** agent is a lifecycle fault, not a start failure: a background spawn against it fails with the typed `egress_agent_released` refusal (the task is not spawned) instead of degrading into a task that silently runs without its egress seam, and the foreground bash path aborts before the fence exists.

## Consequences

**Positive / Applied:**

- The credential subtrees are walked once per session instead of once per call, the protected-target scan scope is walked once per session instead of once per call, and the CA + credential mint happen once per engine instead of once per call.
- Violation attribution is now exact: each call's sink holds only the violations that call produced, and the bash tool drains that call's sink.
- The 407 correction makes `git` over HTTPS work through the seam without relaxing authentication or widening the allowlist.

**Negative / Trade-offs:**

- The upstream package's one-filter-per-instance binding is now load-bearing: any future attempt to collapse the endpoint back into a single long-lived proxy server would have to reintroduce a request-header identifier, which this ADR forbids.
- The mask cache holds a **single** entry, not a map: a session that alternates between two different plan keys rebuilds on every switch. The saving materialises when consecutive assemblies share a key.
- The protected-target snapshot holder holds a **single** entry as well, and its key includes the home root, the workspace root and the enumeration bounds: a session that changes its scan scope walks again.
- The protected-target saving is the **walk**, not the decision: every assembly still re-`lstat`s every walked directory (the stat-only identity pass) and re-derives the bind set, and the fast path pays that identity pass twice — once to route (fresh vs. stale) and once inside the materialization, immediately before the binds. A changed tree is a **re-walk**, not a refusal, so a credential that appears under the protected subtree costs a walk (the awaited one, exactly as before this ADR) and is then masked by that very call.
- A race no stat pass can close — the tree changes between the holder's identity pass and the materialization's — falls back to the ordinary synchronous enumeration inside the materialization, so the credential is still masked by that call, at the cost of a blocking walk in that one case.
- The agent is engine-scoped, so in serve/hub it is shared across the conversations of one root.

## Follow-up

**The legacy per-call egress session path is deprecated, not yet removed.** `createEgressSession` (`src/harness/sandbox/egress/session.ts`) is the **fallback** for an assembly that was handed **no** agent — the compatibility path, which the worker / ask assemblies take only when their registry is built without one (`src/harness/aci/tools/registry.ts`, `egressAgentSpread`). In production the agent IS handed to them: `buildHarnessEngine` creates one agent and passes the same instance to the main registry, the ask registry, the worker base-tools registry and the background manager, so the worker / ask assemblies run on the **agent** path, not the legacy one. The legacy path also still serves the background manager's own unit tests (which run without an agent, through `adaptLegacyTaskSession`). The two models therefore have different teardown semantics — the legacy session releases the credential layer itself, while the agent releases it once for the whole session. The follow-up is named explicitly: **retire the legacy per-call session path once the compatibility path is dropped** (the worker's own unit tests must be moved onto the agent path before `createEgressSession` can go). Until then both paths stay live, and the legacy path is the fallback — not the production seam.
