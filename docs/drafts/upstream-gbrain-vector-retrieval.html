GBrain 向量检索技术栈全景

分析对象：_upstream_gbrain/（garrytan/gbrain v0.42.57.0，commit 058f448）· 方法：codebase-memory 图谱 + 4 路并行子代理源码深挖 + hybrid.ts 逐段交叉验证

核心认知：GBrain 的检索不是"向量搜索"，而是四路召回 + 多级重排的混合栈。官方理念：单一策略都会失败，四层叠加才互补——向量（语义）+ BM25（词法）+ RRF（融合）+ 知识图谱（关系）。

§1 写入侧：文本 → 向量

从源文件到 pgvector 落库的完整链路

1.1 分块（Chunking）策略

生产主链路只有两条，并非"可配置 chunker 框架"。semantic.ts 和 llm.ts 虽然实现完整，但未接入生产 ingestion。

recursive 分隔符优先级（段落→行→句→从句→词→字符）递归切分 + 贪心合并 + 重叠 + 6000 字符硬顶 chunkSize=300词 / overlap=50词 / maxChars=6000 ✅ 文本默认

🔧 开发要点
  • compiled_truth 与 timeline 分别独立分块并打 chunk_source 标记——这是读取侧 ×2.0 boost 的数据基础。
  • 分块带版本号（MARKDOWN_CHUNKER_VERSION=3 / CHUNKER_VERSION=4），写入 page，升级后触发重分块/重嵌。
  • recursive 写入前做隐私预处理：剥离 takes fence、仅保留 world 可见 facts（recursive.ts:58-88）。
  • 字符硬切分本身带重叠：overlap = min(500, maxChars/10)，默认 6000 字符时 overlap 500。

1.2 Embedding Provider 抽象（Gateway + Recipes）

这是接 LLM/embedding 的唯一正确入口。纯数据配方 + 静态工厂模式。

📋 Recipe 声明内容（纯数据）
  • provider id/name、implementation 类型（native-openai / openai-compatible / native-google / native-anthropic）
  • 默认 base URL、API key 环境变量名（如 OPENAI_API_KEY）
  • 支持的 embedding models、默认维度和可选维度
  • max_batch_tokens、chars_per_token（默认 4）、safety_factor（默认 0.8）
  • 是否支持 multimodal

非对称编码

ingestion 用 embed()（document 编码），查询用 embedQuery()（query 编码）。Voyage/ZeroEntropy 等非对称模型靠此区分。

维度协商

opts.dimensions → config.embedding_dimensions → DEFAULT（当前通用 1536）

provider 返回后逐向量校验长度，不符即抛配置错误（gateway.ts:1582）。

Batch 策略（两层）

层 机制 参数
外层 embedBatch 每 100 条分页（进度粒度） BATCH_SIZE=100
内层 gateway 按 provider token 预算 splitByTokenBudget，每条先截 8000 字符 budget = max_batch_tokens × safety_factor

provider 报 batch 超限 → 对半递归 + safety_factor×0.5；连续成功 10 批后 ×1.5 恢复。

不做统一 L2 归一化：gateway 仅 new Float32Array(e)，是否单位化取决于 provider。cosine 算子本身按范数计算，故不依赖归一化不变量。别假设"provider 返回单位向量"。

2.1 四路召回详解

臂 实现 算子/机制 top-k 策略
向量 engine.searchVector pgvector cosine <=>，HNSW 候选 CTE innerLimit = offset + max(limit·5, 100)
关键词 engine.searchKeyword search_vector @@ websearch_to_tsquery 过滤 + ts_rank 打分（无 trigram） innerLimit = min(limit·3, MAX·3)

向量召回两阶段 CTE

-- postgres-engine.ts:1927
WITH hnsw_candidates AS (
  SELECT ..., 1 - (cc."embedding" <=> $1::vector) AS raw_score
  FROM content_chunks cc JOIN pages p JOIN sources s
  WHERE cc."embedding" IS NOT NULL AND cc.modality = 'text'
  ORDER BY cc."embedding" <=> $1::vector   -- 裸距离，让 HNSW 生效
  LIMIT $innerLimit
),
best_per_page AS (
  SELECT DISTINCT ON (COALESCE(source_id,'default'), slug) *
  FROM hnsw_candidates
  ORDER BY ..., score DESC                  -- 按页取最优 chunk（max-pool）
)
SELECT ... FROM best_per_page ORDER BY score DESC LIMIT $limit
🔧 开发要点：max-pool 设计

DISTINCT ON (source_id, slug) 确保向量侧返回 N 个不同页面（每页最优 chunk），而非 N 个 chunk 在下游折叠成更少页面。复合键含 source_id 防跨源误并。

2.2 意图分类（零 LLM）

query-intent.ts:248 classifyQuery：纯正则，优先级 full_context > temporal > event > entity > general。输出 QuerySuggestions { intent, suggestedDetail, suggestedSalience, suggestedRecency, suggestedModality }。

仅在 cross_modal_llm_intent: true + 正则返回 'text' + 查询模糊时，才触发 Haiku 1s 超时的 LLM 模态裁决（llm-intent.ts:37），频率 <1%。

2.3 查询扩展（LLM）

expansion.ts:57 expandQuery：仅当 mode expansion=true（tokenmax）+ 词数 ≥3 时触发。生成 2-3 个同义改写变体，原 query 始终在首项。双向 sanitization 防注入。

2.4 关系召回（图遍历）

relational-intent.ts:222 parseRelationalQuery：纯正则，4 种 kind（who_rel/who_at/connects/intro）。命中后 buildRelationalArm + engine.relationalFanout 走 typed-edge 图，注入边推导答案到 RRF。非关系查询纯 no-op。

2.5 Two-Pass 结构检索

two-pass.ts：仅当 walkDepth>0 或 nearSymbol 设置时激活。从锚点集出发，沿 code_edges_chunk + code_edges_symbol 表走 1~2 跳（MAX_WALK_DEPTH=2，每跳邻居 cap 50）。邻居分数 = anchor.score / (1+hop)。

3.1 RRF 加权融合

score(chunk) = Σ 1/(k_i + rank_i)    其中 k_i = RRF_K / weight_i，RRF_K = 60
normalized = raw / max(raw)  →  boosted = normalized × (2.0 if compiled_truth else 1.0)

实现：rrfFusionWeighted（hybrid.ts:1860）。每路独立 k，intent 权重 >1 → k 降低 → 该路 top 排名更陡。

融合键（防跨源误并）
function rrfKey(r: SearchResult): string {
  return `${r.source_id ?? 'default'}:${r.slug}:${r.chunk_id ?? r.chunk_text.slice(0, 50)}`;
}

3.2 Cosine 重打分

final = 0.7 · normRRF + 0.3 · cosine(query_emb, chunk_emb)

实现：cosineReScore（hybrid.ts:1951）。关键：从 HNSW 实际使用的同一向量列 hydrate embedding 重算（getEmbeddingsByChunkIds(col)），避免 Voyage 检索却拿 OpenAI 向量重算导致 NaN/错排。

§4 后处理与重排

dedup → rerank → alias hop → evidence → adaptive → autocut → budget

4.1 Dedup 四层去重

dedup.ts dedupResults，默认 cosineThreshold=0.85 / maxTypeRatio=0.6 / maxPerPage=2：

  1. 每页 top3：按复合 pageKey (source_id, slug) 每页按 score 保留 top3
  2. Jaccard 去重：chunk_text lowercase words 的 Jaccard > 0.85 → 删除
  3. type 比例：maxPerType = ceil(len × 0.6)，超额丢弃
  4. 每页上限：maxPerPage=2

末了 guaranteeCompiledTruth：若某页没有 compiled_truth chunk，从 preDedup 同页挑最高 compiled_truth 替换该页最低分 chunk。

4.2 Cross-Encoder Rerank

全错误 fail-open 原序返回。官方基准：reshuffle 60% 的 top-1。

4.3 Alias Hop

hybrid.ts:636 applyAliasHop：query normalize 后 exact match（最多 6 tokens），命中已有 canonical → score ×1.10 + alias_hit 标记；缺失则注入 canonical page（score = topScore + 1e-6），最多 3 个。

4.4 Evidence 契约

evidence.ts stampEvidence：每条结果带两个字段：

evidence create_safety 含义
alias_hit exists 别名精确命中
exact_title_match exists 标题精确匹配
high_vector_match（≥0.85） exists 高向量相似
keyword_exact（≥0.6） probable 关键词命中
weak_semantic unknown 弱语义

agent 判"是否已存在、可否不写重复"靠 create_safety，不靠裸分数。

4.5 Autocut 评分断崖

autocut.ts：基于 rerank_score（非 RRF/cosine）找最大归一化分差。gap ≥ 0.2（jumpRatio）则断崖截断，minKeep=1，永不空。

4.6 Token Budget

token-budget.ts：tokens = ceil(len/4)，自顶向下贪心，超预算即 break。mode 默认：conservative 4000 / balanced 12000 / tokenmax off。

4.7 语义缓存

query-cache.ts SemanticQueryCache：HNSW 最近邻查 query embedding，distance < 0.08（即 similarity > 0.92）+ TTL 3600s + knobs_hash + 页面 generation gate（防 stale）。

缓存跳过条件：disabled / walkDepth>0 / nearSymbol / 非默认 embedding 列 / adaptiveReturn enabled。

7.2 陷阱清单（必读）

  1. 官方 RETRIEVAL.md 流程图过时：真实顺序是 dedup → rerank → adaptive/autocut → slice → budget，以 hybrid.ts 为准。
  2. src/core/storage/ ≠ 数据库：那是对象存储（local/S3/Supabase）；DB 引擎在 pglite/postgres-engine.ts。
  3. backfill embedding_voyage 是 no-op：补主文本向量用 gbrain embed --stale。
  4. embedding-column write-path 未完成：registry 当前主要是搜索侧路由；写任意自定义列不能假设已就绪。
  5. semantic/llm chunker 未接入生产：仅定义，挂接需改 import-file.ts。
  6. 不做统一 L2 归一化：别假设"provider 返回单位向量"是强不变量。
  7. 缓存污染防御：knobs_hash 折了 mode/列名/provider/relational 深度；改任一 knob 需同步 KNOBS_HASH_VERSION。
  8. 改 SQL/索引必须双引擎同步：pglite 与 postgres lockstep，由 parity 测试 pin。
