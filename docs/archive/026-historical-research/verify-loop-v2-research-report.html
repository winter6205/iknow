摘要

摘要

Abstract

Agentic loop 的验证闭环（verify-loop）决定「模型产出是否被判定为完成」。v1 采用 单候选串行修正、纯 maxRounds 预算、单判官 LLM 判定——三个维度均与 2023–2024 年的 测试时计算（test-time compute）与 LLM-as-a-Judge 研究结论相悖。verify-loop v2 以论文交叉验证驱动设计：对同一 command 做 K 次验证采样并做 self-consistency 聚合 （best-of-N），用多判官 majority 替代单判官盲信，以 rounds/tokens/costUsd/wallMs 四元组预算替代纯 maxRounds，并让真实执行（exit + signature）先于 LLM 判定（execution-first）。 本原型保持 v1 的 advisor 包裹形态与引擎零改动约束，验证新一代状态机；若通过可 lift 进生产。

1 · 一致性　self-consistency majority voting（Wang et al. 2023）
2 · 预算感知　optimal frontier → budget-aware 决策（Snell et al. 2024）
3 · 采样饱和　固定 N 无 cap 是反模式（Brown et al. 2024）
4 · 自修正陷阱　无外部 verifier 的 self-correction 会失败（Huang et al. 2023）
5 · 判官瓶颈　judge 准确率 ~75% → multi-judge pool（Tan et al. 2024）
6 · 多样性　judge 去相关，多样性 > 单判官（Nine Judges, Two Effective Votes）
7 · 采样聚合　best-of-N multi-candidate + consensus aggregation
8 · 偏倚缓解　position-bias shuffle（Zheng et al. 2023 swap-pair 工程化）
01

研究背景

验证闭环解决的问题：Agentic loop 中，模型每轮产出后需要一个「完成判定」。判定过松则错误代码被放行，过紧则浪费 compute 反复修正。

v1（verify-loop.ts，#128）的验证模型是单候选串行撞墙： 每次失败注入一个验证失败信封，模型重新生成一个候选修复，再跑验证——直到 maxRounds 耗尽。 判定侧则主要依赖单判官 LLM。2023–2024 年的研究揭示这三条路径各有结构性缺陷：

单候选不稳定　单条 greedy / 单次采样不可靠，majority 采样显著更稳（2203.11171）
重复采样有饱和点　N-sampling 随 N 单调提升到饱和，无 budget cap 是反模式（2407.21787）
compute 分配需最优　parallel vs sequential 存在 optimal frontier，需 budget-aware（2408.03314）
单 judge 不可盲信　最强 judge 仅 ~75%，且带 position/length bias（2410.12784 / 2306.05685）
自修正缺外部 verifier 会失败　纯自我评估不可靠，需真实执行做判据（2310.01798）
多样性优于单一升级　多 judge 聚合 > 单 judge 变强（2408.02666）

verify-loop v2 以这组论文交叉验证为设计输入，将研究结论映射为五条升级点。形态上保持 v1 的 advisor 包裹 run()（引擎零改动，ADR-0011 冻结停止语义），并复用 v1 的 seam： RunVerifyFn / RunClassifierFn / VerifyConfig / TraceService。 依赖方向与 v1 相同：只消费纯函数层（consensus / judge-pool / effort-budget / verdict / inject）+ sandbox 基础层， 不 import ACI 装饰层与 settings。

报告边界：本报告为「学术依据整理与呈现」，全部内容锚定自源码头注释与上述研究结论； 论文的完整标题、作者全名等细节若源码注释未给出，则标注「引用自 verify-loop-v2.ts 头注释」，不补造细节。

04

设计决策：为什么这样设计

v2 相对 v1（#128）的五项学术升级，每项给出「论文依据 → 为什么这样设计 → 源码落点」。

升级点 1

Multi-candidate best-of-N + self-consistency 聚合

2203.11171 · 2407.21787

为什么：v1 失败修正时是单候选串行撞墙——单条候选具有随机性，一次失败不代表真实失败， 且失败后重新生成也未必收敛。Self-Consistency 证明多数采样显著提升一致性； Large Language Monkeys 证明重复采样随 N 提升。v2 将「验证失败是否为真」的判断从一次采样 扩展为 K 次采样的多数共识：全 pass 放行、全 fail 注入信封继续修正、恰好各半判 unstable （不静默放行）、分裂按 passRatio 多数决定。

锚点：verify-loop-v2.ts · checkOneCandidate / aggregateConsensus / buildMultiCandidateEnvelope

升级点 2

Multi-judge pool（3 判官 majority）

2306.05685 · 2410.12784 · 2408.02666

为什么：JudgeBench 给出最强 judge 仅 ~75%，单 judge 不可盲信； Self-Taught Evaluators 给出多 judge 聚合 > 单 judge 升级，majority 在 3–4 judge 边际收益最大 → 默认 3 判官。Judge-as-Judge 揭示 position/length/self-enhancement 三大 bias → 内置 position-bias shuffle 缓解。abstain（判不了）不参与多数计算，全部 abstain → fail-open 到不稳定上游，不静默放行。

锚点：judge-pool.ts · aggregateJudgePool / shuffleBySeed（xorshift32）

升级点 3

Effort budget 多维（rounds + tokens + costUsd + wallMs）

2408.03314 · 2407.21787

为什么：纯 maxRounds 只限制迭代轮数，无法表达 token 消耗、估算成本与墙钟时间。 Test-Time Compute 要求 budget-aware 决策；Monkeys 指出无 cap 的固定 N 是反模式 → 四元组预算 { rounds, tokens, costUsd, wallMs }，任一维度超限即 exhausted。未设置的维度不参与判定（视为无限），保持 v1 maxRounds 语义的可兼容扩展。

锚点：effort-budget.ts · initialEffort / spendEffort / isBudgetExhausted / budgetSummary

升级点 4

Confidence-based stop（dispersion 置信信号）

2408.03314

为什么：验证判定的置信度可以从候选一致性离差中读出：dispersion = 1 − |pass−fail|/N， 离差高 = 判官/候选分裂严重 = uncertainty 高，应加大采样或降级；离差低 = 高置信，可放行避免过采样。 v2 中 dispersion 已计算并记录进 record，但 stop 判定当前为纯 majority（低离差高置信放行）； dispersion 驱动的早停/加采样（shouldSampleMore：打平 → 采， dispersion > 0.5（如 2v1）→ 采，3v1（0.5）→ 边缘不采）留待 lift。

锚点：consensus.ts · shouldSampleMore / aggregateConsensus（confidence 字段）

升级点 5

Execution-first 验证分层

2302.08468 · 2304.05128 · 2306.09896 · 2310.01798

为什么：无外部 verifier 的 self-correction 会失败（2310.01798），而 LLM judge 自身仅 ~75%。 v2 让可执行命令的真实运行成为第一层判据：command 路径产 artifact（exit code + failure signature） 的结构化判定——真实、可复现、不依赖模型主观；LLM judge 仅兜底无 command 的 free-form classifier 路径。judge 判定只出现在命令不可用时的降级通道。

锚点：verify-loop-v2.ts · checkOneCandidate / buildFailureSignature（verdict.ts）

架构决策

Advisor 包裹 + 纯函数层 + 七态 outcome

对齐 v1 #128 · ADR-0011

为什么：v2 保持 v1 的 advisor 包裹 run() 形态（引擎零改动，ADR-0011 冻结停止语义）， 复用 v1 seam（RunVerifyFn / RunClassifierFn / VerifyConfig / TraceService），使新一代状态机 可在不触碰引擎的前提下原型验证。共识聚合、判官池、预算全部落在纯函数层 （零 IO 零副作用，状态由调用方持有并传入，与 verdict.ts 同纪律），可测且可复现。 outcome 七态（passed / failed / unstable / escalated / aborted / disabled / exhausted）： exhausted 为 v2 新增（预算耗尽），escalated 为 v1 向后兼容保留的 union 成员、本原型不产出。

锚点：verify-loop-v2.ts 头注释 / buildResultV2

05

原型简化与诚实的局限

本模块标注为 PROTOTYPE：验证新一代状态机，若通过可 lift 进生产；当前不替换 v1 装配（chat-session 仍接 v1）。以下简化均在源码注释中显式披露。

  1. 简化 1 · best-of-N 局限在验证层 K 候选 = 对同一 command 做 K 次验证采样（验证层 best-of-N），不是模型产 K 个候选修复。 模型侧候选采样（多候选修复再选）留待 lift。
  2. 简化 2 · position-bias shuffle 仅影响观测 shuffle 只改变判定展示顺序（观测），聚合本身顺序无关。 真实缓解需逐判官差异化输入/模型（swap-pair 双跑思路的工程化轻量版：不双跑，只改呈现顺序、减少成本）。 逐判官差异化留待 lift。
  3. 简化 3 · effort 数字为估算占位 command 候选每次采样固定计入 tokens:200 / costUsd:0.001 / wallMs:1000； judge 每次调用计入 tokens:800 / costUsd:0.004 / wallMs:5000。 均为估算占位（原型），生产应从 RunResult.usage 实测。
  4. 简化 4 · confidence-based stop 未接线 dispersion 已计算并记录进 record，但 stop 判定当前为纯 majority（低离差高置信放行）； dispersion 驱动的早停/加采样（shouldSampleMore）留待 lift，预算兜底为 exhausted。
  5. 简化 5 · judge 输出三态简化解析 判官输出以字符串包含匹配判定 "kind":"pass" / "kind":"fail"，否则 abstain； 生产走 parseClassifierResult 正式解析。
  6. 简化 6 · command 路径二值归一化 超时折叠为 fail 候选（exit≠0 同路），不含 v1 的 B13 不稳定语义通道——本原型二值归一化不含该通道， 语义与注释一致（诚实记录，见头注释升级点 5）。
  7. 简化 7 · escalated 不产出 无趋势裁判/escalate 信封注入，escalated union 成员仅为 v1 向后兼容保留， 本原型不产出；新增 exhausted（预算耗尽）。
  8. 简化 8 · 未替换 v1 装配 本模块只验证新一代状态机，chat-session 仍接 v1；v2 验证通过后可 lift 进生产。
验证路径说明：command 空 + 无 classifier → 透明关闭（disabled，rounds=0， 对齐 v1 SC7 向后兼容）；classifier 路径判定 pass / 全部 abstain / tie / 耗尽 均显式处理， abstain 与 tie 不静默放行。
