先给结论

#425 是 goal（目标）数据基础的「第一稿」：只做目标怎么存、怎么来，没有任何验证逻辑，最后关闭未合并。#433 不是建立在 #425 上，而是同一份 #408 spec 的另一条平行实现线：它在自己的分支里重做了同样的 goal 基础，再叠上「子代理 LLM 判官」，整体 squash 进了 master。合并后的今天，机制是：目标固定不变，用它验证当前结果；失败就把缺口塞回对话让模型继续修，直到通过或轮数耗尽。「换目标」这件事，始终由人决定，系统从不自动换。

Q1PR #425 具体做了什么？

CLOSED 未合并它是 issue #408（session 级 goal 机制）的第一次落地尝试，只做 T1-T3 三个任务：

T1：给 session 文件加 goal 字段（schema 从 v4 升到 v5，GoalState 类型：text / source / status / history）；T2：首条用户消息自动 seed 成 goal（source = user_initial）；T3：用户用 ## GOAL: 文本指令或 /goal 斜杠命令重钉目标（旧 goal 进 history 标记 superseded）。

注意：它不碰 verify 目录，没有验证判定，没有子代理，也没有自动换目标。它只解决「目标存在哪、从哪来」。结局：2026-08-14 关闭，作者注明 superseded by PR #432。

Q2「自动更换目标」实现了没有？

未实现没有。goal.text 只有两个写入口：首条消息 seed、用户显式重钉。类型里预留了 model_proposed 这个 source，但没有任何代码会写它（spec 原话：reserved, no writer）。

spec 还明确划了红线：判官只能写 goal.status（achieved / aborted），不许写 goal.text。验证失败时系统唯一会「换」的东西是修复思路：escalate 消息提示模型「别重复同一个修法，换个方法」，但目标文本纹丝不动。闭环每一轮复用的都是同一份 userText。

Q3「用子代理验证」实现了没有？

#425 没有#433 有子代理验证不在 #425 里，而在 #433 里，就是它标题里的「分类器（子代理 LLM 判官）」。

它是真正的子代理，不是同一 loop 里多问一次 LLM：SubAgentManager.spawn 起一个独立 worker 进程（node iknow --subagent-worker），跑一个「严格任务完成度判官」。判官被禁用 bash / edit_file / write_file / web_fetch / web_search，最多 2 个 turn，只允许输出三态 JSON：pass / fail / abort。

Q4所以它只是「设置一个目标，用它验证当前结果是否成功」？

对，就是这个机制你的理解准确。模型说「我做完了」（stopReason = completed）之后，verify-loop 拿「当前结果」对照「目标」做一次验收：

配了 verify.command（比如 npm test）就在沙箱里跑这条命令，看 exit code；没配命令，就由子代理判官读任务 + 结果来判。通过 = 收工，写 goal.status = achieved；失败 = 把缺口打包成「失败信封」伪装成用户消息塞回对话，让模型继续修，一轮一轮直到通过、趋势停滞或轮数耗尽。目标本身不参与生成、不进 system prompt，只作为「验收标准」存在。

Q5#433 跟 #425 有什么区别？是建立在 #425 上做的吗？

不是继承关系不是建立在 #425 上。git 层面证据：#425 的三个 commit（449a21a3 / aa77dee0 / 32b47fab）不是 #433 分支的祖先。两者是同一份 #408 spec 的两次独立实现，同源并行：

#425 是被放弃的第一稿（关闭）；#433 分支里经 PR #427 重新实现了同一套 goal 基础（对比两边 goal 文件，内容等价，只是 commit 不同），然后在上面叠分类器，最后连同 #128 的验证闭环本体一起 squash 成一个 commit（faaf5f37）进 master。区别一句话：#425 = 只有目标存储；#433 = 目标存储 + 验证闭环 + 子代理判官，全套。

目标在整个流程里的角色

是什么验收标准。闭环每一轮的 task 字段都是它。
不是什么不参与生成，不进 system prompt，不驱动工具层。
谁来写只有用户（seed / re-pin）。判官只写 status。
验证后pass 写 achieved，用户 abort 写 aborted，失败不改它。

子代理判官：它到底是什么

这是 #433 的核心新东西。抽象说法很多，这里全部拆成具体事实。

形态：真正的子进程，不是多问一句

怎么起SubAgentManager.spawn 起独立 worker 进程：node iknow --subagent-worker，stdin 进 JSON 任务，stdout 出 JSON 结果。
输入三个字段：task（= goal.text）、summary、finalText（模型本轮的最终输出）。
输出三选一 JSON：{kind:"pass", reason, evidence[]}、{kind:"fail", reason, missing[], evidence[]}、{kind:"abort", reason}。
护栏禁 bash / edit_file / write_file / web_fetch / web_search；maxTurns = 2；输出截断 2000 码点。
出错时JSON 烂了、pass 没证据、transport 挂了，一律降级 abort，闭环判 unstable 停下。永远不会被当成 pass。

判官的 system prompt（要点翻译）

「你是一个严格的任务完成度判官。给你一个任务，评估它是否真的做完了。只输出一个 JSON 对象，三种形状之一。规则：pass 和 fail 必须带至少一条 evidence；不许输出空证据的 pass。如果你无法确定是否完成，用 abort。」

原文在 src/harness/verify/run-classifier-adapter.ts:23-43（JUDGE_ROLE）。设计意图：判官是「只读」的，它能看、能核对，不能动手改东西，所以它的结论才可信。

什么时候走判官这条路？只在 verify.command 没配置、且 SubAgentManager 在场时。配了命令永远优先走命令路径（exit code 比 LLM 判断更确定）。ask oneshot 形态没有 manager，会退回「透明关闭」：行为等同裸 run。

verify-loop（验证闭环）点击展开

人话：模型说「我做完了」之后，系统自动给它做一次验收考试；不及格就把错题拍回去让它重做，直到及格或者考到次数上限。

精确：runVerifyLoop 包在 run() 外层，仅当 stopReason = completed 触发验证；每轮产出三态判定，true-failure 注入信封进入下一轮，pass / unstable / 耗尽则终局。

advisor 形态点击展开

人话：发动机（loop-engine）完全不知道有验收这回事。验收是一个「顾问」，站在发动机外面包了一层，出问题就拦下来重跑，发动机本身一颗螺丝都没动。

精确：verify-loop 以 runFn 委托真实 run()，loop-engine 内没有任何 goal / verify 概念，引擎零改动。

goal（会话级目标）点击展开

人话：这场会话「到底要干什么」的一句话记录。第一条消息自动当目标；你随时可以用 /goal 或 ## GOAL: 改。改的时候旧目标不删，归档进 history。

精确：schema v5 的 GoalState：text / source（user_initial、user_pin、model_proposed 预留）/ status（active、achieved、aborted、superseded）/ history。

classifier（分类器）点击展开

人话：没配验收命令时的替补裁判。请一个独立的 AI（子代理）来读任务要求和实际产出，判断「这活儿到底干完没有」。

精确：command 缺失时接管的子代理 LLM 判官，输入 {task, summary, finalText}，输出 {kind, reason, evidence?, missing?} 三态。

失败信封（envelope）点击展开

人话：验收不过时，系统写一张「整改通知单」，伪装成用户发的消息塞回对话里。模型下一轮看到它，就知道哪里没做好、要修什么。旧通知单每轮都会清掉，不会越堆越多。

精确：buildValidationEnvelope（命令路径：command / exit_code / failed_count / signature / output_excerpt）与 buildClassifierEnvelope（分类器路径：task / missing[] / reason），注入为 user 消息，下一轮 priorMessages 重建时滤除。

src/harness/verify/inject.ts:83-107

确认阶梯点击展开

人话：测试失败一次不算数，可能是偶发（flaky）。先全部重跑一遍确认，再把失败的那几个单独跑一遍定位，两级都站得住才认定是真失败。

精确：confirmFailure 两级确认：全量 rerun → rerunTemplate 单跑失败用例，产出 flaky（放行）/ unstable / true-failure。

src/harness/verify/verdict.ts

失败签名 + 趋势判定点击展开

人话：给每次失败按指纹（归一化后的错误特征），然后比较连续几轮的指纹：在进步就继续跑；同一个指纹连续两轮没变 = 原地打转，停；越修越糟，也停。防止模型在同一个坑里无限重试。

精确：buildFailureSignature 归一化输出，evaluateTrend 按进展放行 / 同签名停滞停 / 连续退化停 / 震荡宽容。

src/harness/verify/verdict.ts:209-252

escalate点击展开

人话：轮数用完了还没修好，先别急着判死刑：给模型一次「加时赛」，附带一句「别再重复同一个修法，重读任务换个思路」，预算翻倍。只给一次。

精确：onExhausted = escalate 且首次耗尽时注入 buildEscalateMessage，maxRounds 延长为 2 倍，总预算不重置。

src/harness/verify/verify-loop.ts:439-441, 664-674

透明关闭点击展开

人话：「没配置就当不存在」：既没配验收命令、又没有判官可用时，整个验收层静默消失，行为跟没装它时一模一样。这是向后兼容的保底，现在只有 ask oneshot 会走到。

精确：command 缺失且 runClassifier 未装配时，单次 run + enabled:false, outcome:"disabled"，与裸 run 逐字节一致（旧 SC7 语义，#433 把它从默认路径降为兜底）。

src/harness/verify/verify-loop.ts:804-813

fail-open点击展开

人话：裁判自己出了问题（说话格式不对、进程挂了），宁可停下来报告「没法判定」，也绝不顺手盖章通过。误放行是最坏的结局。

精确：判官 abort / transport 错 / schema 错 → verdict = unstable，不注入信封、不静默放过，终局如实报告。
