# Feishu / Lark platform facts

This page is a **per-platform facts page**: it records only verified platform
constraints of one IM bridge target (here: Feishu / Lark) plus the items that are
still unverified and how to measure them. It makes **no design decisions** — those
live in the spec. Future bridge targets get their own sibling page under
`docs/platforms/`, so the platform-specific numbers never mix across targets.

Every fact below carries the official Feishu / Lark documentation URL it came from.
Entries whose research note was taken at summary level are flagged
`(re-read pending)` — treat them as directionally right, not as quotable numbers
until the page has been re-read.

## Scope of this page

- In: platform-side constraints (endpoints, topics, scopes, quotas, payload shape,
  documented absences), and what must be measured before being relied on.
- Out: architecture, module boundaries, retries/backoff policy, feature choices —
  all of that belongs in the spec.
- Sources: Feishu / Lark official Open Platform documentation, plus §Measured — entries there
  come from probes run against our own tenant on a stated date and say so. No repo path
  other than this one implies an implementation exists.

| Official Node SDK                                           | `@larksuiteoapi/node-sdk`: `new Lark.WSClient({appId, appSecret, loggerLevel})` + `eventDispatcher.register` + `start()`; encryption/decryption is handled inside the SDK.                                                                                                                          | same page as "Long-connection mode"                                                                                                                            |

| Item                         | Fact                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Source                                                                                                                                                |

| App forms                    | Only two kinds exist — enterprise self-built application and store/marketplace application. There is **no "personal app" form**.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | https://open.feishu.cn/document/home/app-types-introduction/robots-web-applications-and-mini-programs                                                 |
| Availability scope           | A self-built app's availability can be narrowed to a subset of members (including exactly one person), but **every change requires submitting a version for review** and taking effect only after the tenant admin approves.                                                                                                                                                                                                                                                                                                                                                                                                             | https://open.feishu.cn/document/develop-process/test-and-release-app/availability?lang=zh-CN                                                          |

| Bot capability state         | `GET /open-apis/bot/v3/info` requires **no permission scope** and returns `bot.activate_status`, whose documented values are `0` 初始化，租户待安装 / `1` 租户停用 / `2` 租户启用 / `3` 安装后待启用 / `4` 升级待启用 / `5` license过期停用 / `6` Lark套餐到期或降级停用. The response has **no** `bot.enable` field.                                                                                                                                                                                                                                                                                                                    | https://open.feishu.cn/document/client-docs/bot-v3/obtain-bot-info?lang=zh-CN                                                                         |
| App self-inspection endpoint | `GET /open-apis/application/v6/applications/:app_id?lang=zh_cn`, called with the app's **own** `tenant_access_token`, needs no tenant-admin scope and returns the app's own configuration: `scopes[]` (each `{scope, description, level, token_types}`), `callback_info.{callback_type, subscribed_callbacks}`, `app_name`, `owner.owner_id`, `status`, `online_version_id`. So granted-scope inventory and callback transport can be read programmatically instead of walked in the console. **It lists callback subscriptions only — event subscriptions are not exposed**, which is why §Unverified item 8 keeps a live-message half. | measured 2026-09-22 against our own app (see §Measured)                                                                                               |
| Owner open_id is readable    | The same response carries `owner.owner_id`, an `ou_` value, which is the app owner's `open_id`. An admission allowlist can therefore be seeded without waiting for a first message; the `chat_id` still only arrives on an inbound event.                                                                                                                                                                                                                                                                                                                                                                                                | same as "App self-inspection endpoint"                                                                                                                |

## Measured against our own tenant (2026-09-22)

Method: credentials from the environment only; `curl` plus a throwaway `@larksuiteoapi/node-sdk`
1.74.0 `WSClient` under `/tmp`, so nothing here added a dependency to this repo. Every probe
below prints status fields only — no secret, no token, no id value is recorded.

| Probe                                                                              | Result                                                                                                                                                                                                                                                                                                | What it proves                                                                                                                                                                                                            |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/v3/tenant_access_token/internal`                                       | `code 0`, token issued, `expire 7200`                                                                                                                                                                                                                                                                 | the app authenticates on the self-built face and the 7200 s lifetime on this page reproduces exactly                                                                                                                      |
| `GET /open-apis/bot/v3/info`                                                       | `code 0`, `activate_status 2`                                                                                                                                                                                                                                                                         | bot capability present and 租户启用 (per §Bot capability state)                                                                                                                                                           |
| `POST /callback/ws/endpoint`                                                       | `code 0`, connect URL + `ClientConfig` returned; a started `WSClient` logged `ws client ready` and held one connection for 30 minutes with zero reconnect, close or error lines in that window — no public address, from a WSL2 laptop                                                                | long connection is provisioned for this app and is durable, so the `PingInterval` returned by the endpoint keeps a laptop-resident client alive without a reconnect loop                                                  |
| send text / add reaction / patch card element, each with a deliberately invalid id | `99992351`, `99992354`, `99992402` — all _validation_ failures, not permission failures                                                                                                                                                                                                               | the three outbound scopes this spec needs (`im:message:send_as_bot`, `im:message.reactions:write_only`, `cardkit:card:write`) are already granted, and a validation code proves the permission gate was cleared before it |
| `GET /im/v1/chats`                                                                 | `code 0`, empty                                                                                                                                                                                                                                                                                       | `im:chat` granted; bot is in no group yet, so nothing was visible to anyone during these probes                                                                                                                           |
| `GET /application/v6/applications/:app_id`                                         | `code 0`; `callback_info.callback_type = "websocket"`, `subscribed_callbacks = ["card.action.trigger"]`; 36 granted scopes including all five this spec needs (`im:message.p2p_msg:readonly`, `im:message:send_as_bot`, `im:message:update`, `im:message.reactions:write_only`, `cardkit:card:write`) | card-button callbacks are already routed over long connection on a freshly created app, and no outbound scope has to be requested before T6/T7/T8 can run — the remaining permission work is **removal**, not addition    |

Durable finding, not tenant-specific: **an id-validation error code is a side-effect-free scope
probe.** Feishu checks permission before field validity, so calling an endpoint with a
syntactically-invalid-but-well-formed id distinguishes "scope missing" (permission error) from
"scope granted" (validation error) without mutating anything. This is how the row above was read.

Still not measured by these probes: whether an inbound `im.message.receive_v1` **event** actually
arrives over this connection — that needs one real direct message to the bot (§Unverified item 8).
The **callback** half is already configured for websocket transport, so it does not depend on a
manual console step.

## Unverified — measure before relying on it

1. **Whether typing indication exists at all.** Measure: enumerate every interface in
   the `im` domain from the API debugging console and confirm.
2. **Reaction details** — can a reaction be added to another user's or your own
   message, the per-message count cap, whether the same emoji can repeat, how quickly
   add/remove takes effect. Measure: minimal script doing create → list → delete
   against one `message_id`, recording every `reaction_id` and error code.
3. **Conflicting rate-limit numbers.** The frequency-control page says message-class
   interfaces are 100/min while the send-message page says 1000/min and 50/sec.
   Measure: drive traffic flat out for 60 seconds and record where 429 / 99991400
   first appears.
4. **Exact card JSON size cap.** No page gives a number (30KB is the documented send
   limit, not necessarily the card-JSON limit). Measure: send `interactive` messages of
   increasing size and bisect for the rejection point.
5. **Whether mobile clients actually satisfy CardKit's ≥ v7.20 requirement**, and what
   degradation looks like on older clients. Measure: send a streaming card on a real
   phone and observe.
6. **Availability and admin-approval friction.** Partly closed: an app does exist in our
   tenant today, authenticates on the self-built face, and reports `activate_status 2`
   (租户启用) — see §Measured. Not yet tested: what happens when the availability scope is
   narrowed, whether a version submission plus tenant-admin approval is really needed
   before a chosen member can DM it, and how long that takes. Measure: attempt the
   availability change once and record every screen and error.
7. **Encrypt Key / Verification Token signature algorithm** — closed for the mode this
   project uses. The long-connection page states that mode needs no extra decryption or
   signature-verification logic, so no algorithm is required (§Subscription and transport).
   Reopen only if a webhook fallback is ever kept, where the algorithm still matters and
   the page was never located.
8. **Whether `im.message.receive_v1` actually arrives over long connection.** Narrowed: the
   endpoint provisions a connection for our app and a `WSClient` connects and holds steady
   (§Measured), which was the blocking half — the transport exists without a public address.
   Remaining half: an event has never been observed on it. Measure: keep a registered
   listener alive and send the bot one direct message, then confirm the handler logs
   `chat_id`, `chat_type` and `sender open_id`. Note the console ordering trap from
   §Saving long-connection mode requires a live client: the client must be up before the
   subscription mode can be saved.
9. **Two pages could not be fetched** (`.../reference/im-v1` and
   `.../message/get-message-resource` returned a front-end script shell instead of
   content). No conclusion from either was adopted.

## Hard constraints that shape any design

These are the facts that constrain the shape of a bridge regardless of which design
is chosen — the spec decides how to live with them, this page only states them.

- **3-second processing deadline per event/callback** on both subscription modes; a
  slow handler is treated as failure and the event is re-pushed.
- **Webhook domain check must echo `challenge` within 1 second**; webhook needs an
  IPv4 public address. Long-connection mode removes the public-endpoint requirement.
- **At most 50 long-connection instances per application.**
- **Enterprise self-built application only** — long connection is not available to
  store apps, and there is no "personal app" form to fall back on.
- **Long-connection subscription mode can only be saved while a client is already running**,
  so the setup order is credentials → code connected → console, never console first.
- **Encrypt Key / Verification Token are webhook-side only**; long connection carries its own
  encryption and authentication, so the adapter has no signature-verification work in that mode.
- **Availability-scope changes require a version submission plus tenant-admin
  approval**, so narrowing visibility to a test user is not instantaneous.
- **Card payload cap 30KB** (text messages 150KB); the card-JSON-specific cap is
  unverified.
- **Updating a sent message works only within 14 days, only for `interactive`
  messages, at 5 QPS per message.**
- **Streaming card updates require a strictly increasing `sequence`**, cannot change an
  element's `tag`, are capped at 10 requests/sec per card entity, need card JSON 2.0 and
  client ≥ v7.20, and **`streaming_mode` must be explicitly closed at the end or card
  callbacks will not be handled.**
- **No typing indicator found** — progress feedback has to be built from what does
  exist (cards, reactions).
- **Reactions can only be removed by whoever added them**, are unavailable on system
  messages, non-revocatable messages and external groups, and `emoji_type` is a closed
  whitelist of roughly 150 values.
- **Resource download is capped at 100MB per file with Range slices ≤32MB; sticker
  packs cannot be downloaded.**
- **Message-class rate limits are documented inconsistently** — treat the real ceiling
  as unknown until measured, and design against 429 / 99991400 with
  `x-ogw-ratelimit-reset`.
- **`tenant_access_token` lifetime is 7200 seconds** with the 30-minute refresh
  boundary.
